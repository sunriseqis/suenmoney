# 设计决定与理由

改动任何一处之前先读对应章节。每条都标注了**为什么**，因为「结论」容易记住，
「理由」才决定了将来遇到新情况时该往哪边靠。

---

## 一、需求边界

### 只记支出

家庭 2 人共用一套账。目标只有两个：**这个月/今年花了多少**、**花在什么上面**。

### 明确不做

多账本 · 收入项 · 账户余额与对账 · 转账 · 借贷与分摊结算 · 多币种 ·
预算与超支提醒 · 拍照 OCR · 有息分期 · 资产负债与净值

**理由**：这些功能每一个都会把数据模型和交互复杂度翻倍，而它们回答的不是
上面那两个问题。需要时再单独评估，而不是「顺手加上」。

### 退款用负数金额

不单独建「冲销」模型。`amount_cents` 允许为负，报表求和自然抵消。

### 分类最多两级，只能停用不能删除

- **两级**：一级是分析粒度，二级是记账粒度。三级以上没有实际收益，
  却让选择器的交互复杂度上一个台阶。
- **只能停用**：硬删会让历史记录的 `category_id` 变成空值，报表里冒出一块
  「未分类」黑洞，而且这个错误会随同步扩散到所有设备（包括备份）。
  停用后它从新记账的选择列表消失，但历史记录与报表照常显示。
- 停用前必须把该分类下的记录**转移**到别的分类，或停用其子分类 ——
  宁可拦住用户让他决定，也不替他做决定。

### 分类的「框架」不可变，「皮」和「位置」可变

「只能停用不能删除」解决的是**不要制造孤儿引用**，但它不该顺带冻住其他一切。
默认播种的分类树是给所有人用的模板，必然对不上每一家 —— 所以：

- **可变**：名字、图标、颜色。这三样都只是显示层，改了不动任何记录。
- **可变，但限同深度**：二级分类可以在不同一级之间移动（改 `parentId`，
  移动后仍是二级）。因为二级是记账粒度，它挂在哪一级只影响报表的归并口径，
  而这个口径本来就由"当前挂在谁下面"决定。
- **不可变**：一级 ↔ 二级的**跨深度**移动。它会让已有记录的分析粒度发生
  不可预期变化（一级的"餐饮"变成二级，那么它原本汇总的兄弟分类全部改了归属），
  代价远高于收益。真需要时，用「停用 + 新建」两步走。
- **一级分类的「N 笔」累计其子分类。** 原先只数直接挂在它下面的记录，于是
  只往二级记账的家庭会看到一级全是「0 笔」。这个字段本身没说谎，
  但它就印在「停用」按钮旁边 —— 会被读成"这是个空分类，可以安全停用"。
  **显示口径必须服务它旁边的动作**。

### 支付方式只能停用，且**不受历史记录阻挡**

与分类的关键差别：**支付方式是历史事实**。「这笔是招行卡付的」没有替代品，
也不该被改写；若因存在历史记录就禁止停用，这张卡将永远无法退休。
所以只有「进行中的计划还在依赖它」时才拦。

## 二、计划与提醒

### 房贷与分期是同一个模型

「计划 + 待办」：期数有限 = 分期，可续 = 房贷。差异只在期数与创建入口
（手动新建 / 消费时分期待生成），不需要两套定时逻辑。

### 提醒只做「开屏仪表盘」，不做推送

不接 APNs / FCM，不做系统通知、微信、邮件。代价是「不来打开应用就看不到」——
这是明确的取舍，不是遗漏。

### 到期不自动入账，要确认（或显式开自动）

- 自动生成会在用户毫无察觉时改动账目。一旦计划参数填错（金额、起始月、期数），
  错误的记录已经堆积了几个月，回滚很痛苦。
- 计划上带 `auto_post` 开关：房贷设「需确认」，免息分期设「自动入账」。
  默认值是 `需确认`，风险可控。
- **一直没人确认就不产生任何记录**，条目以逾期待办常驻仪表盘（红色）。
  既然要求确认，就不能偷偷替用户入账。
- 逾期后确认时**让用户选择入账日期**（默认填还款日），否则拖延几天就会
  把支出挪到下个月，报表月份归属被打乱。

### 待办确认允许离线，归属 = 谁先同步到服务端就算谁的

这是全系统**唯一一处跨用户的写冲突点**。用 `(plan_id, period_seq)` 唯一约束
做幂等：谁先写入谁成功，后到的撞约束失败并收到「已被家人确认」。

### 改计划 = 改参数 + 重算未来

```
改参数 → 作废所有未执行的待办（status='cancelled'，保留可追溯）
       → 按新参数从「最后一期已确认期的下一个月」重新生成待办
```

- **期序续接，不重排**。如果从 1 重排，「第 3 期」这个说法会随时间改变含义，
  两个人看到的「第 3 期」可能是不同的一期。
- 已确认的历史期待办与支出记录**原地不动**。
- LPR 浮动、提前还款都走这条路，不需要单独的功能。
- 新待办从「最后一期已确认期的下一个月」开始，绝不能与已有历史重叠或漏月。

### 分期按「每期」入账，但仍要能看到原价进度

- 买手机 ¥6,000 分 12 期 → 每期 ¥500 入账。月报表显示的是「这个月实际支出」。
- 代价：那笔 6,000 **永远不会以 6,000 的形式出现在任何报表里**，只以 12 笔 500 存在。
  这是刻意的，因为用户要的是现金流出口径。
- 报表额外展示进度：`原价总额 / 已付金额与期数 / 剩余金额与期数 / 预计结清月`。
- 不做：利息、本金利息拆分、提前还款重算。

### 分期各期之和必须恰好等于原价

`¥1000 分 3 期` → `[333, 333, 334]`，**最后一期补足差额**。

若每期各自四舍五入成 333.33，三期之和是 999.99 —— 账面上凭空少一分钱，
而且这一分会永远留在「剩余未付」里，让分期**永远无法结清**。
这不是凑数，是分期在会计上的标准做法。见 `domain/installment.ts` 与它的测试。

另外：总额小于期数时直接拒绝（会产生金额为 0 的期，而 `amount_cents > 0` 是硬约束）。

### 改计划时未执行的待办是**删除**，不是标记作废

原本打算「标记作废以保留可追溯性」，但那会占住 `period_seq`，
让重新生成的期序必须跳过一堆空洞 —— 界面上「第 25 期」这种说法会变得无法解释。

追溯改由 `plan_revisions` 承担：它记录了「删了几期、又生成了几期、
参数从什么改到什么」。这比留一堆不可见的作废行更有用。

**未开始的计划**与**已开始的计划**走同一条路径：都从「最后一期已执行期 + 1」
续接期序（没有已执行的期就从 1 开始），差别只是前者没有历史。

### 逾期确认时选的日期**不改报表月份归属**

`spendDate` 只记录「哪天实际付的」；归属仍以待办的还款日为准。

理由：这笔钱在计划里就是那天该付的，隔了几天才补点确认不该把它挪到别的月份 ——
否则「忘记点确认」会莫名其妙地改变已经过去的报表。用户要改的往往是「记录上的实际付款日」，
而不是「这笔算哪个月的支出」。

### 自动入账没有定时任务，靠「打开首页」触发

`GET /api/plan-todos?today=...` 会先结算所有到期的自动入账待办。
服务端没有 scheduler：定时任务要额外处理服务器停机期间的补生成、时区、
以及「跑了两遍」的幂等 —— 而这些幂等已经由待办的状态机天然保证了。

**结算是全局的**，不受 `planId` 等筛选条件影响：打开一次首页就该把所有到期的都结清。

`today` 由客户端按本地时区传入，服务端不猜（与报表的 `month` 必填同一个理由）。

### 自动入账的记录人是计划所有者

手动确认时记录人 = 点确认的人；自动入账没有「操作人」，所以取计划的所有者。

### 「撤销入账」必须连带压住自动入账

计划待办确认入账后要能撤销，但**仅把状态改回 `pending` 是假的**：
`settleAutoPost` 的选取条件是 `status='pending' AND auto_post=1 AND 还款日 <= 今天`，
用户下次打开首页它就立刻被重新入账，表现是「撤销按了没用，过一会儿又回来了」，
且不报错。

所以要给待办加一个「本期不再自动入账」标记（`plan_todos.hold_auto_post`，
migration 002），`settleAutoPost` 的 WHERE 里带上它。
**恢复跳过的期次同样要置上这个标记** —— 跳过的期次通常已经到期甚至过期，
恢复成 `pending` 的那一刻就满足 `还款日 <= 今天`，会被当场自动入账，
又是一个「按了没用」。恢复的语义是「放回待办列表等我处理」，不是「立刻替我付款」。

标记一旦置上就不再自动清 0，手动确认也不清：清掉会埋一个
「撤销过的手动确认，某天又被自动入账」的隐性反悔。改计划时待办整批重建、
新行默认 0，**那才是「重新开始」的时机**。

这是一类值得记住的失败模式：**当"撤销"与"自动执行"共用一个状态判断时，
只改状态不改判断条件，撤销就是假的 —— 而且因为不报错，看起来只是"偶尔不灵"。**

### 撤销 = 软删支出 + 待办回待办，不做物理删除

一次撤销在同一事务里写三条东西：支出打墓碑（软删 + `op:'delete'` 变更）、
待办回 `pending` 并清空 `posted_date / confirmed_by / confirmed_at / expense_id`、
置 `hold_auto_post = 1`。

- **支出必须软删而不是物理删除**：同步层靠 `changes` 做增量，
  物理删除会让其他设备永远不知道它没了（同「删除 = 墓碑」那节）。
- **待办不能删、也不能留期序空洞**：进度是相对于计划整体算的，
  删掉一期会让「已还 N 期 / 剩余 M 期 / 预计结清」全部错位。
  回 `pending` 保留位置，只是把它压住，用户可以再确认回来。
- **撤销是可逆的**：再确认一次就会生成一笔新支出（不是复活旧墓碑）。

### 撤销与恢复的权限和「确认」对称

确认是家庭共同事务，两人都能做；撤销是它的逆操作，也两人都能做。
这不是放松：撤销本身可逆，而它唯一的破坏性动作（软删支出）留下的墓碑
同样可以通过重新确认覆盖。

与之对照，`softDeleteExpense` 拒绝直接删「计划生成」的支出
（提示「请在计划里作废该期」）—— 计划生成的支出只有计划这条路径能动它，
这是**有意的一条单行道**，不是遗漏。

### 撤销入口只在计划的期次列表，交互做两套

仪表盘是「该处理了」的即时视图，撤销是回看既往；放一起会让两类操作同权重，
而其中一个要动已经记账的钱。

入口做两套、走同一段逻辑：**期次行左滑露出动作**（触屏）+
**行内小按钮**（桌面端没有左滑手势，只有左滑等于桌面端无路可走）。

**跨月要警告**：支出的月份归属锚在还款日，撤销一笔属于上个月的支出会让
那个月的合计当场变小。先告知金额与月份再动手 —— 一个已经看过、已经对过账的
数字变了，用户多半会以为数据坏了。

### 有息分期不做

有息分期的真实成本 ≠ 金额/期数，要引入手续费/利率模型，复杂度翻倍而收益极低。
遇到有息分期按「全额记当期」当普通消费处理。

## 三、数据与时间

### 金额一律整数「分」

`REAL` / `DECIMAL` 在 SQLite 里是 IEEE754 浮点，`0.1 + 0.2 = 0.30000000000000004`，
累计求和会出现「总账差一分钱」这类查不出原因的 bug。前端解析也走整数
（`parseYuanToCents` 绝不用 `parseFloat(x) * 100`）。

### 业务日期是 `YYYY-MM-DD` 字符串，不是时间戳

- 用时间戳存支出日期，会因设备/服务端时区不同而让一笔账掉进相邻月份，
  **整月报表悄悄出错**。
- 存字符串，按月聚合就是前缀匹配（`LIKE '2026-01%'`），零时区换算。
- **「今天」由客户端按本地时区判定后传入，服务端不自行推算业务日期。**
  这是报表接口把 `month` 设为必填的原因：服务端常年跑 UTC，让它猜「现在是几月」
  会制造只在跨零点复现的归属错位。
- 审计时间戳（`created_at` / `updated_at`）另存 UTC ISO8601，两者职责分离。
- 日期工具的运算全部借 `Date.UTC` 并只用 `getUTC*` 取回，保证与设备时区无关。

### 报表月份归属以**还款日**为准

这是现金流出视角 —— 回答「钱什么时候出去」，而不是「什么时候消费的」。
所以一笔 1 月 11 日的消费，若账单日 10、还款日 28，就归属 2 月。

### 信用卡账单周期

消费日 `d`，账单日 `B`，还款日 `R`：

| 情形 | 入账日 | 还款日 |
|---|---|---|
| `d ≤ B` | 本期 `B` | 本期 `R` |
| `d > B` | 次期 `B` | 次期 `R` |

- 账单日当天消费算本期（我们自己定死的规则，不留「看情况」）。
- 还款日的「期」必须与入账日对齐：`R > B` 同月，否则次月。
  用 `R > B ? 本期 : 次期` 判定，等于或小于都推到次期 —— 因为还款日必须晚于入账日。
- 现金 / 储蓄卡没有账单周期，`入账日 = 还款日 = 消费日`，运行时推导、**不落库**。

### 月末无此日时钳到当月最后一天，绝不顺延

「每月 31 号」在 2 月不存在。若顺延到 3 月 1 日，「2 月的房贷」就落到了 3 月，
报表月份归属直接错乱，而且只在特定月份出现。

### `posting_date` / `repayment_date` 冗余落库

报表的核心查询是「按 `repayment_date` 的月份聚合」，必须能走索引。现算意味着
全表扫描 + 每行一次账单周期推算，且无法建索引。

这是**为查询而反范式的计算值**，与「把 `入账日=还款日=消费日` 这种常量塞进
支付方式表」是两回事 —— 后者才是没有意义的冗余。

### 列表顺序**不能按 name 排序**

SQLite 默认的 BINARY 排序就是 UTF-8 字节序，对中文没有任何语义。
「招行信用卡」的「招」(U+62DB) 会排在「现金」的「现」(U+73B0) **前面** ——
而列表第一项就是记账抽屉的默认选中项。

后果很具体：用户随手记一笔，默认用了信用卡，还款日跨到下个月，
本月报表纹丝不动，看起来像「没记上」。

所以顺序用 `sort_order, created_at, rowid, name`：`created_at` 反映用户自己的
建立顺序，`rowid` 是同一毫秒内的精确插入序兜底（`created_at` 只到毫秒，
打平后会退回按 name 比，坑就复现了）。

### 单笔金额上限 10 亿元

不是业务规则，是**输入防呆**。多按几个 0 会得到天文数字，瞬间把月度总额、
分类占比、环比全部污染成无意义的值。「金额打错一笔，整月报表失去参考价值」
是记账里真实且高频的挫败。

## 四、同步与离线

### 服务端权威 + 客户端全量副本

客户端持有完整数据，可独立运行；服务端只做同步中转与管理后台。
家庭账本十年也就几万条记录，全量副本在这个规模下完全成立。

### 客户端本地存储用 IndexedDB

不用 SQLite：服务端是 `node:sqlite`（Node 专有 API），Capacitor 里对应的是
`@capacitor-community/sqlite`，两者 API 与 SQL 方言都不完全一致，
会被迫维护两套数据访问层。IndexedDB 在浏览器和 Capacitor WebView 里**同一套 API**。

### 主键全部 ULID，由客户端生成

服务端自增 ID 在离线场景下无解：客户端创建记录时必须立刻知道自己和关联对象的 ID，
否则「记录 → 分类」「记录 → 计划」这些引用关系根本无从建立。

### 删除 = 墓碑，永不物理删除

其他设备的本地副本里还有这条记录，物理删除后它会在下次同步时被「复活」。

### 增量游标用服务端单调递增版本号，绝不用时间戳

客户端时钟与系统时区都不可信。用时间戳做游标迟早丢数据或反复全量。
`changes` 表存变更后的实体快照 —— 不存「引用 + 回读」，因为同一实体在两次拉取
之间可能又变了几次，回读会拿到未来的版本，中间态被静默跳过。

### 冲突用记录级 LWW 兜底

`rev`（Lamport 计数）+ `device_id`，`rev` 大者胜，相等则 `device_id` 字典序大者胜。

**但真正的冲突消解机制是权限规则**：只能改自己创建的记录。两个人各自离线修改的
永远是不同记录，编辑冲突在结构上不存在，只剩同一人两台设备的极端情况。

### 写入只有一个入口（`db/sync.ts`）

漏写 `changes` 不会报错 —— 表现是「手机上这笔账莫名不出现」，只在别的设备复现，
极难排查。所以路由层不许直接拼 `INSERT`。

### 事务用 `BEGIN IMMEDIATE`

裸 `BEGIN` 是延迟事务，先以读锁开始、首次写入时才升级为写锁，
两个并发请求会在升级点互相等待并触发 `SQLITE_BUSY`。

## 五、权限

| 对象 | 读 | 增 | 改 / 删 |
|---|---|---|---|
| 支出记录 | 两人都可 | 两人都可 | **仅创建者** |
| 计划 | 两人都可 | 两人都可 | **仅创建者** |
| 分类 / 支付方式 | 两人都可 | 两人都可 | 两人都可（共享字典） |
| 服务器配置、账号 | — | — | 仅管理员 |

- 记录人 = 登录账号（外键），**不做「代记」** —— 替家人记一笔会让记录人变成自己，
  权限与统计全乱。
- **服务端必须强制校验**，客户端隐藏按钮不算权限控制。
- 不允许把最后一个管理员降级，否则会出现「有账号但没人能进后台」的死局。
- 计划生成的记录**只允许改备注**：金额与日期来自计划和它的待办，独立修改会让
  「已还多少期 / 剩余未付」与台账对不上，而且**没有任何机制能发现这种不一致**。

## 六、认证

### 不透明会话令牌，不用 JWT

- `crypto.randomBytes(32)` 生成，库里**只存 SHA-256 哈希**，明文只返回一次。
  数据库被拷走 ≠ 会话被冒用。
- 不依赖任何服务端签名密钥 —— JWT 的密钥一旦变化就是全员掉线。
- 可以按设备列出、单独吊销。
- 有效期 180 天：家庭自用，「过几天就要求重新登录」是纯粹的骚扰，
  安全性由「只存哈希 + 可吊销」保证，而不是靠短有效期。

### 口令哈希用 scrypt

`bcrypt` / `argon2` 都是原生模块，需要本地编译工具链。为哈希 2 人家庭的口令
而要求部署环境装 C++ 编译器不划算。scrypt 是内存硬的，Node 标准库直接提供。

### 防用户名枚举

- 用户不存在时也跑一次同开销的 scrypt，抹平时序差异。
- 「用户名不存在」与「密码错误」返回完全相同的提示。

### 登录限流

同一来源 + 同一用户名，15 分钟最多 10 次。家庭服务暴露在公网时这是最低限度防线。

### `/api/auth/setup` 只在系统里一个用户都没有时可用

它是「部署后怎么进后台」的答案，不能变成「陌生人自开管理员」的后门。

## 七、界面

见 `docs/design/flat-design.md`。此处只记与需求直接相关的：

- **支出金额不加语义色**，靠超大字号 + `tabular-nums` 撑视觉重量。
  屏幕上的颜色越多，金额就越不显眼。
- **流水列表行 15px**，超大字号留给首页总额与报表大数字。
  列表是「数据」，不是「排版展示」。「一屏能扫多少条」直接决定高频使用的体验。
- **底部固定入口，不用悬浮球**。悬浮按钮会盖住列表最后一条，且滚动时始终悬在内容上。
- **≥1024px 换成顶部导航 + 双栏**。Web 端承担管理后台职责，桌面给 720px 窄栏会让
  两侧各空 360px；但断点不选 768px —— 900–1000px 的平板仍是触摸窄屏设备。

### 饱和色的面积必须与「必须现在处理的事」成正比

待办卡与「本月待还」的紧急度**只由左侧 4px 色条与状态文字表达，卡片底色一律中性**。

这条试错了两轮才定：先是一律琥珀满色（一屏五块饱和色，读起来像五条并列的警告横幅，
**紧急度反而消失**，因为全都一样刺眼），再是按紧急度分色填充（语义对了，
但两笔逾期就变成三块红加两块琥珀，**比第一版更花**）。

结论：问题不是「用什么颜色」，是**填了多少面积**。满色卡片在待办只有 1 笔时看着还行，
积到 5 笔就是一堵色墙 —— 而待办积起来恰恰是最常见的状态。中性卡 + 色条在 1 笔和 20 笔时都成立。

紧急度判定统一在 `web/src/utils/urgency.ts`，首页与报表两处共用，
各写一遍的话「几天算紧急」迟早只在一处生效。

### 分类图标存名字，不存组件

`categories.icon` 会随同步下发到所有设备。存组件名或数组下标的话，任何一个客户端
换了图标库版本都会让**别的设备**解析不出图标。存一个稳定的 kebab-case 字符串，
解析表放在前端，遇到不认识的名字回落到通用图标 —— **永远不会崩，最差只是不够好看**。

解析优先级是 **显式存储的 icon > 按分类名反查 > 通用图标**。中间那条不是优化：
默认分类是早期种下的，那 34 条记录的 `icon` 全是空字符串，而只要前端还认得
「外卖」「房贷」这些名字，**存量数据不用迁移就能立刻有图标**。

支付方式反过来 —— **按类型推断就好**（`cash → banknote`、`credit → credit-card`），
不给 `payment_methods` 加字段：它只有两种类型，图标完全由类型决定，
加一列只是让用户有机会把「现金」配成信用卡。

### 记账抽屉必须**明说这笔会记在哪个月**

这是本项目里最容易被忽略、却最容易造成误解的一条信息。

信用卡的还款日很可能落在下个月，于是用户记完一笔回到首页，看到「本月还是 0」，
会认为保存失败。**第一次做浏览器端到端验证时，我自己就被这件事骗了一轮** ——
查了数据库才确认记录其实好好地存在，只是归属下个月。

所以抽屉在用户选完支付方式与日期后，立刻显示：

- 同月：`还款日 9月27日`（低调，次级色）
- 跨月：**`这笔会记在 2026 年 10 月（还款日 10月28日）`**（醒目，强调色 + 加粗）

**实现方式刻意选了一次服务端请求**（`POST /api/expenses/preview`），而不是在前端
再实现一遍账单周期：那段逻辑是整个项目最容易「看着对、少数情况下错一个月」的地方，
两份实现迟早漂移，而漂移的方式是**安静地算错**。宁可多一次请求。
测试里有一条断言专门保证「预览结果与真实写入完全一致」。

### 记住上次用的分类与支付方式

记账是高频动作，绝大多数时候重复的是同一组选择。每次都从第一项重新选，
等于每天多做两次没有信息量的点击。存在 `localStorage`，
且沿用前会校验「它现在仍然可选」（分类可能已被停用）。

### 空状态文案要指对地方

写过「点**右下角**『记一笔』开始」—— 但入口在底部导航栏里，不是悬浮球。
用户的视线被引到错误位置后，第一反应是「按钮不见了」而不是「文案写错了」。

### 记账抽屉：一份逻辑，两种容器

窄屏（<1024px）是贴底的抽屉，桌面（≥1024px）是右侧 500px 的定宽面板。

上一版是 `inset-x-0` 通栏且没有 `max-width`：1440px 的屏幕上它就是一个
1440×846 的贴底大抽屉，输入框横跨整屏 —— 那不是「适配了桌面」，
只是把手机上的抽屉拉宽。桌面上鼠标从右侧进入、视线也是从左往右扫，
右侧定宽面板既符合这个习惯，又让背后的页面保持可见
（记账时经常要对照上一笔流水）。

**不拆成两个组件**：字段、校验、保存路径、键盘逻辑全部共用，只有外层容器按断点
切换。两边分开写的话，光「退款怎么切」「跨月怎么提示」这些规则就会开始漂移。

### 「本月已支出」要出现在键盘上方

记账时最想知道的就是「这个月已经花了多少」，但抽屉一弹出来整屏都被盖住，
那个数字恰好是唯一看不见的 —— 于是要么凭记忆记，要么关掉抽屉再去看一眼。

代价是一次 `GET /api/reports/monthly`（聚合查询，很轻），且**不 await**：
拿不到就显示占位符。它是背景信息，不是记账流程的一环，
慢一点都不该让抽屉晚开一帧。

### 报表的构成用环图，排名的行中间要有条

- **构成用环图 + 明细**。之前是「N 行各自独立的横条」，每条都占满自己那一行，
  于是它们之间不可比 —— 「构成」这件事反而看不出来。环图一眼给出整体比例，
  明细给出精确值。用 inline SVG 画弧，不引图表库：这里只需要画弧，
  引一个库的成本远大于收益。
- **排名行（按支付方式 / 按记录人）中间必须有占比条**。这类行的名称与金额摆在
  半栏宽（约 540px）的两端，中间空出一大块，眼睛要横跨整行才能把两者对上。
  注意这与设置页的列表不同 —— 那里一行只有「名称 + 一个尾部值」，右对齐的留白
  是正常的（macOS 设置面板就是这样）。**数据排名不行，中间要有东西。**
- 环图的几何计算放在 `utils/donut.ts`，是纯函数且有单元测试。原因：`offset`
  少累加一段的表现只是「弧画歪了」，界面不报错、颜色也照样是彩的，
  靠肉眼几乎判断不出来。

### 报表页**块纵向堆叠、块内两栏**，桌面不分栏

桌面版曾把报表切成左右两栏（左「钱花在什么上」、右「怎么花的」），已撤掉。
第三轮进一步明确为：**页面层面保持纵向堆叠各块，块内部允许两栏** ——
两者不矛盾，「分栏」指的是把不同的块并排，而不是禁止块自己用两列。

原因是**半栏宽会把两件事同时弄坏**：排名行的占比条缩到 200 多像素，长短差距
看不出来（而条形的唯一作用就是表达差距）；环图也被挤小，弧段细到分不清。
分栏换来的收益本来也不成立 —— 这几块是**同一份数据的三种切法**
（花在什么上 / 怎么花的 / 谁记的），纵向读下来是一条线，不存在跨栏对照的需求。

设计稿里这套结构本来就写作单栏（`.duo { grid-template-columns: 1fr }`），
双栏是实现时自己加的。现在与设计稿对齐：分类构成 → 按支付方式 → 按记录人。

排名行仍在容器 ≥620px 时摊成一行四列、窄容器折两行。注意这个判断依据的是
**行自己所在容器的宽度**（`@container`），不是视口宽度 —— 所以无论外层是
单栏还是将来再分栏，行为都成立。

单栏之后暴露、并已修掉的两个排版问题，都是「拉满宽度」的直接后果：

- **图例不能跟着 `flex-1` 一起拉伸。** 明细行原本被拉到 1000px 宽，
  「购物」在左、「44% ¥1,359.00」在右，中间空出 600px —— 与排名行「中间要有条」
  是同一个病。改用 `max-w-[22rem]`（约等于手机上这一行的实际宽度），
  两种屏宽看起来才是同一个东西。**可复用的结论：一行里只有「名称 … 数值」
  两段时，必须给它一个宽度上限。**
- **名称列要按最长的那一行算宽。** 宽屏排名行的名称列原为 136px，
  装不下「9月28日 还款 · 今天到期」，截成「…· 今天到…」—— 恰好把紧急度
  两个字切掉（而这正是这一行存在的理由）。改 192px。
  不能用 `auto`：每个 `<li>` 各自是一个 grid，列宽随内容变会让各行的条起点参差不齐。

**上面第二条修完之后，又留下了一片新的空白**：环图 + 图例被限到约 352px，
宽屏下右边空出约 700px，于是看起来又像回到了「左侧有东西、右侧全空」。
这是修 A 造成的 B，不是分栏回来了。

第三轮的解法不是把 `max-w-[22rem]` 撤掉（撤掉就退回 600px 空档那个病），
而是**让块内用两栏**：左栏放环图 + 图例，右栏放这个块的补充信息，
把这块宽度用满。判断标准始终是同一个 —— **一段内容自己占满一整行宽度时，
它要么有东西把行填满，要么就该有个宽度上限**，两者必居其一。

同一条思路的另一半在首页：首页 hero 原本也有「支出构成」堆叠条，
与报表的环图是同一份数据的两种画法。**同一份数据在一个应用里出现两次，
才是「这一页信息太少」的真正原因** —— 删掉重复的那块，再补上不重复的
（首页改四项指标，报表补分类环比 / 单笔最高 / 年度同比），两边同时变厚，
而用户要读的总量没有增加。

### 计划卡要有「身份物」，危险动作收进「更多」

- 待办卡补上分类图标、期次、分期进度刻度、下次还款日。之前只有「名字 + 第几期
  + 金额」，而同一屏的流水行有图标有日期有备注 —— 两种卡片像两个产品拼在一起。
- **进度刻度最多画 12 段**。段数本身就是信息（12 期一眼看得出还剩几格），
  但 30 年的房贷有 360 期，逐期画出来只会变成一片灰点。超过 12 期时压缩成
  12 格、按比例取整填充，**精确数字始终由旁边那行文字给出**。
- 动作从「确认入账 + 跳过」两个同权重按钮改为「主按钮 + 更多菜单」：
  跳过是低频且**不可逆**的（跳过的期次不会回到待办列表），
  平铺等于把误触的代价做得和正常操作一样低。
- 卡片**不能** `overflow-hidden`。左侧 4px 色条靠它裁圆角，但「更多」菜单会被
  一起裁掉 —— 圆角改由色条自己带（`rounded-l-md`）。

### 「图标取自己的、颜色跟一级走」收敛到字典 store

二级分类用**自己的图标**，但**颜色跟一级走** —— 用户给「餐饮」选的紫要落在它所有
子分类上。这条规则原先散在各个调用处，漏掉一处的表现只是「这一页的颜色跟别处
不一样」，不报错、也不容易被发现。

现在统一由 `dictionaries.visualOf(categoryId)` 给出（图标 + 颜色 + 用于推导颜色的
名字），`CategoryIcon` 也支持直接传 `categoryId`。报表那种**聚合结果**只有 name、
没有完整的 Category 对象，继续走 name/color 入参，两条路互不干扰。

## 八、首次安装

### 必须播种一个默认支付方式

分类为空只是记账时不方便；**支付方式为空会让「记一笔」直接走不通** ——
抽屉显示「还没有可用的支付方式」，保存键永远点不动。
全新部署的人第一步就卡住，而且不知道要去设置里建。

所以 `db:init` 播种一个「现金」。**只播种现金**：它是唯一普适的默认值，
信用卡的账单日/还款日因卡而异，替用户猜一个反而会让他记错账。

## 九、数据的进出

### 「导出」和「备份」是两个功能，不是一个功能的两个参数

- **导出**：可指定时间范围（全部 / 按年 / 按月），文件**自包含**
  （该期间支出 + 全量配置 + 该期间计划与待办），用于对账、报税、迁移。
- **备份**：**始终全量**，只服务「一键恢复」。

**理由**：如果只有一个入口、只是多一个范围参数，用户会把「按月导出」当成
月度备份拿去恢复 —— 而恢复是覆盖性的，于是**静默丢掉其他月份**。
这类错误的发现时间以"年"为单位，代价是数据本身。
把两者的范围和用途在 UI 上摆成两件事，比写一段警示文案可靠得多。

### 按年 / 按月的口径必须与报表同源

期间筛选一律锚在 `repayment_date`（前缀匹配），与 `reports.ts` 的聚合口径一致。
**不能改用消费日 `spend_date` 去筛** —— 那样「9 月导出的合计」与「9 月报表的合计」
会不相等，而这种不一致看起来像丢数据，排查方向会完全跑偏。

### 跨期计划不裁剪

一条计划只要有任何期次落在导出期间内，就**整条（含全部期次）**带出。
否则一条 12 期房贷按年导出会只剩"12 期里的 5 期"，导入后
「已还 N 期 / 剩余 / 预计结清」全部错位 —— **计划的进度是相对于计划整体算的，
不是相对于某一年**。已入账但支出落在期间外的期次，那笔支出也一并带出。

### 导入是合并去重，不是覆盖

指纹用 `entity_type + id`。主键全部是客户端生成的 ULID，所以同一份文件
重复导入不会产生重复记录 —— 这是阶段一预埋「主键全部 ULID、由客户端生成」
时顺带换来的能力，现在才用上。

### 恢复必须走 `db/sync.ts`

一键恢复**绝不能直接往表里灌数据**：每次写入都要 `recordChange` 落 `changes`
+ 递增 `rev`。否则其他设备永远同步不到，而且**不报错** ——
同「写入只有一个入口」那节的论证。恢复前先自动存档一份当前全量快照作为安全网。

### 入口仅在 Web，移动端不含导入导出

采纳的直接后果要明说：**手机本地副本一旦损坏，用户只能回到电脑上恢复。**
这是一个被显式接受的取舍，不是待办。落地方式是**移动端的设置页不挂这一页**
（而不是隐藏按钮）—— 屏幕再小也不渲染它，比运行时判断可靠。

接口本身不绑 Web 会话形态（纯 HTTP + 查询参数），Web 只是它的一个消费者，
这样以后加 cron 归档或 CLI 备份不必改接口。这层解耦成本为零，
但不写清楚就会被做成"必须带浏览器会话态"。

（计划待办的撤销 / 恢复与自动入账的关系，见第二节
「『撤销入账』必须连带压住自动入账」。）
