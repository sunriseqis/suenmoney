# 设计系统：Flat Design（扁平）

## 一、哲学

**移除一切人工深度。** 没有投影、没有倒角、没有拟真渐变、没有纹理。
层级完全由**字号、字重、色块、几何形状**承担。

1. **零人造深度** —— Z 轴不存在。但视觉层级通过尺度、颜色对比、平面形状的
   战略叠加来建立。
2. **颜色即结构** —— 用整块背景色划分区块与分组，而不是用线或阴影。
   颜色转换是硬切的，绝不渐变模糊。
3. **排版即界面** —— 字号与字重承担层级重任。几何、粗黑、要求注意力。
4. **几何纯度** —— 矩形、圆、方块主导。圆角统一且适中。不用有机形状。
5. **交互反馈** —— 悬停与按压通过颜色变化、缩放、瞬时过渡表达，**绝不用阴影深度**。
6. **战略装饰** —— 背景里的大型低透明度几何形状提供视觉趣味，不破坏扁平感。

## 二、令牌

见 `web/src/styles/tokens.css`（权威来源，本文件只记推导与偏离）。

### 浅色（原始设计系统基准值）

| 角色 | 值 |
|---|---|
| 画布 | `#FFFFFF` |
| 前景 | `#111827`（Gray 900） |
| Muted | `#F3F4F6`（Gray 100） |
| 描边 | `#E5E7EB`（Gray 200） |
| Primary | `#3B82F6`（Blue 500） |
| Secondary | `#10B981`（Emerald 500） |
| Accent | `#F59E0B`（Amber 500） |

### 暗色（本项目推导）

原始设计系统只有浅色。暗色的推导逻辑是**把 Gray 900 从「前景」换成「背景」，
三个强调色各上移一档以补偿深底上的亮度损失**，描边与次级底色退到 Gray 700 / 800。

| 角色 | 值 | 对比度 |
|---|---|---|
| 画布 | `#111827` | — |
| 次级底色 | `#1F2937`（Gray 800） | — |
| 前景 | `#F9FAFB` | 16.4:1 |
| Muted 文字 | `#9CA3AF` | 7.0:1 |
| 描边 | `#374151`（Gray 700） | — |
| Primary 文字 | `#60A5FA` | 7.0:1 |
| Secondary 文字 | `#34D399` | 9.2:1 |
| Accent 文字 | `#FBBF24` | 10.6:1 |

**为什么暗色是「几乎免费」的**：扁平系统本来就没有阴影，所以不存在
「阴影在深色下要重新调」这个问题 —— 而这恰恰是拟物类设计系统做暗色最大的成本。

### 主题切换机制

```
<html data-theme> 只在用户**显式选择**主题时写入
不写该属性 = 跟随系统（由 prefers-color-scheme 分支接管）
```

不写属性时是真正实时的：用户在系统里切深浅色，界面立刻跟着变，无需刷新。
显式选择 `light` 会锁定浅色，哪怕系统是深色 —— 否则用户的选择形同虚设。

## 三、可读性：本项目追加的硬约束

原始设计系统只给了「对比度要高」的原则，没有给具体数值。本项目追加一条：

> **任何「文字 / 底色」组合都必须过 WCAG AA：正文 ≥ 4.5:1，
> 大字号（≥24px，或 ≥18.66px 且粗体）与纯图形 ≥ 3:1。**

为此把每个强调色拆成**三个角色，不可混用**：

| 角色 | 用途 | 说明 |
|---|---|---|
| `--x` | 纯图形（图标、图表、装饰） | 可以低对比 |
| `--x-fill` | 填充块 | 其上的文字颜色见 `--on-x` |
| `--x-text` | 该色**当文字**用在浅/深底上 | 必须单独给深一档 |

**为什么必须拆**：原始设计系统给的 `#3B82F6`、`#10B981`、`#F59E0B` 直接当文字用
全部不达标 —— 白底分别只有 **3.68 / 2.54 / 2.15**。把它们原样用作文字或图标文字，
就是明确的 WCAG 违规。

## 四、与原始设计系统的三处偏离

| 偏离 | 原始值 | 本项目 | 理由 |
|---|---|---|---|
| 主按钮填充 | `#3B82F6` + 白字 | `#2563EB` + 白字 | 原值配白字只有 **3.68:1**，不到 AA 的 4.5:1；深一档后 5.2:1 |
| 暗色主题 | 无（仅浅色） | 按扁平逻辑反向推导 | 晚上睡前记账是高频场景，白底刺眼 |
| 字号基准 | 未规定 | 列表 15px、总额 56px、报表 96px | 见下 |

**关于字号**：原始设计系统只写了密度是 "Medium / Functional"，没有规定 px。
所以列表用 15px 不越界 —— **列表是「数据」，不是「排版展示」**，
而「一屏能扫多少条」直接决定高频使用的体验。撑视觉重量的任务交给
`--fs-amount` / `--fs-display` 两档超大字号，尺度台阶拉开后层级反而更清楚。

## 五、中文适配

原始设计系统是为拉丁字母设计的，直接照搬会在中文界面里失效三处：

### 1. 「全大写」在中文里不存在

原始系统靠 `UPPERCASE + 字距` 制造标签感。中文字符没有大小写，
这条路走不通。替代方案（`web/src/styles/base.css` 的 `.label-cn`）：

> 小字号（12px）+ 加宽字距（0.08em）+ 半粗（600）+ 次级色

### 2. 字体没有中文字形

`Outfit` 只覆盖数字与拉丁字母。字体栈写成：

```css
'Outfit Variable', 'MiSans VF', -apple-system, 'PingFang SC', 'HarmonyOS Sans SC', 'Noto Sans SC', sans-serif
```

目的是**金额永远由 Outfit 绘制、中文字形由 MiSans 兜住**，
不会出现「数字圆润、中文方正」两种气质打架。

字体从 npm 包**本地**引入（`web/src/main.ts`），不走 CDN：

| 包 | 字体族 | 字重 | 说明 |
|---|---|---|---|
| `@fontsource-variable/outfit` | `Outfit Variable` | 100–900 | 拉丁字母与数字 |
| `misans` | `MiSans VF` | 150–700 | 中文，切成 56 个 `unicode-range` 分片按需下载 |

移动端是 Capacitor 打包，必须离线可用 —— 外链字体在断网时会直接退化成系统字体。

**踩过的坑（务必读）**：字体栈里写着 `'MiSans VF'` 但 `main.ts` 里没有引入它，
是**不会报错的** —— 浏览器只是静默回落到后面的系统字体，观感变差但一切"正常"。
改字体名时必须同步改 `main.ts` 的 import 与 `tokens.css` 的字体栈，两处的名字要**逐字一致**。

⚠️ **字重上限**：MiSans VF 只到 700，Outfit 到 900。所以**中英混排**的元素字重不要超过 700，
否则英文取 800/900、中文被截在 700，同一行出现肉眼可见的粗细断层。
只有纯数字元素（首页总额、报表大数字）才允许用到 800。

### 3. 等宽数字

中文排版下金额的位数对齐问题更突出。全局启用：

```css
font-variant-numeric: tabular-nums;
font-feature-settings: 'tnum' 1;
```

这是记账应用里比任何视觉装饰都更影响实际使用的一条 ——
比例数字会让「¥1,111」和「¥9,999」位数错位，列表滚起来数字左右跳。

## 六、组件规则

| 组件 | 规则 |
|---|---|
| 卡片 | 纯色块（`--bg-subtle` 或强调色淡底），**无阴影无边框**，圆角 8px，内边距 16–32px |
| 按钮 | 实心填充 + 圆角 6–8px，高 44–56px（满足触摸目标），`duration-200`，按下 `scale-95` |
| 选项胶囊 | 见 `web/src/components/ChipButton.vue`。选中 = `--primary-fill` 填充 |
| 输入框 | `--bg-sunken` 底 + 无边框，聚焦时给硬轮廓（`outline: 2px solid var(--focus)`） |
| 焦点态 | **必须显式给**：扁平系统没有阴影，不能靠发光或扩散表达焦点 |
| 分区 | 用色块或留白，**不用细分隔线** |
| 背景装饰 | 低透明度几何形状可接受（`bg-white/5`），但不得影响正文对比度 |

## 七、颜色纪律：饱和色的面积必须与「必须现在处理的事」成正比

这是踩了两次才定下来的一条，记下来是因为它很容易反过来做。

**第一版**：所有待办卡一律琥珀满色。一屏五块饱和色 → 读起来像五条并列的警告横幅，
**紧急度反而消失了**，因为全都一样刺眼。
**第二版**：按紧急度分色填充（逾期红 / ≤1 天琥珀 / 更远中性）。语义对了，
但演示数据里恰好有两笔逾期，于是变成三块红加两块琥珀，**比第一版更花**。

结论：问题从来不是「用什么颜色」，是**填了多少面积**。最终规则：

| 位置 | 做法 |
|---|---|
| 卡片底色 | **一律中性**（`--bg-subtle`），三档完全一致 —— 底色不参与表达紧急度 |
| 左侧 4px 色条 | **紧急度唯一的着色位置**。逾期 `--danger`、≤1 天 `--accent`、更远 `--line`（等于没有） |
| 状态文字 | 用 `--danger-text` / `--accent-text` / `--ink-muted`（**不能**用 `--danger` / `--accent` 本体，那是图形色，当文字不达标） |
| 动作按钮 | 统一 `--primary-fill`。它成了整页**唯一**的强色块，扫视落点从「一片红黄」收敛到「那个蓝按钮」 |

饱和色总面积从屏幕的 **~65% 压到 ~2%**，视觉重量回到首页那个「本月支出」大数字身上。

**为什么满色卡片这条路走不通**：它在待办只有 1 笔时看着还行，积到 5 笔就变成一堵色墙，
而待办积起来恰恰是最常见的状态。中性卡 + 色条在 1 笔和 20 笔时都成立。

唯一的例外是**分区级别的色块**（整个 section 一个强调色底），那才符合原始设计系统的
"Vibrant full-section color blocks" —— 它指的是区块，不是列表项。

## 八、图标

`@lucide/vue`（注意不是已废弃的 `lucide-vue-next`）。

**分类图标存的是名字，不是组件、不是索引。** `categories.icon` 会随同步下发到所有设备，
存组件名或下标的话，任何一个客户端换了图标库版本都会让**别的设备**解析不出图标。
存一个稳定的 kebab-case 字符串，解析表放在前端（`web/src/utils/icons.ts`）：

> 优先级：**显式存储的 icon > 按分类名反查 > 通用图标（`tag`）**

「按名字反查」那张表是必要的，不是优化：默认分类是很久以前种下的，那 34 条记录的
`icon` 全是空字符串，而只要前端还认得「外卖」「房贷」这些名字，**存量数据不用迁移就能立刻有图标**，
用户在别处新建的「早餐」「宠物」也能自动命中。用户手动选过的图标永远优先。

**支付方式图标按类型推断**（`cash → banknote`、`credit → credit-card`），不给
`payment_methods` 加字段：它只有两种类型，图标完全由类型决定，加一列只是让用户有机会
把「现金」配成信用卡。分类不一样 —— 分类有成百种语义，图标必须可自定义。

选择器见 `web/src/components/IconPicker.vue`。其中「自动（按分类名推断）」按钮放在
**滚动区之外**：它恰恰是「改错了想撤销」时第一个要找的东西，被 288px 的滚动高度截掉等于没有。

**图标列必须定宽。** 不同图标实际宽度不同，不定宽会让分类名左右错位，
而列表唯一的用法就是「扫」。

## 九、响应式与桌面布局

断点 **1024px**（Tailwind 的 `lg`），不选 768px：900–1000px 的平板仍是触摸窄屏设备，
铺成多栏反而更难用，它们继续走移动布局。

| | 手机（<1024px） | 桌面（≥1024px） |
|---|---|---|
| 导航 | 底部固定栏，图标 + 文字 | **顶部粘性栏**，品牌名 + 图标 + 文字 + 记一笔 |
| 内容宽度 | 720px 居中 | 1120px |
| 首页 / 报表 / 计划 / 设置 | 单栏 | **双栏** |
| 流水 | 全宽列表 | 收窄成 768px 阅读栏 |

**桌面双栏的分栏依据不是「内容多少」，是「用户要不要做决定」**：

- 首页：左 = 该处理了 + 本月待还（要动手），右 = 支出构成 + 最近流水（只需阅读）
- 报表：左 = 分类构成（钱花在什么上），右 = 按支付方式 + 按记录人（怎么花的）
- 计划：左 = 该处理了，右 = 我的计划
- 设置：左 = 账号相关，右 = 共享字典

**实现要点**：桌面只改两个「尺寸令牌」就完成了大半 ——

```css
@media (min-width: 1024px) {
  :root { --content-max: 1120px; --bottom-bar-h: 0px; }
}
```

各页的底部内边距都写着 `pb-[calc(var(--bottom-bar-h)+var(--safe-bottom)+24px)]`，
所以 `--bottom-bar-h` 归零后**所有页面的底部留白会一起收掉**，不必逐页加 `lg:pb-24`。
后者的毛病是迟早漏掉一页，而漏掉时的表现只是页面底部平白多出 84px 空白 —— 不报错，只是看着别扭。

**流水的特例**：一开始按「全宽对账单」做，结果分类名和金额之间空了约 600px，
因为这一行只有「日期 / 图标 / 文字 / 金额」四段，文字段是弹性的，多出来的宽度全变成空档。
表格要宽得靠**增加列**去填（备注一列、支付方式一列、还款日一列），
而不是把四段摊开。在那之前收窄到 768px 是更诚实的选择。

**月份/期间切换器在桌面上要收窄并居中**，且 `h1` 定宽（`min-w-32`）：
手机上是 ← 贴左、→ 贴右（拇指够得到），但桌面上把 24px 的箭头分置 448px 两端，
看着跟中间的「2026年9月」没关系了；定宽还能让月份从「9月」变「12月」时箭头不左右跳。

## 十、CSS 分层：`base.css` 必须包在 `@layer` 里

**这是整个项目里最隐蔽的一个坑，它让全站每个按钮的样式失效过。**

Tailwind v4 把产物放进 `@layer theme, base, components, utilities` 四层，
而 CSS 级联有一条硬规则：

> **未分层的样式永远压过分层样式 —— 与选择器优先级、与源码先后都无关。**

`base.css` 里那两条重置：

```css
button, input, select, textarea { font: inherit; }
button { background: 0 0; border: 0; padding: 0; }
```

一旦它们是未分层的，就会把全站**每一个按钮**上的 `bg-*` / `px-*` / `py-*` /
`text-*` / `font-*` 工具类悄悄干掉。表现是所有按钮退化成一行裸文字：
没有底色、没有内边距（高度塌到 23px）、字重回到 400。

它不报错、不警告、构建通过、测试通过。只有量 computed style 才看得见：

```
类名写着 bg-canvas → 实际 rgba(0,0,0,0)
类名写着 font-bold  → 实际 400
类名写着 py-2.5     → 实际高度 23px
```

同一元素上的 `rounded-sm`（6px）**却是生效的** —— 这种"有的生效有的不生效"
正是分层问题的指纹（`rounded-*` 不与重置冲突）。

**规则**：基础重置 → `@layer base`；可复用的类（`.label-cn` / `.skeleton` / `.sr-only` / …）
→ `@layer components`。这样 utilities 层始终能覆盖它们。

**`tokens.css` 是唯一的例外，它必须保持未分层** —— 自定义属性要压过 Tailwind 的
`@theme` 层，否则主题切换会失效。它只声明变量，没有元素样式，所以不会误伤工具类。

## 十一、CSS 陷阱二：不要用 `display: block` 隐藏/显示 `<table>`

流水列表有宽屏表格与窄屏两行式两套结构，切换时如果写成：

```css
.fulllist { display: block; }   /* 想让它在宽屏出现 */
```

**表格会被破坏。** `<table>` 变成 `block` 后，浏览器会在内部生成一个**匿名表格**
包住行与单元格，那个匿名表是 shrink-to-fit 的 —— 外层元素确实占满 100%，
但里面的表格只延伸到各列固定宽度之和（约 700px）就停了，右侧留一大块白。

**危险之处在于它极难被发现**：如果你量的是外层元素的 `getBoundingClientRect().width`，
它会老老实实返回 100% —— 和卡片内容宽度**相等**，看起来一切正常。
正确的量法是**最后一列单元格的右缘**与卡片内容右缘的差。

```css
.fulllist { display: table; }   /* 正确 */
.minilist  { display: block; }  /* minilist 是 div，block 没问题 */
```

同一类错误的通则是：**验证布局时要量"内容的末端"，不是"容器的边框"**。
容器永远是对的，内容才会在悄悄收缩。

## 十二、本项目独有的一条 UI 决定

**支出金额不加语义色**（不用红/绿），靠 `#111827` + 超大字号 + 等宽数字撑重量。

理由：屏幕上的颜色越多，金额就越不显眼。**颜色只用于表达「需要行动」**
（见第七节的紧急度规则）与**分类图标**，不用于表达数值本身。将来若有收入项，再引入颜色区分。
