## 一、分支 A：期间选择器（问题 1、2）

### 现状

两个页面各自内联了一份「上一个 / 下一个」箭头，只能逐月翻：

- `web/src/views/LedgerView.vue:132-143` —— `@click="month = shiftMonth(month, -1)"`
- `web/src/views/ReportView.vue:142-144` —— 自己的 `stepMonth`，按 `scope` 走月或年

**所以要跨到半年前要按 6 次**，而且桌面端它是独占一行的。

### 决策

1. **抽 `web/src/components/PeriodPicker.vue`**，三处共用：流水页、报表页（月 / 年两种
   scope 都在内）、导出页（**补充**带来的第三个消费者）。
2. **标题本身可点** → 弹出年月面板：年份可上下切换 + 12 个月网格。
3. **桌面端不再独占一行**，与筛选胶囊 / 搜索框同一行，右对齐。
4. **往后到当月为止**（未来没有数据）。往前不设限。
5. 面板里必须有**一键回「本月 / 今年」** —— 翻远了回不来是这类组件的经典毛病。

### 为什么不做「<< >> 跳一年」

最省事的"快跳"是加两个跳一年的按钮。但那是把 6 次点击降到 2 次，用户仍要**猜按几下**；
年月面板是 1 次点到位，而且顺带解决了「我想看看今年 3 月」这种任意跳转。
既然要做面板，就不要再留一套箭头按钮 —— 两套并存的界面没人能预测。

## 二、分支 B：报表的信息布局（问题 6）

### 现状：两件事被混成了一件事

用户说的是「分类构成仅显示在左侧、右侧完全空白，且信息偏少、多数已在首页展示」。
核下来这其实是**两个独立原因**：

1. **右侧空白不是分栏造成的**（上一轮已经把双栏撤成单栏了）。是上一轮为了修
   「图例被拉到 1000px 宽、中间空 600px」而加的 `max-w-[22rem]` —— 环图 + 图例
   被限到约 352px，于是右边空出约 700px。**修 A 造成的 B。**
2. **「信息偏少、与首页重复」**：首页 hero 已经有「本月已支出 + 支出构成堆叠条」，
   与报表的环图确实是同一件事的两种画法。

另外查到一处**「数据已备好、只差画」**：`monthlyReport` 已经返回 `previous`（上月）
与 `change`（环比 `deltaCents` / `ratio`，见 `server/src/db/repo/reports.ts:201-216`），
但前端从未使用过。

### 决策

1. **页面仍是块纵向堆叠**（不回到双栏），但**块内允许两栏**：环图 + 图例在左，
   该块的补充信息在右，把右侧空白填掉。
2. **首页删掉「支出构成」整块**，hero 改补**四项指标**：本月已支出 / 本月笔数 /
   日均 / 与上月环比（环比数据现成）。
3. **报表补三项**（服务端需新增）：分类环比（每个一级分类与上月比）、单笔最高、
   年度同比。
4. **保持平铺**：不折叠、不加二级钻取。

### 为什么

删首页那块是整个分支的关键，理由不是"首页太挤"，而是：**同一份数据在一个应用里
出现两次，才是"信息太少"的真正原因。** 页面上不是缺东西，是**重复的东西占了位**。
把重复的删掉、再补不重复的，两边同时变厚，而总阅读量不增。

### 待复核

「块内两栏」的具体分法（哪些信息进右栏）设计稿里没有对应画面，落地时按本节第 1 条
的口径定，并补一张截图。

## 三、分支 C：底栏 / 抽屉 / 键盘（问题 4、5、7）

### 现状

| 位置 | 事实 |
|---|---|
| 底栏 | `web/src/App.vue:32-36` NAV 只有 3 项（首页 / 流水 / 报表）。底栏排列是 `NAV.slice(0,2)` + 记一笔 + `NAV.slice(2)`，所以记一笔在 **4 格里的第 3 位**。三个 tab 是 `RouterLink`（有激活态着色），记一笔是 `<button>`，只有 `text-ink-muted hover:text-ink`，**没有任何状态** |
| 键盘 | `web/src/components/NumericKeypad.vue` 用 `grid-cols-4` 自动排布，只有「保存」显式定位 → ⌫ 与 ＋ 被挤到第 3 行 |
| 抽屉 | 窄屏底部抽屉，分类在中间、支付方式 / 日期 / 备注更靠下；软键盘弹起后这些要下滑才看得到 |

### 决策

**1. 底栏：记一笔移到最右 + 32px 软色底衬。**

- 移到最右：`NAV` 三项占前三格，记一笔独立在第 4 格。
- **软色底衬而不是填充主色**：它常驻不高亮（点开就进抽屉，没有"选中"状态），
  但需要比另外三个 tab 醒目。软色底衬正好表达「同一组里的特殊项」，
  又不会像实心主色那样与三个 tab 的激活态打架。
- 与桌面顶栏的差异是**刻意的**：桌面那枚（`App.vue:90`）是 `bg-primary-fill` 实心主色，
  因为它在顶栏右侧独立成块、不与任何 tab 同组；底栏这枚与三个 tab 同组，才必须区分层级。
- **实现时同步改掉 `App.vue:121-125` 那段注释。** 它现在写着「记一笔是普通 tab，
  不是特殊按钮」，在当前代码下是**正确的**；一旦按本节改，注释就变成错的，
  而下一个读注释的人会照它改回来。

**2. 键盘：只修错位，不改布局。**

⌫ 钉 `col-start-4 row-start-1`、＋ 钉 `row-start-2`，与显式定位的「保存」凑成整齐的 4×4。

不改布局的理由：这套键盘已经是 4 列、拇指可达，改排布的风险大于收益 ——
而"错乱"这个观感的全部来源就是两个键掉到了第 3 行。

**3. 抽屉：分类常驻 + 摘要行常驻。**

- 分类不再折进"更多"，直接在抽屉里铺开。
- 键盘上方常驻一行**摘要**（已选分类 / 支付方式 / 日期 / 备注），
  重要选择不用下滑就能核对。上一轮已经在键盘上方常驻了「本月已支出」，
  摘要行与它共用这条区域。
- 桌面形态（右侧 500px 面板）不受影响。

### 为什么修抽屉不是"把输入搬上去"

「支付方式 / 日期 / 备注被分屏」的诉求很容易被理解成"把它们都挪到首屏"，
但那样首屏会挤成一团。摘要行的思路是：**不用把控件搬上来，只要把结果露出来** ——
用户要确认的是"我选对了没"，而不是"我要改"。

## 四、分支 D：分类可改 + 账目平移（问题 9）

### 现状

- **服务端改不了层级**：`PATCH /api/categories/:id` 只接受
  `name / icon / color / sortOrder / isEnabled`（`server/src/http/categories.ts:53-62`），
  **不接受 `parentId`**。所以分类建错层级后只能停用重建。
- **转移与停用保护都已实现**：`expenses.ts` 的 `transferExpenses`（逐条写 change）
  与 `categories.ts` 的 `assertCategoryDeactivatable` 都在。
- **前端只能新建 / 停用 / 启用**，不能改名、换图标、换颜色。
- **一级分类的笔数只数直接挂在其下的记录**，于是演示库里一级分类全显示「0 笔」
  （支出全都挂在二级上）。字段本身是对的，但会被读成"这个分类可以安全删掉"。

### 决策

1. **改名 / 换图标 / 换色收进一个「图标 + 颜色」面板**，点分类行右侧的图标打开
   （复用 `IconPicker.vue` / `ColorPicker.vue`）。**不做行内编辑** ——
   行内编辑会让整棵树在编辑态下抖动，两级树尤其明显。
2. **只做「转移」这一种批量动作**，不做"合并到某个分类"等其他变体。
3. **支持同深度移动**：二级分类可以在不同一级之间移动（改 `parentId`，
   移动后仍是二级）。**一级 ↔ 二级的跨深度移动不做** —— 它会牵动报表粒度与
   已有记录的分析口径，代价远高于收益。
4. **一级分类的笔数改为累计子分类**（`decisions.md` 的「分类最多两级」那节要同步更新）。
   理由：`0 笔` 这个显示会把"这个分类下面挂着 7 笔"读成"空分类"，
   而它恰恰就在"停用"按钮旁边。
5. **服务端**：`PATCH` 补 `parentId`，并校验"移动后仍是同一深度"。

## 五、分支 E：计划的撤销与跳过恢复（问题 8）

这一条是六件里**唯一需要改 schema** 的，也是唯一一条现有实现会**静默失效**的。

### 现状

- **确认入账后没有任何反悔路径。**
- **撤销对自动入账的计划完全无效。** `settleAutoPost` 的选取条件是
  （`server/src/db/repo/plans.ts:972-974`）：

  ```sql
  WHERE t.status = 'pending' AND t.deleted_at IS NULL
    AND p.deleted_at IS NULL AND p.state = 'active' AND p.auto_post = 1
    AND t.repayment_date <= ?
  ```

  把待办改回 `pending` 之后，用户下次打开首页它就**立刻被重新入账**。
  表现是「撤销按了没用，过一会儿又回来了」，而且**不报错**。
- **跳过同样不可逆**：`skipped` 不在上面这个选取条件里，跳过的期次永远不回待办列表。
- `plan_todos.status` 的 CHECK 允许 `pending / confirmed / skipped / cancelled`
  （`001_init.sql:301-302`），所以回 `pending` 在 schema 层本来就合法 ——
  挡住撤销的不是状态机，是上面那条 SQL。

### 决策

1. **撤销入口只在计划的期次列表里，不放仪表盘待办卡。**
   仪表盘是「该处理了」的即时视图，撤销是回看既往；放一起会让两类操作同权重，
   而其中一个不可逆（见 `decisions.md` 关于「跳过」的同类论证）。
2. **交互：期次行左滑 60% 露出「撤销」，同时提供行内等价入口。**
   必须两套 —— 桌面端没有左滑手势，只用左滑等于桌面端无路可走；两者走同一段逻辑。
3. **跳过要可恢复**（`skipped → pending`）。
4. **跨月要警告。** 撤销的支出若已计入上个月，撤销会让上个月的合计变化，
   先告知：「这笔已计入 2026 年 9 月，撤销后 9 月合计将减少 ¥X」。
5. **服务端三件事**：
   - `plan_todos` 加「**本期不再自动入账**」标记（migration 002），
     `settleAutoPost` 的 WHERE 补 `AND t.<该标记> = 0`。
     **不加这一列，撤销功能在有自动入账的计划上是假的。**
   - 撤销 = 同一事务里两条 change：支出软删（墓碑）+ 待办回 `pending`
     并清空 `expense_id / confirmed_by / confirmed_at`。
   - 恢复跳过 = `skipped → pending` + 置上「本期不再自动入账」。
     否则恢复的那一刻它就到期了，会被立刻自动入账 —— 又变成用户按了没用。

### 为什么不是"直接删掉待办"

待办删掉之后期序会出现空洞，「已还 N 期 / 剩余 M 期 / 预计结清」全部错位，
而计划的进度是**相对于计划整体**算的。回 `pending` 保留了期次位置，只是把它压住。

### 落地状态（已完成）

| 落点 | 内容 |
|---|---|
| `db/migrations/002_plan_todo_hold_auto_post.sql` | 加 `plan_todos.hold_auto_post INTEGER NOT NULL DEFAULT 0`。默认 0 = 存量待办照旧自动入账，升级不改变行为 |
| `db/repo/plans.ts` | `settleAutoPost` 的 WHERE 补 `AND t.hold_auto_post = 0`；新增 `revertTodoConfirm` / `restoreSkippedTodo`（各在一个事务里落 changes） |
| `http/plans.ts` | `POST /api/plan-todos/:id/revert`、`POST /api/plan-todos/:id/restore` |
| `tests/http/plans.test.ts` | 新增「撤销确认与恢复跳过」6 条：撤销后**再结算一次仍为 pending**（这是本分支存在的理由）、墓碑与 delete 变更、报表回落、重复撤销 409、恢复跳过**不被当场入账**、家人也能撤销 |
| `tests/schema.test.ts` | 迁移执行器用例改为按目录动态断言；新增「002 的列存在且默认 0 / NOT NULL」 |

实现时比方案多定的两条（已回填 `decisions.md`）：

1. **手动确认不清 `hold_auto_post`**。清掉会埋一个「撤销过的手动确认，
   某天又被自动入账」的隐性反悔。只有改计划整批重建待办时它才回到 0。
2. **权限与「确认」对称：两人都能撤销**。撤销本身可逆，且它的破坏性动作
   （软删支出）留下的墓碑可以通过重新确认覆盖 —— 与 `softDeleteExpense`
   拒绝直接删计划支出那条单行道并不冲突，后者管的是「不要绕开计划改账」。

## 六、分支 F：导出 / 导入 / 备份（问题 3 + 补充）

### 现状

**全项目零实现。** `server/src/http/` 下没有任何 export / import / backup 路由；
`SettingsView.vue:105-108` 只有 4 个 tab（分类 / 支付方式 / 计划 / 家庭与账号）。

### 补充（2026-09-28 追加）

> 数据导入导出的**入口仅在 Web 前端**，未来移动端不包含导入导出内容。
> 导出应该可以指定时间范围：**全部 / 按年 / 按月**。

### 决策

**1. 「导出」与「备份」是两件事，UI 上分开摆。**

| | 导出 | 备份 |
|---|---|---|
| 范围 | 全部 / 按年 / 按月 | **始终全量** |
| 用途 | 对账、报税、迁移 | 只服务「一键恢复」 |
| 内容 | 自包含包（见第 3~5 条） | 全量快照 |

理由：如果只有一个入口，用户会把「按月导出」当成月度备份拿去恢复，
**静默丢掉其他月份**。这类错误的发现时间以"年"为单位，代价是数据本身。

**2. 范围口径与报表同源。** 期间筛选必须用
`e.repayment_date LIKE ? || '%'`（即 `reports.ts:83` `scopeClause` 的形状），
可走 `ix_expenses_repayment_date`。**若改用消费日 `spend_date` 去筛，
会出现「9 月导出的合计 ≠ 9 月报表的合计」** —— 看起来像丢数据。
这条要写进实现注释。

**3. 跨期计划不裁剪。** 一条计划只要有任何期次落在期间内，就**整条（含全部期次）**
带出。否则一条 12 期房贷按年导出会变成"12 期里的 5 期"，
导入后「已还 N 期 / 剩余 / 预计结清」全部错位 —— 进度是相对于计划整体的。

**4. 已入账但支出落在期间外的期次，那笔支出要一并带出**（标 `context: true`）。
不带的后果是导入后出现「期次显示已入账、但找不到对应账目」。

**5. 配置全量附带。** 分类 / 支付方式 / 家庭成员没有时间维度，一律全量带出。
好处是任意一份导出都能单独导入到一套空系统，不会出现「支出引用了不存在的分类」。

**6. 导入 = 合并去重，不是覆盖。** 指纹用 `entity_type + id`；主键全部是客户端生成的
ULID，所以同一份文件重复导入不会产生重复记录。

**7. 全部仅 admin。** 导出含全家庭数据、导入会改数据，都不是普通成员的操作。

**8. 接口不绑 Web 会话形态。**
`/api/export?scope=all|year|month&period=2026|2026-09` 是纯 HTTP，
Web 只是它的一个消费者 —— 以后加 cron 归档或 CLI 备份不必改接口。
这层解耦成本为零，但不写清楚就会被做成"必须带浏览器会话态"。

**9. 恢复必须走 `db/sync.ts`。** 一键恢复**绝不能直接往表里灌数据**：
每一次写入都要 `recordChange` 落 `changes` + 递增 `rev`。
否则其他设备永远同步不到，且**不报错** —— 这正是 `decisions.md`
「写入只有一个入口」那条的由来。恢复前**先自动存档一份当前全量快照**，是这条的安全网。

**10. 移动端没有恢复入口，是一个必须显式接受的取舍。**
它意味着：手机本地副本一旦损坏，用户只能回到电脑上恢复。
这条要写进 `decisions.md`，不靠"以后再说"。

### 入口怎么落

`SettingsView.vue` 新增第 5 个 tab「**数据**」，与设计稿 `mockup.html:1196-1200`
的 `账目 / 家庭与数据` 分组对齐。

「入口仅在 Web」的落地方式**不是隐藏按钮，而是移动端的设置页根本不挂这一页** ——
屏幕再小也不会渲染它，比运行时判断更可靠。这也顺带符合 `plan.md` 开头已有的定位：
Web 端承担管理后台职责。

## 九、落地顺序

按「依赖少、改完立刻能看到」排：

1. **键盘错位** —— 最小，纯 bug，完全独立
2. **`PeriodPicker` + 流水 / 报表接入** —— 一个组件解决两个问题
3. **底栏与抽屉**（问题 4、7）
4. **报表块内布局 + 首页删重复块 + 补指标** —— 依赖服务端补的环比三件事
5. **分类改造** —— `PATCH parentId` + 前端面板 + 笔数口径
6. **计划撤销链路**（含 migration 002）—— 排在这里是因为它唯一动 schema，
   且要跨仪表盘 / 计划页 / 报表三处对齐口径
7. **导出 / 导入 / 备份** —— 体量最大，且要先有 2 与 5 的期间与分类口径

## 十、不在本轮范围

- 一级 ↔ 二级的**跨深度**移动分类
- 支付宝 / 微信账单文件解析导入（本轮只做通用格式）
- 移动端的导出 / 导入（**明确不做**，见分支 F 第 10 条）
- 左滑之外的手势（长按菜单等）
