### 〇.1 第二次修正：用户看完预览页之后

预览页出来之后用户提了三条，第一条推翻了本文档第二版的**分工方式**：

> 把支出分类的挪到报表页，职能上做明确区分，首页是概况，纬度横跨月年总。
> 报表是统计，精度细化到每年每月甚至到天。
> 还有累计其实就是一行数据，单独一个卡片会不会太占地方？

三条的落点：

| 意见 | 落点 | 它推翻了什么 |
|---|---|---|
| **分类整体归报表** | §五 第 3 条 | 「一级归首页、二级归报表」—— 那是**靠精度分边界** |
| **首页看量、报表看结构** | §六 总原则 | 两页都在碰分类，用户永远记不清该去哪页 |
| **累计压成一行** | §6.1 ⑤ | 「一个信息 = 一张卡片」的惯性 |

**第 1 条值得单独说**，因为它和 §一 那个错误是同一个思维惯性的第二次现形。
第一版错在「**把一页只有一个时间窗口当成前提**」；
第二版错在「**把同一类信息切两半当成分工**」——
把「分类」按一级 / 二级劈给两页，表面上是分工，实际上是**两页都变成了半成品**：
首页有分类但看不到二级，报表有二级但没有总量对不上。
真正能成立的分工得是**按问题分**（量 vs 结构），不是按数据分。

### 〇.2 第三次修正：报表按档位组织、移动端只留一页

第三次看预览页，用户又提了两条，这次推翻了**报表页的组织方式**和**整站的导航结构**：

> 当然是按档位显示，月只看月的，年只看年的，无关的不多显示。
> 另外针对移动端界面进行优化，移动端仅保留一页，即流水页。具体调整如下：
> 流水页顶部展示提醒框；将首页、报表、设置入口统一收纳到搜索框下方；
> 其中首页重命名为「概况」，原因是这些页面在移动端不属于高频使用场景；
> 移除页面下方的 tab 栏，改为通过下拉手势直接唤出记账页面。

落点：

| 意见 | 落点 | 它推翻了什么 |
|---|---|---|
| **报表按档位显示不同块** | §6.3 档位矩阵 | 「三档只值一个大数字」—— 档位其实是**页面的组织方式** |
| **移动端只留一页（流水）** | §6.6 | 「四页平权 + 底栏四格」 |
| **首页 → 概况** | §6.6 二 | 「首页」是**位置词**；移动端落地页换成流水之后，它就不再是首页了 |

**第 1 条为什么值得单独说**：这一版之前的三档 tab，只换了 hero 的大数字与三个子指标 ——
也就是说，**档位在那一版里只值一个数字**。现在把它升格成**页面的组织方式**：
换档 = 换掉一整组块。这才配得上 §2.3 从参考项目学来的那条
（`月 / 年 / 全部` 三档是**最外层**的结构），也顺手解掉了「报表页 7 块、
手机上约 6 屏」那个待决问题 —— **长不是靠折叠解决的，是靠不给无关的块上屏**。

**第 2 条是一次真正的结构变化，不是版式微调**：它把「四页平权 + 底栏四格」
换成「**一页为主，三页降为入口**」。理由用户自己说了 ——
那几个页面**在移动端不属于高频使用场景**。而底栏的作用恰恰是
「把高频入口放在拇指够得到的地方」；低频页占着底栏格子，
就是在用高频位置的租金养低频入口。

**术语变更**：从这一版起，那个页面叫**「概况」**，不再叫「首页」。
本文档 §一 ~ §四 是诊断与外部调研，里面的「首页」有的是指参考项目的首页、
有的指我们这一页的历史状态，**保留原样不改**；§五 之后（前瞻部分）一律用「概况」。

### 〇.3 第四次修正：移动端顶卡的形态、首屏的行数、PC 端的空白

第四次看预览页，用户提了三条，前两条是移动端，第三条是**全站性的版式问题**：

> 移动端本月支出应与处理提醒同行展示，当存在处理提醒时采用两列布局，
> 无处理提醒时本月支出独占整列；处理提醒需支持折叠，默认收起，
> 点击后可向下展开查看处理内容明细。
> 同时，将月份选择与搜索框合并为同一列，或与三个入口合并为一列，
> 以减少用户向下滚动查找的负担。
> 此外，在部分 PC 端页面中，为避免卡片对齐而塞入无法填满固定项目（例如危险区），
> 导致出现大量空白，请一并排查并修正此类空白问题。

落点：

| 意见 | 落点 | 它推翻 / 补上了什么 |
|---|---|---|
| **本月支出与处理提醒同行** | §五 第 11 条、§6.6 三 | 上一版把提醒压成**通栏一条 chip** —— 它换来的是「不占格」，代价是**本月支出不在这一页** |
| **提醒可折叠、默认收起** | §6.6 三 | 「一行摘要」的形态被否定：摘要是每天都看的，细节才是偶尔看的，**默认展开是拿高频的成本去赔低频的内容** |
| **月份选择 + 搜索框合并** | §6.6 二·补 | 首屏之上**从 3 行压到 2 行** |
| **PC 端「为对齐而撑高」的空白** | §五 第 12 条、§6.7 | 这条不是审美意见，是**一个 CSS 默认值**（`align-items: stretch`）没被覆盖 |

**第 1 条值得单独说**，因为它修正了上一版一个不太明显的错误：
上一版把「提醒」从 hero 的网格块**压成一条 chip**，理由是「待办清空是常态，空块会留洞」。
这个理由成立，但结论走过头了 —— 压成一条之后，**那个位置就只剩提醒了**，
而移动端这一页又恰恰**没有本月支出**（它在概况那页，属于二级页）。
于是用户打开 App 看到的第一屏是：一条提醒 + 一堆流水，**「这个月花了多少」要进二级页才有**。
现在两列并排，一行同时回答「花了多少」和「还有什么要动手」——
这两个问题本来就是同一句话的两半，分居两屏是没道理的。

**第 2 条是一个通用原则的又一次应用**：**结论默认可见，细节默认收起**。
「3 期待处理」是结论，每天都看；「哪 3 期、各多少、几号还」是细节，一周看一次。
默认展开就是用每天都看的东西的成本，去赔一周才看一次的细节。

**第 3 条是这三条里最值得记的**：用户描述的是症状
（「为避免卡片对齐而塞入无法填满固定项目」），根因却是 CSS 里
grid 的 `align-items` **默认值就是 `stretch`**。也就是说，
**只要没人显式覆盖它，任何一行里的矮卡片都会被拉高**
—— 项目里没有一个人「决定」要这么做。修法因此也不该是逐页调样式，
而是**在 `.grid` 这个基类上把它关掉一次**，见 §6.7。

### 〇.4 第五次修正：控制行的拆法、提醒要能动手、二级页的关闭

第五次看预览页，三条：

> 1、月份还是和三个入口一行吧，搜索条独占一行没问题，三个入口一行孤零零的很奇怪。
> 2、处理提醒展开以后需要处理按钮，自动入账的显示确认，表示用户知道了，不要提醒了。
> 非自定入账的显示入账和跳过。否则提醒毫无意义。
> 3、二级表头，你说的对，但是不建议独占一行。改为 × 设置 或者 设置 ×。
> 这里的 x 表示关闭这个页面，一种放在标题前，一种放在行尾，个人觉得行尾可能好一点。

落点：

| 意见 | 落点 | 它修正了什么 |
|---|---|---|
| **月份与三个入口同一行** | §五 第 13 条、§6.6 二·补 | 上一版是我判的「期间 + 搜索同行、入口单独一行」。**判据只用了语义，漏了视觉重量** |
| **展开后要有动作按钮** | §五 第 14 条、§6.5 三 | 补上三层里最要紧的一层：**行动层原先只有「显示」，没有「动作」** |
| **二级页关闭收进标题行** | §五 第 15 条、§6.6 六 | 上一版的 `‹ 流水` 单独占一行，等于在页面之上又压了一条工具条 |

**第 1 条，我原来的判据是半对的。** 我说「期间 + 搜索都是限定列表的条件，
入口是去别处，混在一行会让用户以为『概况』也是一种筛选」——
这条仍然成立，但它**只算了语义，没算视觉重量**：三个 12px 的链接单独占一行时，
行高由它们决定、横向却空着大半，看起来像一行被遗弃的东西。
而期间选择器本身也是个固定宽度的小控件，两者同行的**视觉重量是匹配的**。
语义问题改用**位置**解决 —— 控制靠左、跳转靠右，中间那段留白本身就是分隔符。
真正该独占一行的反而是**搜索框**：它是这一条里唯一需要撑开的控件。
（顺带说明：这一条推翻了我上一版自己下的「二选一」结论。）

**第 2 条是这一轮最实质的一条。**「否则提醒毫无意义」这句点到了要害：
**没有动作的提醒只是通知** —— 通知的责任是「让人知道」，提醒的责任是「让人做完」。
展开之后只有明细、没有按钮，用户看完还得自己跑去计划页找那一期，提醒就降级成了一条横幅。

动作按「**这一期现在还会不会自动入账**」分两种（判据不是计划那一级的 `auto_post`，见 §6.5 三）：

- **会**自动入账 → 只给一个「**知道了**」（纯知悉，不改业务状态）
- **不会**自动入账 → 给「**入账 / 跳过**」（这两个是现成的 `confirmTodo` / `skipTodo`）

其中「知道了」需要一个**新状态**（建议 `plan_todos.ack_at`）：**「跳过」不能被复用** ——
它会把这一期置成 `skipped`，而 `settleAutoPost` 只挑 `status = 'pending'` 的期次，
于是「跳过」用在自动入账的期次上等于**偷偷把自动入账关掉**（用户以为只是「别提醒我」，
结果账单不再入账，且不报错）。**这是这一轮唯一需要动服务端的地方。**

> 关于按钮文案：用户原话是「确认」，我改成**「知道了」** ——
> 因为 `confirmTodo` 的语义是*确认入账（生成一笔支出）*，同一个词既表示「我看到了」
> 又表示「记账」，用户会以为点了就记账。「确认」这层意思应该留给「入账」那个按钮。列进待决。
>
> 注意：**已被否决，见 §〇.5**：用户拍板**用「确认」**（不是「知道了」），
> 并把另一个按钮从「跳过」改叫**「忽略」**。否决成立的原因是
> **两类按钮互斥出现** —— 有「确认」的那一条旁边永远没有「入账」，
> 所以「确认」不会被读成「确认入账」。**这是文案能省掉一个词的前提。**

**第 3 条顺带解决了一个我没意识到的浪费**：上一版的 `‹ 流水` 自己占一行，
而**标题行本来就要有** —— 把关闭并进去等于**白得一行**。用户给了两种摆法并倾向行尾，
我同意，理由写在 §6.6 六（`×` 在行尾与「关闭在右上」的通用预期一致，
且它与标题之间隔着整行宽度，误触率最低）。

#### 改判据的两条，值得单独记

**内容 4 —— 分组层级跟着档位走，不是「一律按天」。**

原方案是「按天分组 + 组头小计」一条规则打三档。用户明确：

| 期间 | 组头 | 默认 |
|---|---|---|
| **月** | **没有组头** | 全部显示 |
| **年** | **一级 = 月** | **默认折叠** |
| **全部** | **一级 = 年 → 二级 = 月** | **默认折叠** |

这比原方案更对：**「按天分组」在一个月里会长出 28~31 个组头**，
而月档下期间是已知的 —— 组头在重复期间选择器已经说过的话。
组头的职责是**补出列表本身没有的层级**（月档没有层级可补）。
连带的好处：**行内日期永远只写「日」**（`28日`），
月份由组头或期间给 —— 这正好解掉原方案「日期提到组头才腾得出宽度给账期」的前提，
宽度问题不存在了（见 §6.2）。

**内容 5 —— 紧急度用「一个标记 + 一句话」，不用整片背景。**

原来我把紧急度做成**三档卡色**（临近琥珀 / 逾期红）。用户否掉：

> 提醒卡片无色，加入一个颜色标记，自动入账的没有，需要手动确认的黄色，逾期的红色。
> 展开后的提醒内容也通过文字来提醒用户紧急程度，而不是做卡片背景的全部渲染。

改后规则（§6.5 六）：

- **容器永远中性色** —— 提醒条 / 顶卡那一格**不染色**
- **一条明细前挂一个颜色标记**（小圆点）：**自动入账 = 无标记 / 需手动确认 = 黄 / 逾期 = 红**（红优先）

用户：*「点击日历的年份或月份可以查看该月的相关信息……下方加入进入按钮或者再次点击

|---|---|
| **第一次点某格** | 选中该格，**下方那张卡切到这个期间**（花多少 / 几笔 / 分布）。**不换页、不滚动、不出现返回栈** |
| **再点同一格**，或点卡上的 **「进入 … →」** | 才真正下钻：全部档点年 → 年档；年档点月 → 月档＝**正常流水** |

**为什么值得分两步**：一格上只有一个数，看不出「这个月花在哪」。一步就跳走的话，
用户得跳过去、发现「不是这个月」、再跳回来 —— 两步把「看看」和「进去」拆开，
**翻月份的成本从两次跳转降到点一下**。

这一步顺带把第六次那个悬着的说法答清楚了 ——「每个日历页下方要有相对应的统计卡片」：
**下方那张卡就是统计卡**。未选中时它显示本档（年 / 全部）的统计，选中后整组切到那一格。
所以「点一下看该月信息」和「日历下方挂统计卡」**是同一件事的两种说法** ——
日历在这儿的作用就是**一个期间选择器，它驱动下面同一组卡**。

#### 第三条：流水行「一行一项」

> 流水目前的布局预览的静态页面存在多行一项的问题，改为一行一项，不要换行。

原来 `.trow__mid` 是块级，主名与副信息**上下叠着**，一笔要两行才对得齐。
改成同行 flex：主名 `flex: 0 0 auto; max-width: 62%`、副信息 `flex: 1 1 auto`，
**装不下时副信息先截断**（名字是识别项、优先级更高），行高不变、不换行、不撑高。

**这条不只是好看**：行高固定之后，**一屏能装的行数是确定的** ——
这是 M9（一次加载多少）能算得出来的前提。

> **两条的共同点**：都是**「把已经说过的话再说一遍」之外的另一种浪费**。
> 组头重复期间、第二行重复主名 —— 用户两次指的都是同一类问题：
> **同一条信息不该占两份空间。**

前几次我们都在争「哪些档位该有组头」；这一句把问题换了个问法 ——

留着它的代价不是多几行 CSS，是**下一个人会以为它可以被打开**。

> **一条可复用的判断**：**「暂时不用」和「不该存在」是两种删法。**
> 前者留口子 + 注释（第七次对 `.daygroup` 就是这么做的），后者**连注释一起删**。

#### 第 2 条：标记从行首挪到箭头，省的是什么

| | 第六 / 七次 | 第八次 |
|---|---|---|
| 染色位置 | 每条明细行首的 8px 圆点 | **展开箭头本身** |
| 收起态看到 | 只有「3 期待处理」一个数 | 那个数 + **一个染色的箭头** |
| 展开态看到 | 三个圆点 | 三行**文字颜色**（琥珀 / 红 / 灰） |

省下来的不只是几个圆点 —— **收起态和展开态现在各自只答一个层次的问题**：

- **收起态**：`要不要我动手？` → 一个箭头，一眼就有答案；
- **展开态**：`具体哪条、多急？` → 每条的文字颜色，逐条读。

前几版把「逐条的紧急度」提到了收起态（三个圆点就是三个颜色），
等于**用展开之后才看得懂的东西，去打扰还没展开的人**。
用户说「条目展开后无需再额外标记，因为文字颜色已具备区分效果」——
**把标记移到箭头上、同时删掉展开态的标记，这两步是一件事的两半。**

#### 第 3 条：被删的那行为什么属于「设置-计划」

删的是 `9月28日 提醒 · 9月30日 还款 · 自动入账`。用户这句话本身就把归属讲清楚了：

| 这行里的东西 | 该在哪 |
|---|---|
| `提醒日` / `还款日` 两个日期 | **设置 → 计划**（那是配置它们、也是唯一能改它们的地方） |
| `自动入账` 这个状态 | **留在提醒行里** —— 它决定「要不要你点」，是**此刻**的信息 |

所以不是「删掉信息」，是**把静态配置从动态提醒里分出去**。
主界面只留「此刻要我做什么」，配置留在能改它的地方。

> **一个字段该不该出现在主界面，唯一站得住的理由是「它此刻影响我要不要动手」。**

#### 第 4 条：一行放得下的前提是「信息精简」，不是「字变小」

目标格式：`¥2,800　第 3 期 · 房贷　明天到期　自动入账`。

一行里有四类信息，**顺序就是优先级**：金额 → 哪一期 → 多急 → 要不要我动手，
按钮接着放最右。380 宽里这一行约 290px，是挤的，所以配两条纪律：

- **只说「是什么」，不说「为什么」**：不写「撤销过，不自动入账」，写「需手动入账」；
- **牺牲顺序写死**：状态词可以截断，**按钮永远不许截断**，金额与名称次之。

> **「能单行收纳则不换行」是一条有次序的规则，次序本身必须写下来。**
> 只写「不换行」，实现的人会按自己的判断决定谁先被挤掉。

> **第九次修正改了这条的上半句。** 目标格式最终落在
> `¥2,800　3期 · 房贷　明天到期　自动入账　[确认]`（约 269px），
> 而**牺牲顺序被整个翻过来**：可截断的从「状态词」改成**计划名**。
> 原因见 §〇.8 第 2 处。
>
> **但上面那句判断仍然成立、而且更重要了**：**次序本身必须写下来**。
> 第九次出问题，正是因为第八次虽然写下了次序，**却没有把它写进 CSS**——
> 文档说「状态词可截断」，代码里那格写着 `min-width:0`，
> 而**真正该缩的那格什么也没写**。**只写在文档里的纪律，等于没有纪律。**

#### 第 5 条：全局禁 emoji 的实际范围

| 原来的 | 改成 |
|---|---|
| 分类图标（4 个原本用在餐饮 / 居住 / 交通 / 购物上的 emoji） | **分类首字**（食 / 住 / 行 / 购） |
| 状态标记 `注意：` | **文字**（有 / 无 / 注意 / 直接删） |
| 底栏图标（原本的 4 个线性图标） | **只留文字**（图标后续用 SVG，不用符号） |
| 提醒条开头那个带表盘的钟 | 删（那一条本来就在说「提醒」） |

**保留的是排版符号，不是表情**：`→`（`年 → 月` 这种路径）、`▾`（展开箭头）、
`①②③`（章节编号）。这三类没有表情语义、也不上色。

> **判断标准写下来，免得下一个人再来问**：
> **彩色、或带表情语义的 → 删；纯几何、只承担排版功能的 → 留。**
> 按这条：分类图标那几个删（彩色），对勾也删（虽不彩色，但它是「对勾」这种装饰语义）；
> `▾` 留 —— 它是这个界面里**唯一表达「能展开」的符号**，没有替代品。

#### 第 6 条：日历的深浅

完整判据表在 §6.3.3 末尾那一节。一句话版本：
**「平均数上下＝普通」这句话本身就要求「普通」这一档跨在均值两侧** ——
所以基准只能是**均值**，不能在最大最小之间等分。

### 〇.8 第九次修正：一条明细必须**真的**是一行

用户给了一张真机截图（提醒条 + 流水行），标了两处：**「显示不完全，文字精简」**、**「多行」**，
并给了判据：

> 如果文字确实必要无法精简，重新设计布局，起码保证视觉上应该是一行。

#### 先说结论：这次修的不是文案

两处症状看起来都像「字太多」。但把 DOM 和样式摊开看，**两处的主因都不是文案长度**：

| 处 | 症状 | 真正的原因 |
|---|---|---|
| **流水行** | `¥62` 掉到第二行，「28日」折成「28 / 日」 | **那条网格规则从来没生效过** —— 优先级 bug |
| **提醒行** | 「自动入账」被按钮压住、文字显示不完全 | **那一格少了「允许被压缩」的声明** —— flex 的 `min-width:auto` 默认值 |

文案只是最后压上去的那根稻草。

**所以这次的动作顺序是「先修结构、再减字」，不是「先减字」。**
如果反过来，下次数据一变长，同样的毛病会原样回来 —— 而且看起来又像「文案问题」。

#### 第 1 处：`写了规则` 和 `规则生效` 是两件事

窄屏流水行的网格是这样的：

```css
.trow--dated { grid-template-columns: 30px 26px minmax(0,1fr) auto; }   /* ← 写在前面 */
...
.trow        { grid-template-columns: 26px minmax(0,1fr) auto; }       /* ← 写在后面 */
```

两个选择器**特异性完全相同**（都是 0,1,0）→ 按 CSS 层叠规则，**源码顺序在后的赢**。
于是 `.trow` 把 `.trow--dated` 整条覆盖掉：模板只剩 3 列，而这一行有 4 个格子。

后果是精确可推的，和截图完全对得上：

- 第 4 个格子（金额）**没有列可放** → 自动换到第 2 行第 1 列 → 在左边缘显示 `¥62`
- 日期列从 30px 掉回 26px → 装不下「28日」→ 在「8」和「日」之间断行 → 竖着排

**修法两条，都很小但性质不同：**

1. 选择器提成 `.trow.trow--dated`（0,2,0）—— 让**特异性**决定胜负。
   这不是绕开问题：`.trow--dated` 的语义就是「`.trow` 的一个变体」，
   变体压过基类本来就该由特异性表达，而不是由「谁恰好写在后头」表达。
2. 日期列由固定 `30px` 换成 `max-content` + `white-space: nowrap` ——
   让它**随字号自适应且永不折行**。固定像素在这里是错的选择：
   日期列的内容宽度由字号决定，不该写死。

> **可复用的一条**：
> **同一个元素的多个类规则分散写在两处时，「顺序」就是一个隐形的优先级。**
> 它不出现在任何一条规则里，只出现在文件的行号里 —— 于是下一次有人挪动代码块，
> 界面就悄悄坏掉，而且坏得没有任何报错。
> **覆盖要么靠特异性、要么就近书写；绝不能靠「我记得它在后面」。**

#### 第 2 处：`min-width:auto` 会偷偷禁止收缩

提醒行的五个格子是 flex 项。flex 项的 `min-width` 默认值是 **`auto`**，
意思是**「不小于自己内容的宽度」** —— 也就是说，**它默认是缩不动的**。
而这一行里，唯一「愿意被牺牲」的那格恰好就是那个没写 `min-width:0` 的：

| 格子 | 原样 | 结果 |
|---|---|---|
| 金额 `¥2,800` | 没声明 → `min-width:auto` | 缩不动（本来也不该缩） |
| **计划名** `第 3 期 · 房贷` | 没声明 → `min-width:auto` | **缩不动 —— 但它才该缩** |
| 紧急度 `明天到期` | 没声明 | 缩不动 |
| 状态 `自动入账` | 有 `min-width:0` | **唯一的可缩项** → 被截断 |
| 按钮 | `flex:0 0 auto` | 不缩 |

于是：**该缩的缩不动，不该缩的被截断。** 整行撑破卡片，按钮只好压到状态词上。

**修法是把宽度纪律写进代码，而不是继续抠文案**：

```css
.topcard__item-amt   { flex: 0 0 auto; }                    /* 永不截断 */
.topcard__item-plan  { flex: 0 1 auto; min-width: 0; ... }  /* 唯一可牺牲 */
.topcard__item-why   { flex: 0 0 auto; }                    /* 永不截断 */
.topcard__item-state { flex: 0 0 auto; }                    /* 永不截断 */
```

这条纪律同时把**优先级**说清楚了：

> **宁可看不清是哪一期，也不能看不清多少钱、多急、按哪个键。**

而且数学上是闭合的：最坏情况（计划名缩到 0）仍然短于最窄的 320px 机型，
**不可能再溢出**。这比「但愿文案够短」可靠得多。

**顺带纠正第八次的一个判断**：上一轮把「状态词」定成**最先被牺牲**的一格。
这次改掉了 —— 截断一个 4 字词，读者看到的是「自…」，**比不显示更糟**。
可牺牲的必须换成**计划名**。

#### 然后才是减字

结构修对之后，文案才轮到被挤（省下的宽度全留给必须留下的词）：

| 原 | 现 | 为什么可以 |
|---|---|---|
| `第 3 期 · 房贷` | `3期 · 房贷` | 旁边就是金额，不会读成别的 |
| `逾期 29 天` | `逾期29天` | 数字与单位之间不需要空格 |
| `10月2日 到期` | `10月2日到期` | 同上 |
| `需手动入账` | `需手动` | 右边的按钮就写着「入账」，**两个槽拼起来正好是一句话** |
| `自动入账` | **不动** | 见下 |

**`自动入账` 是这一行里唯一不能删的**：它回答的是「**我不点会怎样**」。
金额、期次、紧急度都能从别处推出来，只有这一条推不出来 ——
删了它，用户就会在「我没确认过」和「怎么多了一笔」之间懵住（这是 §6.5 三·补 原本就写下的判据）。

#### 流水行：账期在窄屏让位

窄屏一行放不下「名称 + 支付方式 + 账期 + 金额」四样，**先减信息、再谈挤**：

| 字段 | 窄屏 | 判据 |
|---|---|---|
| 支付方式 `招行信用卡` | **留** | 它回答「这笔钱从哪张卡出」，是**识别这一笔**的一部分 |
| 账期 `账期 16 天` | **让位** | 它回答「这笔什么时候出账」，是**对账**细节；报表与对账页有完整呈现 |

**桌面两者都在。** 同一个组件、两种宽度、两种写法 —— 不是两套组件。
实现上用容器查询（`@container (max-width: 460px)`），不是复制一份窄屏标记。

#### 第 1 条：图例删掉，因为那个数已经在上面说过了

那条图例是：

```
越深＝花得越多（月均 ¥8,033）      最少 ● 普通 ● 稍多 ● 最多 ● 空月
```

它的**载荷只有一个数**（月均 ¥8,033），而这个数就在图例正上方那张卡的汇总行里：

```
2026 年    共 312 笔 · ¥96,400    月均 ¥8,033
```

所以它一个字都不是新信息。用户的话是「这种说明不要」——
而**判断依据不是「它是不是说明」，是「同一个数有没有已经在页面上出现过」**。

> **同一个数在一个页面里出现两次，不是强调，是让人怀疑「这两处是不是同一个数」。**
> 汇总行与图例挨着放，读者第一反应就是去比对它们 —— 而比对的结果永远是「一样」，
> 那一次比对纯属浪费。

那四档深浅呢？**图例本来也不是为了解释深浅**：
「最深＝最多、最浅＝最少」在四格并排时是**看图就懂**的（深浅是连续的、方向唯一的量），
需要解释的只有**轴在哪**，而轴就是那行汇总里的月均。轴搬到汇总行之后，
图例剩下的部分就空了。

**保留的那一行格式**（用户给的）：

```
2026 年        共 312 笔 · ¥96,400    月均 ¥8,033      ← 年档
9月 · 2026     共 38 笔 · ¥13,860      日均 ¥364.7      ← 月档选中
```

顺序固定为「**笔数 → 金额 → 一个派生指标**」。派生指标随档位换
（月档日均 / 年档月均 / 全部档总笔数与首笔日期），但它永远在最后，
且前面始终是「共 N 笔 · 金额」这一对 —— **同一个形状换一个词**，不是换一种写法。

#### 第 2 条：「说明式文字」的判据

> 所有页面里这种说明式的文字全部拿掉。

**判据一句话：这句话有没有改变「你要做什么」。**

| | 留 | 删 |
|---|---|---|
| 是什么 | 字段标签、空态指引、错误提示、**约束**、**后果** | 机制解释、设计理由、口径说明、**位置指引** |
| 为什么 | 它让用户知道下一步按哪、或者别按错 | 它让用户理解这个设计有多合理 —— 而用户不负责评审这个 |

逐条落到具体文案：

| 原文 | 处置 | 为什么 |
|---|---|---|
| `越深＝花得越多（月均 ¥8,033）` + 五格图例 | **删** | 那个数已经在汇总行 |
| `只记录「哪天实际付的」。这笔账仍算在 X 所属的月份 —— 补点确认不该挪动已经过去的报表。` | **删** | 解释数据模型；字段标签已经写着「实际付款日」 |
| `之后可以在计划详情里恢复` | **删** | 位置指引。菜单项「跳过这一期」已经说清了动作 |
| `一级分类不能移动。二级分类可以在不同一级之间平移，那才是「挂错了组」的常见情形。` | 留前半句、删后半句 | **约束**要留（不说用户会去找那个按钮）；**理由**要删 |
| `只改分组。历史记录的归属与报表的分组口径会跟着变，记录本身不动。` | 留后果、删过程 | 「归属会跟着变」是后果，用户据此决定按不按 |
| `这个月还没有记录。点下方「记一笔」开始。` | 删后半句 | 空态指引本身要留；但「下方」**在桌面上是错的**（按钮在右上），错的位置指引比不指引更糟 |

> **边界**：预览页里给评审看的 `annot` / `callout--key` / `mock__cap`
> **不在这条规则的管辖内** —— 它们是**文档的批注层**（解释「为什么这么设计」），
> 不是产品界面。把它们一起删掉，等于把这份评审材料变成一份没有论证的截图集。
> 这一条管的是**产品界面里的字**。

#### 第 3 条：文字显示不全的根因是「按钮太多」

第九次把两个结构 bug 修掉了，这一行的文字**仍然挤**。用户直接指出了根因：

> 文字显示不全的问题来自于按钮太多。

算一下就知道他是对的：那一行里两个按钮（「入账」「忽略」）
`px-3 + 2 个字 + gap` ≈ **110px**，占掉 390 宽手机可用宽度（约 358px）的**三成**。
而文案能再挤出的量是 `第 3 期` → `3期` 这种，一次 **10–20px**。
**方向反了：这一行的宽度不该由动作按钮来定。**

手势把动作从**排版**里搬走，信息拿回全部宽度 —— 于是文案反而可以**写回完整**：

```
¥2,800   3期 · 房贷   明天到期   需手动入账          ← 窄屏（无按钮）
¥2,800   3期 · 房贷   明天到期   需手动入账  [入账][忽略]   ← 桌面（有按钮）
```

同一个组件、同一份标记，只有动作那一格在两种宽度下换形态。

**三类动作的判据与第九次同一条**（`willAutoPost`，不是「计划开没开自动入账」）：

| 这一期现在会不会自动入账 | 动作 |
|---|---|
| **会**（计划开了自动入账 且 本期没被摘出） | 左滑 / 点「确认」→ **`ack`**：只记「我知道了」，**不改任何业务状态** |
| **不会** | 左滑 / 点「入账」→ 生成那笔支出；右滑 / 点「忽略」→ 这一期不记 |

##### 手势的五条实现纪律

1. **阈值 72px，且越过阈值时换词**（`忽略` → `松手忽略`、`入账` → `松手入账`）。
   手势最容易出的问题是「不知道松手会发生什么」，换词就把这件事变成了可见的。
   72px 是取舍：太短会在纵向滑动时被手指的横向漂移触发，太长要甩两下。
2. **`touch-action: pan-y`** —— 竖向滚动留给浏览器，横向才交给我们。
   再加一道方向判定：前 8px 不认方向（这一段既可能是点击也可能只是按压）；
   判定为竖向就**立刻退出**本次手势，让列表正常滚。
   浏览器真开始滚时会发 `pointercancel`，那时同样重置。
3. **鼠标不走手势**：桌面本来就有按钮，而鼠标拖拽会与文本选区打架。
4. **窄屏的动作按钮不退无障碍树。** 用 `sr-only` + `focus-within` 浮出，
   而不是 `display: none` —— 滑动是触屏 / 鼠标专属交互，键盘用户不能因此失去这三个动作。
5. **有撤销。** 手势**一次完成**，没有第二次确认的机会，所以
   「入账」与「忽略」各留一条 8 秒的「撤销」（走 `revert` / `restore`）。
   **`ack` 不给撤销** —— 它不产生任何账目，没有东西可以被撤回来；
   误点最坏的结果只是这条今天不再出现，而到还款日照旧自动入账。

> **`ack` 需要一个落点，这是本轮唯一动服务端的地方**（`A23` 的前提，`M7` 已拍板）：
> `plan_todos` 加一列 `ack_at`（迁移 `003`）+ 一个端点 `POST /api/plan-todos/:id/ack`。
> 不能放前端：换设备它又冒出来，用户会觉得「点了没用」。
> **撤销与恢复跳过时必须把它清回 `NULL`** —— 不清的话，撤销后的期次再也不会提醒，
> 用户看到的是「撤销按钮没反应」（同 migration 002 那个坑的同一个形状）。

#### 第 1 步：`A22` 的写法被我改了 —— 这是本轮唯一一处推翻既有方案

方案里写的是「`.grid` 一律 `align-items: start`」。**落代码时才发现不能这么写。**
这个项目的网格全是 Tailwind 工具类，而且**有三处网格本来就靠 `stretch` 撑满格子**：

期间选择器的三格、设置页窄屏的 tab 条（五个标签长度不同）。

改成全局覆盖的后果精确可推：**键盘散架、分段控件不等高** ——
而它们坏掉的样子与「卡片多了一截空白」看起来毫不相干，
不会有人想到是同一行 CSS 干的。

所以落地形态是一个**新类** `.card-grid`。**规则的主语是卡片，不是网格。**

#### 第 2 步：`#11` 的三条判断

**① 导出与备份必须摆成两件事。** 只有一个入口的话，用户会把「按月导出」
当成月度备份拿去恢复 —— **静默丢掉其他月份**，而这种错误的发现时间以「年」为单位。
所以：范围只作用于导出；备份那一栏永远全量，并且**明说**「备份始终全量」。

**② 下载不能用 `<a href>`。** 令牌在 `localStorage` 里、走 `Authorization` 头，
而 `<a>` 发出的请求不带这个头 —— 结果是浏览器乖乖下载了一个**文件名正确、
内容是 401 JSON** 的文件。用户会以为「导出成功了，只是文件坏了」，
然后拿着它去导入。必须走 `fetch` + `Blob` + 临时 object URL，
失败时也要能读出服务端那句原话（例如「`scope=year` 需要 `period=YYYY`」）。

**③ 「数据」只给管理员，且用 `v-if` 而不是 `v-show`。**
其余 tab 用 `v-show` 是为了留住各自的编辑态，而这一页要的恰好相反
（每次进来重读概览，条数才是当下的）。用 `v-show` 的话它在页面加载时
就会发一次请求，**非管理员即使看不到这个 tab 也会先吃一个 403**。

#### 顺手落下的危险区：两个按钮的代价**不对称**

「清空账目」用户自己能理解；「重置演示数据」会把**真实数据换成假数据**。
后者因此有一条前置条件：**库里必须只有演示数据**（判据见 §6.4 二）。
一个叫「重置」的按钮最容易被理解成「把我的数据整理一下」——
若它照跑，用户会丢掉全部真实账目、换来一堆假账单，而且以为自己在重置。

三个实现约束都属于「不做就会在第二次点击时炸」的那一类：

1. **凭据与种子写在同一次事务里** —— 种子成功而凭据没写，下一次重置会因为
   「清单是空的」而被自己拒绝；
2. **清空账目时要清掉凭据** —— 留着会让下一次重置拿一份**过期清单**当准入依据；
3. **演示数据的日期相对 `today` 现算** —— 原来那个写死月份的脚本是
   「开发机上跑一次」的工具，而按钮是第二年还会被按的东西。

#### 文档与代码之间的一处漂移（值得记）

设计稿上那两个按钮写的是「清空**全部**数据」。落到代码时字面上说不通：
它清的是支出 / 计划 / 待办，**不动**分类、支付方式、账号 ——
而删掉分类会让**记账当场没有分类可选**。
按钮因此改名为「清空**账目**数据」，§6.4 一里记了这次改名与理由。

> **可复用的一条**：**设计稿上的动词要落到数据模型上校一遍。**
> 「全部数据」在稿子里是个干净的词，在这个库里却必须回答
> 「`categories` 算不算数据」——而它不算，因为它是配置。

## 一 我第一遍读错了什么

第一版只读了 `lib/` 下的 Flutter 源码，结论是「首页以流水为主体、
分析页用视角把维度乘开」。方向不算错，但**漏掉了三样结构性的东西**，
于是得出了一个保守且错误的结论 —— 认为首页与报表的重复「要删掉一份」。

拉下 `preview/` 里的预览图实际看过之后，漏掉的是：

| 漏掉的 | 具体是什么 | 为什么它会推翻第一版 |
|---|---|---|
| **顶层三档时间维度** | Web 首页主数字右上角有 `本月 / 今年 / 汇总` 三个 tab，一个 tab 切换整页数字 | 我们**没有「汇总」这个维度**。整站只有一个「当前期间」 |
| **月度支出热力图** | `2026年月度支出热力`：12 个格子，**用颜色深浅编码金额** | 我只会想柱状图/折线图，没想到「颜色深浅」本身就是信息编码 |
| **「坚持」类指标** | `记录天数 167 天` / `记账笔数 72 笔` / `记账习惯 0.43 笔/天` | 用的是 `created_at` 维度。我们的库里有这个字段，**一次都没展示过** |

以及两条布局层面的：

| 漏掉的 | 具体是什么 |
|---|---|
| **一页里多个时间维度各司其职** | 本月（支出分类 / 日均 / 结余趋势）· 今年（支出 Top5）· 2026 年（月度热力）· 近 6 期（收支趋势）· 累计（笔数 / 天数）。**这五个时间维度同时在一页上** |
| **卡片网格 + 对比型指标带进度条** | 「本月储蓄率 **-370.9%**」带进度条、「已用 **43%**」进度条 |

**错误的根源**：我把「一个页面只能有一个时间窗口」当成了前提。
在这个前提下，「首页显示本月支出、报表也显示本月支出」必然是重复，只能删一份。
**正确做法不是删，是给每个维度一块自己的地方** —— 重复的根因不是「数字太多」，
是「同一个维度占了太多地方，而别的维度一个地方都没有」。

### 2.7 部署实例实测（v1.6.3 · Web 端）

无头 Firefox 逐页截图 + 扒 `index-*.js` 的 i18n 词条表，1626 条）。
实测的价值在于：**源码里有的功能，Web 端可能根本没做**。

**实测到的全部路由**（侧栏 5 个 + 2 个次级）：

| 路由 | 侧栏 | 内容 |
|---|---|---|
| `/app/overview` | 首页 | 一屏总览（见 §2.2 的截图核对） |
| `/app/transactions` | 交易 | 扁平列表 + 分页（20/页，共 162 页） |
| `/app/accounts` | 资产 | 净值 / 资产构成 / 账户卡（含账单日·还款日） |
| `/app/categories` | 分类 | 支出 59 / 收入 4 / 转账 1 |
| `/app/tags` | 标签 | 每行「N 笔 · 支出 · 收入」 |
| `/app/budgets` | | 预算（总预算 + 分类预算） |
| `/app/calendar` | | 月历热力 + 右侧当天详情 + `+ 新增` |

另有 ⌘K 全局搜索（含 AI 记账：文字记账 / 截图记账）。

**四条实测才发现的事**：

1. **Web 端完全没有「计划 / 待办 / 提醒」** —— 词频：提醒 0 · 计划 0 · 待办 0 ·
   到期 0 · 逾期 0 · 分期 0 · 待还 0 · 通知 0。「周期记账」也只有 3 次，
   且全是「账期周期」的意思（`ledgers.monthStartDay.hint`）。
   **所以它不是「把计划提醒放在某一页」，是压根没有这个实体。**

2. **它唯一的「提醒」形态 = hero 卡底部的一条计数 chip** ——
   词条键是 `home.insights.*`：

   ```
   home.insights.hint             = 悬停查看详情
   home.insights.anomalyChip      = 异常 {count} 个月
   home.insights.anomalyChipClean = 无异常 
   home.insights.budgetChipTotal  = 预算 {pct}
   home.insights.budgetChipCatOnly= 分类预算 {count} 个
   ```

   实测悬停展开（`home.anomaly.*`）：popover **向上弹出**，内容是
   `9月 2万 · 比月均 9,252 高 116%` + 归因 chip `手机数码 10,999（本月独有）`。
   → **提醒 = 计数 + 悬停展开 + 归因到具体分类**，三层。它不是「有 N 件事」，
   是「**因为什么**」。
   这是本轮从实测里拿到的**最有价值的一条**，见 §2.8 第 11 条。

3. **它的「还款」不是实体，是账户的两个属性** ——
   `accounts.field.billingDay` / `accounts.field.paymentDueDay`（账单日 / 还款日），
   在**资产页的账户详情**里显示成：

   ```
   detail.account.billingDay    = 账单日
   detail.account.paymentDueDay = 还款日
   detail.account.dayOfMonth    = 每月 {day} 号
   detail.account.daysUntil     = 还有 {days} 天
   ```

   → 所以它不需要想「计划提醒放哪里」：**账户一直在那儿，还款日只是它的一个字段**。
   而我们比它多出的能力恰恰是 —— **金额确定、期数确定**（见 §2.8 第 12 条）。

4. **它的交易页是扁平列表 + 分页，不是按天分组** ——
   `关键词搜索` + `筛选` + `导出 CSV` + `新建交易`，列表行内
   `图标 · 分类/备注` / `日期 时间 · 支付方式` / 金额，悬停才出现编辑·删除。
   **这与我在 §6.2 推荐的「按天分组 + 组头小计」相反。** 见 §6.2 的修正
   （**后来那条「按天分组」也被用户推翻了，改成按档位分层，见 §〇.5 / §6.2**）。

**另外三条会改到我们方案的**：

5. **它没有报表页。** 全部分析都在首页的「扩展分析」区（折叠标题），
   或走 ⌘K。我们的报表页是**额外的东西** —— 它必须回答首页答不了的问题，
   否则没有存在理由。

   > **补（这一轮修正后这个问题有答案了）**：首页被定为「**只看量、横跨月年总**」
   > 之后，报表页的存在理由变得明确 —— **首页给不了「构成」，也给不了「精度」**。
   > 而且这个理由不依赖「首页放不下」，是**结构性**的：只要首页还只看量，
   > 报表就有它独占的活。见 §五 第 3 条、§6.3。

6. **设置不是页面，是顶栏的一个图标 → 弹窗。** 顶栏右侧是图标组：
   `搜索 ⌘K` · `导入导出` · `设置(齿轮)` · `帮助(?)` · `头像`。
   没有「通知铃」—— 再次印证它没有提醒中心。

7. **日历页可达但不在侧栏**（二级入口）。我们的占位要跟这一条对齐：
   日历是「想查那天」时去的，不是每天点的。

### 2.8 学什么 / 不学什么

**学**：

1. **一页里多个时间维度各司其职** —— 这是「有效信息」的唯一机制
2. **顶层三档（本月 / 今年 / 汇总）**，其中「汇总」是我们完全没有的维度
3. **用颜色深浅编码金额**（月度热力图）
4. **「坚持」类指标**（记录天数 / 记账习惯 笔/天）—— 用的是我们已有但从未展示的字段
5. **Top 5 排行**，且是「今年」口径 —— 跳出当期看长期
6. **对比型指标带进度条**（不是只给一个数，给「到了哪」）
7. **未来月份显示 `—` 而不是 0** —— 与「当前周期只画到今天」同一类严谨
8. **折线图逐点标数值**（不用悬浮就能读）
9. **排行榜每行都带金额**，且**可下钻**
10. **口径要说出来**（它用「折算脚注」说明数字怎么算的）
11. **「提醒」做成「计数条 + 悬停展开 + 归因」，不是一个区块** ——
    `注意：异常 2 个月` 是一条 chip，悬停才展开到
    `9月 · 比月均高 116% · 手机数码 10,999（本月独有）`。
    这条同时解决三件事：**不占格**（总览的形状不被破坏）·
    **空态不空洞**（0 条时它显示「无异常 」，而不是留一个空格子）·
    **可增可减**（加一类提醒就是加一条 chip，不用重排页面）。
    详见 §6.5。
12. **归因（attribution）比数量更有用** —— 它不说「9月花了 2 万」，
    而是说「**手机数码这一项本月独有，占 1 万**（超月均 3.2×）」。
    句式是 `{分类} {金额}（{为什么}）`，三种「为什么」：
    `本月独有` / `超月均 N×` / `与月均持平`。
    我们做「涨跌榜」和「洞察句子」时直接照这个句式（见 §6.3）。

**不学**：

1. **多账本 / 资产账户 / 标签 / 币种 / 附件** —— 会把项目推向「通用记账」，
   代价是**每一页都要重新设计一次**
2. **20 套头部皮肤 / 主题商店 / 捐赠 / Star / 评分引导** —— 社区运营需要
3. **AI 记账 / OCR / 语音 / MCP** —— 不是这一轮的问题
4. **分类管理拆四张页面** —— 手机端 native 导航的习惯，Web 上一页内联更快
5. **它的首页三数里有「收入 / 结余」** —— 我们已定**永远不加收入**（见 §四）

十三条特别说明：

- **第 2 条的分界依据**：参与 tab 切换的（大数字 / 子指标 / 进度）回答
  「**这个维度下有多少**」，换维度必须换答案；
  不参与切换的（热力图 / 累计）回答「**跨维度的长期事实**」——
  热力图本身就站在「最近 12 个月」上，累计本身就站在「全部时间」上，
  它们已经各有一个维度了，跟着切换会让人不知道自己在看什么。
  （原先这条把「支出分类」也列进切换组；第 3 条修正后分类整体归报表，已移出。）
- **第 2b 条为什么取「最近 12 个月」而不是「本年度 1–12 月」**：
  参考项目用的是日历年，1 月份时只有第 1 格有数据、其余 11 格全空，信息量骤降。
  滚动 12 个月永远 12 格有数，且永远与当下相关（代价：跨年时格子要带年份）。
- **第 4 条推翻了我自己第一版的提议**（原本写「设置页顶部放三个成就数字，
  学 BeeCount 的『我的』页」）。看清之后才知道那是**手机端的 hub 页**，
  与我们的 tab 式管理后台不是一回事；概况已有「累计」块，设置页再放一遍就是明知故犯。
- **第 3 条是对 grill 结论的修正（用户提出）**。原方案是「概况放一级分类环图 +
  今年 Top5，报表去掉一级构成、只做下钻与对照」—— 那会让**两页都在碰分类**，
  只能靠「一级 / 二级」这种**精度**去分边界，含糊且极易做错
  （概况点一级、报表点二级，用户永远记不清该去哪页）。
  改成「分类整体归报表」之后，边界变成 **量 / 结构**：

  > **概况看量、维度横跨月年总；报表看结构，精度细化到年、月、天。**

  一句话说得清，而且能用一条机械的检查验收：
  **概况的 DOM 里不该出现任何分类名**（见 §三 末尾）。
- **第 8 条的两个数字要分开说**：用户的原话是「精度细化到每年每月甚至到天」，
  但这句里「**精度**」与「**档位**」是两件事 ——
  **精度到天**靠月档的逐日折线达成（30 个点，每天都标数值），
  **不需要**因此多出一个「天档」。做成第 4 档的代价是：
  它与流水页的日期分组是同一件事的两种画法，**又造出一处重复** ——
  正是这一轮要消灭的东西。
- **第 7 条是补的，不在 grill 里** —— grill 走完时漏了「计划提醒放哪里」，
  是**实测部署实例**时才补上的（参考项目压根没有计划实体，见 §2.7 第 1、3 条）。
  它同时修正了 §6.1 原本把「要动手的事」写成**一个网格块**的做法。
- **第 9 条的判据要写清，否则会做成「藏东西」**。每个块在三档上**都算得出数**
  （「较上期」永远能算），所以如果判据是「能不能算出来」，结果是一个块都不减。
  真正的判据是「**这个档位下它还在不在回答一个新问题**」：
  「下月要还多少」在年档下算出来的东西已经退化成「全年各方式占比」，
  而那是「分类构成」已经答过的 —— 所以年档把它去掉，不是把它折叠。
  → **「无关的不显示」的边界是「答案有没有重复」，不是「屏数够不够」。**
- **第 10 条不要做成「把底栏搬到上面」**。最容易走歪的一步是把三个入口
  做成等宽 + 图标 + 选中态的一行 —— 那就是把底栏原样搬到搜索框下面，
  低频入口照样占着高频位置的租金，只是换了个方向。
  那三个入口必须用**和底栏不同的视觉语言**（次要链接，不是导航项），
  且与期间选择器同行、靠右 —— 见 §6.6 二。
- **第 11 条要看清「两种形态」不是一个形态的宽度变化**。有 / 无未处理
  不是「宽一点 / 窄一点」，是**两种布局**：两列 vs 独占整列。
  实现时必须是同一个组件带一个布尔，不能写成两个分支（那会长出两套间距）。
  另：**「无未处理时不放占位」推翻了 §6.5 三 的一条旧规则** ——
  旧规则说「0 条时显示 `没有待处理`，空态本身是信息」。那条在**桌面 hero 的提醒条**上
  仍然成立（一行 12px 灰字，成本≈0）；但在移动端它是一个**半格**，
  格子消失能直接换来本月支出从半格变整格。**同一个信息在两地的成本不同，处理就该不同。**
- **第 12 条是被用户抓出来的**。他看到的不是「留白多」，是
  **「为了避免卡片对齐而塞入无法填满的固定项目（例如危险区）」** ——
  这句话指的其实是 CSS 的默认值：grid 的 `align-items: stretch`。
  它把同一行的矮卡片一律拉到行高，**多出来的空间全落在卡片底部**。
  所以这不是审美问题，是**一个默认值没被覆盖**。修法见 §6.7。
- **第 13 条推翻了我自己上一版的判断**。上一版我把「入口单独一行」当成正确解，
  理由是语义。它错在**只算了语义、没算视觉重量**：一行三个 12px 链接，
  行高由它们决定、横向却空着大半。语义改用**位置**解决 —— 控制靠左、跳转靠右。
  一般化的说法：**一行里出现两种语义时，先想「用位置分开」，不要先想「用行分开」** ——
  后者的代价是白占一整行，而在首屏之上，一整行是很贵的东西。
- **第 14 条的判据必须落到「期」这一级，不能落在「计划」那一级**。
  同一个房贷计划：3期会自动入账，5期因为被撤销过而**不会**
  （`hold_auto_post = 1`）。只看 `plans.auto_post` 会把 5期也判成「确认」，
  用户点了以为没事，**那笔账却永远不入，而且不报错** ——
  这是这一轮里最容易做错、也最难被发现的一处。
  另：**「确认」不能复用「忽略」**，否则等于偷偷关掉自动入账，理由见 §〇.4 与 §6.5 三。
  **文案最后由用户拍了**：用「确认」（不是我建议的「知道了」），
  且「跳过」按用户的用词改叫**「忽略」** —— 三个按钮都是两字，天然等长。
- **第 15 条不要做成「左上角一个返回箭头」**。`‹` 与 `×` 的语义不同：
  `‹` 是「返回上一页」，`×` 是「关闭这个页面」—— 我们的场景是后者
  （从流水页进来，关掉就回到流水页）。而「关闭」的通用位置在右上，
  所以 `设置 ×` 比 `× 设置` 更符合预期，见 §6.6 六。
- **第 16 条推翻了第 11/14 条里我自己定的「紧急度三档卡色」**。
  原来我把紧急度做成**整片卡色**（临近琥珀、逾期整条转红）。用户否了：
  **提醒卡片无色，改挂一个颜色标记**，并且**紧急程度走文字**。
  改后颜色只回答一个问题：**这一条需不需要你动手** ——
  自动入账＝无标记、需手动确认＝黄、逾期＝红。
  这比我原来的「多急」更贴决策：用户看提醒时真正要判的不是紧迫感，是**要不要点**。
  （三档色本身没有被废掉，它降级成了**标记**的配色，见 §6.5 六。）
- **第 5 条也被改了判据**：原「一律按天分组」在**月档会长出 28~31 个组头**，
  而月档的期间是已知的 —— 组头在重复期间选择器说过的话。
  改成「**层级跟着档位走**」：月档无组头、年档按月、汇总档年→月两级。
  组头的职责是**补出列表本身没有的层级**，月档没有层级可补。
  **一条附带的收益**：行内日期因此可以永远只写「日」，`账期` 的宽度问题自动消失。
  > 注意：**第七次修正又改了一半**：月档无组头不变，但**年 / 全部两档不再用组头折叠**，
  > 改用**日历**（见 §〇.6 / §6.3.3）。「层级跟档位走」这条判据仍然对，只是年 / 全部两档
  > 的「层级」被**格子**代替了 —— 日历和折叠列表回答的是同一个问题。
- **移动端下拉手势不留兜底出口**（用户裁决，见 §〇.5）。这意味着
  **手势从「主入口」变成「唯一入口」** —— 原来我留的兜底
  （滚到列表底出现「＋ 记一笔」、空态给按钮）被明确否掉了，理由是
  「不需要额外入口」。风险因此上升：**手势失灵就没有任何记账入口**。
  所以 `A19` 的实测判据要从「手势好不好用」升级成「**手势失败率是不是 0**」，
  并且首次引导必须做到看见即会（§6.6 五）。

## 六 每页重新设置的内容

总原则：**一页里多个时间维度各司其职；同一个数字只在一处出现。**

还有一条统辖四页的二分（§五 第 3 条），它比上面那句更能指导取舍：

> **概况。** 回答「**多少**」，维度横跨 **本月 / 今年 / 汇总**，只看量。
> **报表 = 统计。** 回答「**构成是什么、跟谁比**」，精度细化到 **年 / 月 / 天**，看结构。

由此得到一条能机械验收的规则：

> **分类的统计（构成 / 排行 / 占比 / 金额）只出现在报表页。**
> 概况的 DOM 里不该出现任何分类名。流水行里那个分类名是**单笔的标签**、
> 设置页那一列是**管理视角的笔数**，两者都不是统计，所以不受这条约束。

再加一条管**块的出现**（§五 第 9 条）：

> **一个块出现在哪一档，取决于「这一档下它还在不在回答一个新问题」。**
> 换档 = 换掉一整组块，不是只换一个数字。

以及一条管**平台**的（§五 第 10 条）：

> **块是一样的块，平台只决定「从哪进来」。**
> 桌面四页平权（顶栏四个入口）；移动端只有流水页是「页」，
> 概况 / 报表 / 设置降为**入口行**。**同一份内容不做两套，只换外壳。**

这四条合起来就是这一轮的取舍判据，下面按页给内容。

### 6.1 概况（原「概况」）= 一屏总览

**布局**：卡片网格。窄屏单列，宽屏两列；hero、热力图、累计条跨两列。

| # | 区块 | 内容 | 时间维度 | 参与 tab？ |
|---|---|---|---|---|
| ① | **hero** | 当期支出大数字 + 3 个子指标 + **底部提醒条（仅桌面）** | 当期 | |
| ② | **本月要还** | 信用类 + 还款日 + 紧急度 + **已记 N 笔** | 当期事实 | |
| ③ | **进度对比卡** | `本月已过 18 天` · 日均 · **进度条**（对近 3 个月日均） | 当期 | |
| ④ | **月度支出热力** | **最近 12 个月**，12 格，单色深浅 + 格内金额 + 点格跳报表 | 滚动 12 月 | |
| ⑤ | **累计** | **通栏一行**：已记 N 天 · M 笔 · 平均 A 笔/天 · 首笔日期 | 全部时间 | |

> **① 为什么写「仅桌面」**：提醒条跟着**落地页**走（§6.6 四）。
> 桌面的落地页是概况，所以它挂在 hero 底部；移动端的落地页是流水页，
> 所以它在流水页顶部。**同一个东西只有一个落点，不是两处都放。**

**概况没有任何一个分类名。** 原先的「支出分类构成」环图与「今年 Top 5」
都挪去报表页了（§五 第 3 条）—— 概况只回答「多少」，分类构成是报表的活。

**⑤「累计」为什么不做成卡片**（用户的意见，采纳）：

它**只有一行数**。把它做成一个网格块，等于用一整格装四个数字，
而这些数字之间没有结构关系（不像分类构成有占比、不像热力图有 12 格）。
所以压成**一条通栏的细条**，左端一个小标签「累计」，右端四个数横排。

**并且它不含金额** —— 累计支出那个数在「汇总」档的 hero 上。
一行里出现同一个数字是这一轮要消灭的东西（§三 末尾）。

这一改还顺带**给概况减了负**：原先 7 格里有 2 格是分类，
去掉之后概况只剩「时间维度」一种内容 —— 一个页面只讲一件事，
连视觉语言都统一了（都是数字、格子和图，没有一个分类图标）。

> **改动记录（读完部署实例之后）**：原先这里有一格 ②「要动手的事」，
> 把「该处理了（计划待办卡）」和「本月要还」**合并成一个网格块**。
> 现在**拆开**：
>
> - **「该处理了」不再是一格** → 变成 ① hero 底部的**提醒条**（见 §6.5）
> - **「本月要还」保留为一格**（②）→ 因为它是一个**数字**（还要还多少），
>   不是一个**动作**（现在去做什么）
>
> 理由是「**状态**」与「**动作**」不该同构：网格里其余四格都是**状态**
> （已发生 / 走到哪了 / 累计），插一格「待行动」会破坏总览的形状；
> 而且**待办清空是常态**（房贷一个月只响一次）—— 空态会留一个洞。
> 这个坑我们**已经踩过一次**（`DashboardView.vue` 里那段注释：
> 「上一版是固定的 grid-cols-2……待办清空之后左栏就成了空壳」）。
> 做成一条 chip 就没有这个问题：0 条时它显示「没有待处理」，本身仍是信息。

**① hero 的三个子指标随 tab 变**（这是三档的价值所在）：

| tab | 子指标 |
|---|---|
| 本月 | 日均 · 笔数 · **预计月末** |
| 今年 | 月均 · 笔数 · **最高月** |
| 汇总 | 月均 · 总笔数 · **首笔日期** |

**「预计月末」的算法与陷阱**（写进 `utils/`，与报表共用一份）：

```
预计月末 = 已花 ÷ 已过天数 × 当月总天数
```

月初第 1 天会算出「一天的金额 × 30」，**误差可达十倍** ——
用户第一天打开看到「预计月末 ¥45,000」会以为疯了。
所以：**每当前 3 天不显示这一格**（显示 `—` 并注明「数据太少」）。
**这个「不显示」是刻意的，不是没做。**

**④ 热力图的三条细则**：

- **单色深浅，不用多色** —— 颜色深度已在编码金额，再叠一层色相，
  人会以为颜色还有第二种含义；且多色会和分类色打架
- **格内放金额缩写**（`1,915` / `8,792`），不能只有颜色 —— 只有颜色读不出量级
- **没有记录的月份显示 `—` 而不是 `0`** —— 学参考项目的做法。
  `0` 会被读成「那个月一分没花」，`—` 才是「没有记录」。**这两件事不同**
- **窄屏要改格数与写法**（做原型时用 390 宽实测出来的）：
  手机卡片内宽只有约 320px，12 格平摊每格 **22px** —— 连「10月」都放不下。
  所以窄屏改成 **6×2 两行**（每格约 49px），并把金额换成缩写（`3.8k`）。
  **装不下的时候换写法，不是硬塞。**

### 6.2 流水页 = 浏览 + 查找

概况不再放流水之后，**流水页是唯一能看到「一笔一笔」的地方**，
所以要同时承担「默认浏览（最近发生了什么）」与「精确查找（那笔在哪）」。

| # | 区块 | 内容 | 变化 |
|---|---|---|---|
| ⓪ | **提醒框（仅移动端，置顶）** | 行动层待办，见 §6.5 三 · §6.6 三 | **新增**（移动端） |
| ① | 控制行 + 搜索行 | `PeriodPicker` + **三个入口（概况 / 报表 / 设置）** + 搜索 + 筛选；**期间与入口同一行、搜索独占一行**，仅在移动端（§6.6 二 / 二·补） | 改（移动端） |
| ② | 筛选 | 分类 / 支付方式 chip + **排序（最新 / 最贵）** + **金额区间** | 补 |
| ③ | 合计 | `筛选结果 N 笔 · 合计 ¥X` | **只在有筛选时给金额**；无筛选时给「同本月总额」的指路 |
| ④ | **按期间档位的形态** | **月档**＝流水列表（无组头）；**年档**＝**12 个月格日历**；**全部档**＝**一格一年日历**。日历格只给量，统计挂在下方卡 | **新增**（第六次修正改判据、**第七次修正换形态**） |
| ⑤ | 行内 | 分类图标 · 分类名/备注 · 支付方式 · **日期（只写「日」）** · **账期** · 金额 | **改** |
| ⑥ | 空态 | 已有 | 补「清除筛选」按钮 |

**③ 的改法**：合计是同一个数字的**第 4 次出现**。
但列表语境里它确实有用（「筛出来的这些加起来多少」），所以**不删**，
改成**只在有筛选时才给数字** —— 无筛选时那个数在概况与报表都有，这里再来一遍就是纯重复。

**⑤ 的「账期」是新东西**：显示 `消费日 → 还款日` 相差几天
（如 `9月12日刷 · 28日还 · 16天`）。这是我们**独有**的三个日期字段，
一直没用过。它能回答一个很实际的问题：**免息期用了多久**。

**④ 的档位形态（第六次改判据、第七次换形态，用户定）**：

| 期间 | 形态 | 点一下 | 再点 / 按「进入」 |
|---|---|---|---|
| **月** | **流水列表，无组头** | — | — |
| **年** | **日历页：一格一月**（12 格） | 下方卡切到该月（花多少 / 几笔 / 分布） | **月 →** 月档＝正常流水 |
| **全部（汇总）** | **日历页：一格一年** | 下方卡切到该年 | **年 →** 年档 |

**「没有组头」这一条从第六次起没变过，第八次更进一步：组头设计整套移除。**
理由可数：一个月里有 28~31 天，按天分组就长出 28~31 个组头，
而**月档下期间是已知的** —— 每个组头都在重复期间选择器已经说过的话（「9月」）。
**组头的职责是补出列表本身没有的层级**，月档没有层级可补。

> **第八次修正：连「月档以内按分类分组」那个口子也一起关掉**（用户：*避免不存在组头的问题*）。
> 前几次都在争「哪些档位该有组头」，这一句换了问法：**任何档位都不需要它，
> 那它就不该以「一种可选形态」的身份留在代码里** —— 留着的代价不是几行 CSS，
> 是下一个人会以为它可以被打开。理由与判断标准见 §〇.7 第 1 条。

**连带解开了一个死结。** 原方案说「日期从行内提到组头，腾出来的宽度才放得下 `账期`」
—— 那是为了给按天分组找理由。月档无组头之后日期必须留在行内，
但**月档的月份也是已知的**，所以行内日期**只写「日」**（`28日`，两个字），
`账期` 的宽度自然就有了。**列宽问题不是靠腾空间解决的，是靠不重复已经说过的信息。**

**年 / 全部两档：第七次把「组头折叠」换成了「日历」。**
第六次定的是「年档一级＝月组头、全部档年→月两级、默认折叠」。**那条判据没错**，
只是同一个问题后来有了更省事的答法：
**折叠列表要展开才知道「哪几个月有东西」，日历不展开就看得见**（格子里的量就是深浅），
而且格子上直接能点。分组列表用三行文字说的事，日历一屏格子说完，**还多给了「点进去」**。
**日历是分组列表的升级形态，不是另一个功能。**

> **`.daygroup` 这套样式在第八次修正被整套删掉**（第七次时还留过口子，见 §〇.7 第 1 条）。
> 现在流水页**不存在任何折叠骨架**：月档就是明细，年 / 全部档是日历。

**去掉**：行内那个灰色的「9月28日 还款」药丸（`ui-review.md` D4 记过，
大量行都有、是噪音）。它的信息（紧急度）属于概况「本月要还」，不属于流水行。

> **修正（读完部署实例之后）**：参考项目的 Web 交易页是**扁平列表 + 分页**
> （关键词 + 筛选 + `导出 CSV`，20 条一页、共 162 页），**没有分组**。
> 它不是没想到分组 —— 手机端概况就是按天分组的 —— 而是**在 3,237 笔这个量级上
> 选了分页**。
>
> 这不推翻 ④，但把它**加了一个前提**：
> **「一次加载多少」还没定**（现在是「已加载 N 笔」无限往下加载，几千笔时会失效）。
> 归入 §十一 M9。
>
> 分组仍然值得做的理由是**层级与折叠是一套的**：
> 年档 / 汇总档只有先有组头，才能折叠成骨架；扁平列表给不了「哪几个月有东西」。
> **两条要一起做，只做分组不折叠会看不出收益。**
>
> **注意：这段在第七次修正后被取代了一半**：年 / 全部两档已经不走「分组 + 折叠」，
> 改走**日历** —— 因为日历把「哪几个月有东西」答得更省（见 §6.3.3）。
> **M9 也因此缩小了范围**：现在还长的那一档**只剩月档**（一屏多 ~ 几屏），
> 而年 / 全部档的格子只有十几个，量级完全不同。
> **第八次修正再补一刀**：既然三档都不需要组头，M9 里那条「按段回收」也就彻底无从谈起 ——
> 列表里已经没有「段」了。

### 6.2.一 一行一项（第七次修正）

> 流水目前的布局预览的静态页面存在多行一项的问题，改为一行一项，不要换行。

**原来的问题**：`.trow__mid` 是块级，主名（`午餐 · 公司楼下`）与副信息
（`招行信用卡 · 账期 16 天`）**上下叠着**，一笔占两行 —— 扫读时眼睛要来回跳，
年档 / 汇总档一屏只有十几行时最刺眼。

**改法**（`ui-rework-3-preview.html` 的 `.trow__mid`）：

| 元素 | 改前 | 改后 |
|---|---|---|
| `.trow__mid` | 块级（名字 / 副信息上下） | `display: flex; align-items: baseline`（同一行） |
| `.trow__name` | 块级、无宽度约束 | `flex: 0 0 auto; max-width: 62%` —— **名字是识别项，优先保住** |
| `.trow__sub` | `display: flex; flex-wrap: wrap` | `flex: 1 1 auto; min-width: 0` + `nowrap` + 省略号 |
| 副信息里的多段 | 靠 flex `gap` 分开 | 行内 `·` 分隔（`> span + span::before`） |

**装不下时副信息先截断**，行高不变、不换行、不撑高。
名字有 `max-width: 62%` 这个上限，所以极端长名也仍然会截断，不会把副信息挤没。

> **这条不只是好看**：行高固定之后，**一屏能装的行数是确定的** ——
> 这是 M9（一次加载多少）能算得出来的前提。
> 也就是说它和「分组 / 日历」是同一类改动：**先把一行占多少空间定死，才谈得上一次装多少。**

#### 6.2.一·补 第七次只定了方向，第九次才真正做到（第九次修正）

真机截图暴露：上面这套改完之后，**流水行仍然是两行** —— 金额掉到第二行，
「28日」折成「28 / 日」。原因不是文案，是**这条网格规则从来没生效过**：

```css
.trow--dated { grid-template-columns: 30px 26px minmax(0,1fr) auto; }  /* 写在前面 */
.trow        { grid-template-columns: 26px minmax(0,1fr) auto; }      /* 写在后面 —— 赢了 */
```

特异性相同（0,1,0）→ 源码顺序在后的 `.trow` 覆盖前者 → 4 个格子塞进 3 列。
修法：选择器提成 `.trow.trow--dated`（0,2,0），日期列改 `max-content` + `nowrap`。
完整推理见 §〇.8 第 1 处。

**窄屏再加一条让位**：一行放不下「名称 + 支付方式 + 账期 + 金额」时，
**账期让位**（`.trow__sub-x`，容器查询 `max-width: 460px`）——
支付方式回答「这笔钱从哪张卡出」，是**识别这一笔**的一部分；
账期回答「这笔什么时候出账」，是**对账**细节，报表与对账页有完整呈现。
桌面两者都在，**同一个组件、两种宽度、两种写法**。

#### 6.2.二 移动端的文字原则（第八次修正 · 第九次补上「结构先于文案」）

> 文字显示遵循在移动端能单行收纳则不换行、信息精简有效的原则。

这条从一件事上升成了一条**通则**，它管三处：

| 管到哪 | 具体做法 |
|---|---|
| **流水行**（`.trow__mid`） | 主名与副信息同行；装不下时**副信息截断**，行高不变；窄屏**账期让位** |
| **提醒条目**（`.topcard__item`） | 一行放完：金额 / 期次 · 名称 / 多急 / 状态 / 按钮；`nowrap` |
| **提醒条**（`.chipbar`） | 一行放完，展开箭头挂在行尾 |

##### 先修结构，再减字（第九次修正）

> 如果文字确实必要无法精简，重新设计布局，起码保证视觉上应该是一行。

第九次的真机截图证明：**这两处「一行」没做到，主因都不是文案长。**
一处是优先级 bug（规则压根没生效），一处是 flex 的 `min-width:auto` 禁止了收缩。
文案只是最后那根稻草。**顺序反过来做，下次数据一长，毛病会原样回来** ——
而且看起来又像「文案问题」。完整推理见 §〇.8。

##### 牺牲顺序（第九次改写）

第八次写的是「按钮 > 金额 > 名称 > **状态词**」。**第九次推翻了它**：

| | 第八次 | 第九次 |
|---|---|---|
| 允许截断的 | **状态词** | **计划名**（「3期 · 房贷」） |
| 永不截断的 | 按钮 / 金额 / 名称 / 紧急度 | 按钮 / 金额 / 紧急度 / **状态词** |

**为什么反过来**：截断一个 4 字词，读者看到的是「自…」——
比不显示更糟。而少知道「是哪一期」，**不影响你决定按哪个键**。
纪律写进代码（`.topcard__item-*` 四个类各写各的 `flex`），
数学上闭合：最坏情况仍短于最窄的 320px 机型。

##### 文案的极限：只说是什么、不说为什么

**「信息精简有效」的落点是「只说是什么、不说为什么」**：
不写「撤销过，不自动入账」（解释），写「需手动入账」（结论）。
多出来的字不是信息，是**让读者自己从原因推出结论的成本**。

第九次把这条推到底：

| 原 | 现 |
|---|---|
| `第 3 期 · 房贷` | `3期 · 房贷` |
| `逾期 29 天` | `逾期29天` |
| `需手动入账` | `需手动`（右边按钮就写着「入账」，两槽拼成一句） |
| `自动入账` | **不动** —— 它回答「我不点会怎样」，是全行唯一推不出来的信息 |

**「一行的容量」是有上限的，减到某个点就不能再减了** ——
那个点就是「再减会删掉一条推不出来的信息」。到了这个点，**该改的是布局，不是文案**。
这正是用户那句话的意思。


### 6.3 报表页 = 统计（结构 + 对照 + 精度）

**分工**（§五 第 3 条）：

- **概况回答「多少」** —— 只看量，横跨本月 / 今年 / 汇总
- **报表回答「构成是什么、跟谁比」** —— 看结构与对照，精度到年 / 月 / 天

**这一页是分类唯一的家** —— 一级构成、二级下钻、排行、涨跌榜，全在这里。

#### 6.3.1 按档位组织：换档 = 换掉一整组块（§五 第 9 条）

八块全上屏的话，390 宽上约 6 屏。但**长不是靠折叠解决的，是靠不给无关的块上屏**。
档位不是「一个大数字的开关」，它是**这一页最外层的组织方式**。

| 块 | 月档 | 年档 | 汇总档 | 为什么 |
|---|---|---|---|---|
| ① 档位 + 期间 | | | | — |
| ② **分类构成** | 本月 | 本年 | 全部 | 三档问的是三个不同的「构成是什么」 |
| ③ **期内节奏** | **按天**折线（逐日标值） | **按月**折线（12 点） | **按年**折线 | **换的是形态，不是块** —— 三档都需要「走到哪了」 |
| ④ **对照** | 较上月 / 去年同月 / 近 12 月均值 / 单笔最高 | 较去年 / 近 3 年均值 / 最高月 / 单笔最高 | **隐藏** | 汇总没有对照组 |
| ⑤ **涨跌榜** | 较上月 | 较去年 | **隐藏** | 涨跌必须先有「较谁」 |
| ⑥ **还款节奏** | 本月已刷 + **下月要还** | **隐藏** | **隐藏** | 「下月要还」只有月档成立；年档下它退化成「全年各方式占比」，**而那是 ② 已经答过的** |
| ⑦ **本期洞察** | 月 3 条 | 年 3 条 | **累计 2 条** | **换的是规则集，不是块** —— 档位下的「值得一提」不一样 |
| ⑧ 按记录人 | | | | — |

**落到的块数：月 8 · 年 7 · 汇总 5。** 年档与汇总档各少掉的那两三块，
恰好都是**在那一档下答案已经重复**的块。

**判据要写清，否则会做成「藏东西」**（§五 第 9 条的说明）：
每个块在三档上**都算得出数**，所以「能不能算出来」是个无效判据 ——
按它会一块都不减。有效判据是「**这一档下它还在不在回答一个新问题**」。

**④⑤ 在汇总档一起消失，不是分别判断的**：它们都依赖「较谁」，
而汇总档没有对照物。少掉两块之后汇总档正好只剩「构成 + 节奏 + 洞察 + 记录人」——
**这四块合起来就是「我一共花的钱花在哪了、怎么走过来的」**，一个完整的问题。

**⑥ 为什么年档也去掉**（这条最容易做错）：直觉会说「年度也有还款啊」，
但年度口径下的还款节奏**算出来就是各支付方式的全年金额占比** ——
与 ② 分类构成是同一个问题的另一个切法（一个是按分类切、一个是按卡切）。
**留一个能算出数的块，比留一个折叠起来的块更容易出错**：用户折叠不起来的是它自己的重复。

#### 6.3.2 八块本身

| # | 区块 | 内容 | 变化 |
|---|---|---|---|
| ① | **时间维度 + 期间** | 与概况**同一套三档**（月 / 年 / 汇总）+ 期间选择器；**选档决定下面哪些块上屏**（见上表） | 改（原先只有月 / 年，且不换块） |
| ② | **分类构成** | 环图 + **可展开的图例行**；一级 → 二级；占比 <1% 归「其他」；**环图中心不显示合计**（显示分类数） | **从概况挪来 + 升级** |
| ③ | **期内节奏** | 月档 = **按天折线**（逐点标数值，**点某天 → 展开当天快照**）；年档 = 按月折线（点某月 → 跳到月档）；汇总档 = 按年折线 | 改（原先月档完全没有图） |
| ④ | **对照** | 月档：上月 / 去年同月 / **近 12 个月均值** / 单笔最高；年档：去年 / **近 3 年均值** / 最高月 / 单笔最高 | 改（去掉「日均」，那归概况；**汇总档隐藏**） |
| ⑤ | **涨跌榜** | 按**变化额**排序的分类（涨=红 / 跌=绿）；月档较上月、年档较去年 | 新增（**汇总档隐藏**） |
| ⑥ | **还款节奏** | 本月各方式花了多少 + **下月要还多少** | 改口径（**只在月档**） |
| ⑦ | **本期洞察** | 月档 3 条 / 年档 3 条 / 汇总档 2 条 | 新增 |
| ⑧ | 按记录人 | 排名行 | 保留 |

**② 从概况挪来之后升级的地方**：概况原来那张卡是「环图 + 图例」，
图例只有一级。挪到报表之后，**「精度」成了这一页的职责**，
所以图例的每一行**可展开二级**（`餐饮 ¥1,286` → `外卖 ¥742 / 堂食 ¥386 / 咖啡 ¥158`）。
占比 <1% 的合并成「其他」一行 —— **不然二十个小分类会把图例撑爆**。

**② 环图中心不显示合计** —— 那个数在概况 hero 上（§三 末尾）。
报表讲结构、不讲总量，中心改显示「N 个分类」。

**① 为什么这里可以有「汇总」档**（与上一版相反）：上一版不加它，
理由是「汇总没有对照组」，而报表的核心是对照。现在报表多了一个身份 ——
**它是分类的家** —— 于是「**我一共花的钱花在哪了**」成了一个真问题，
且只有汇总档能答。汇总档下**隐藏 ④ 对照**（确实没有对照组），其余照常。

**③ 为什么「天」靠月档的按天折线，而不做成第 4 档**（§五 第 8 条）：
月档那条折线有 30 个点，**逐日数值都标出来**，这本身就是精度到天。
再给一个独立的「天档」，它与流水页的按天分组是同一件事的两种画法 ——
**又造出一处重复**，正是这一轮要消灭的东西。
所以「看某一天」只在两处，各看各的：
报表里点折线某天（看**比率**：占本月 X%、是日均 N×）·
流水页的组头（看**明细**：那天买了什么）。

**④ 四格全部是「与谁比」**：这是报表页的定义性特征。
新增的「近 12 个月均值」比环比稳 —— 环比会被单月异常带偏，
而「这个月比过去一年平均高多少」更接近用户真正想问的「这个月算贵吗」。

**⑤ 为什么要有「涨跌榜」**：分类构成是**按金额**排的，
结果永远是那几个大类常驻（住房 / 餐饮），**看不出变化**。
涨跌榜按**变化额**排，能回答「这个月是什么让我多花了 800 块」。

> **句式照参考项目的归因写法**（§2.7 第 12 条）：不说「餐饮 2,000」，
> 而说「**餐饮 2,000（比月均 3.2×）**」「**手机数码 10,999（本月独有）**」。
> 三种「为什么」：`本月独有` / `超月均 N×` / `与月均持平`。
> 分类构成里金额最大的那几行也同样要**标出变化的那一项**，
> 否则那几行一年都不变。

**⑥ 为什么改口径**：「本月各卡花了多少」是**已经发生**、用户改不了的事。
「下月要还多少」（`repayment_date` 平移到下月）才是**能让人改变行为**的数字。
这是我们**独有**的能力（参考项目没有 `repayment_date`）。

**去掉**：页首大数字与「共 N 笔」（归概况）。

**不再去掉一级分类构成** —— 这一版把它**从概况搬了过来**。
上一版写的是「删掉一级构成」，方向错了：删掉之后两页都没有构成，
用户想看「钱花在哪了」就没地方去了。
正确的做法是**给它一个明确的家**，而不是让它消失。

#### 6.3.3 日历：**流水页**年 / 全部两档的形态（**第七次修正重写**）

> **这一节在第七次被整个重写。** 上一版把它放在**报表页**（当作 ③ 期内节奏在年 / 汇总档的形态），
> 并注明了「我拿不准 L4 指哪一条」。用户澄清后方向变了 —— **日历属于流水页**。

用户澄清 L5 的原话：

> 按月正常显示流水，按年或全部则进入到日历页，点击日历的年份或月份可以查看该月的相关信息，
> 如展示当年月的概况，花费多少，分布等等，下方加入进入按钮或者再次点击进入下一层级，
> 年进入月，月进入正常流水页。

**结论：日历不是新页面、也没有新路由。** 它就是**流水页**在年 / 全部两档的形态 ——
期档换到年或全部，列表就变成日历。

| 档位 | 上屏的主体 | 点一下（＝选中） | 再点 / 按「进入」 |
|---|---|---|---|
| **月** | **正常流水列表**（无组头，行内只写「日」） | — | — |
| **年** | **日历页：一格一月**（12 格） | 下方卡切到该月：合计 · 笔数 · 日均 · **分类分布** | **月 →** 月档＝正常流水 |
| **全部** | **日历页：一格一年** | 下方卡切到该年：合计 · 笔数 · 月均 · 分类分布 | **年 →** 年档（12 格） |

#### 我上一版错在哪

错在**把日历当成了「统计」**。日历不是一种统计图，它是**期间选择器** ——
所以它属于**流水页**（那里才有「换一段时间看某一段」这件事），不属于报表页。
两页的分界因此写死：

| | 回答什么 | 形态 |
|---|---|---|
| 报表页 **③ 期内节奏** | 「**走到哪了**」 | 月档按天折线 / 年档按月柱 / 全部按年柱 —— **读进度** |
| 流水页 **日历** | 「**哪几个月有东西、点进去**」 | 格子即量，点格选中 —— **找期间** |

#### 两个动作，靠点几次分开

| 动作 | 结果 |
|---|---|
| **第一次点某格** | 选中该格，**下方那张卡切到这个期间**。**不换页、不滚动、不出现返回栈** |
| **再点同一格**，或点卡上的 **「进入 … →」** | 才真正下钻：全部档点年 → 年档；年档点月 → 月档＝**正常流水** |

**为什么值得分两步**：一格上只有一个数，看不出「这个月花在哪」。一步就跳走的话，
用户得跳过去、发现「不是这个月」、再跳回来 —— 两步把**「看看」和「进去」拆开**，
**翻月份的成本从两次跳转降到点一下**。

#### 「下方那张统计卡」就是同一个东西

第六次那句「每个日历页下方需要有相对应的统计卡片内容和数据」，落点如下：

| 选中的是哪一格 | 下方卡显示什么 |
|---|---|
| **没选** | **本档**的统计（年档 / 全部档那一组块） |
| **选了某月 / 某年** | **整组切到那一格**：合计 · 笔数 · 日均（或月均）· 分类分布 |

所以「点一下看该月信息」和「日历下方挂统计卡」**是同一件事的两种说法** ——
日历在这儿的作用就是**一个期间选择器，它驱动下面同一组卡**。

**而「日历只做骨架」这条约束不变**：格子只给量（当月合计 / 全年合计），
**不在格子里塞环图、排名、涨跌** —— 那会做出一张「什么都想说的日历」，
而日历的价值恰恰是**一眼看出哪几格深**。统计一律挂在下方。

#### 选中的样子：描边，不是填充

选中态用 **描边 + 一层极淡的底**，**不用填充色** ——
一块填充色在本站的意思是「这块有事要动手」，选中的某个月没有这层意思。
（同一条纪律见 §6.5 六 的颜色标记、§五 第 16 条。）

#### 下钻改「期间」，不换「页面」

从年档点进 9 月，是 `scope=year & month=9` → `scope=month`，
页面、滚动位置、组件树都不变。**必须写死**：
若做成「跳转到另一个页面」，就会多出一层返回栈，
把 §6.6 六 刚定干净的「二级页只有一个出口」破坏掉。

#### 花销深浅：四档，只用强调色（第八次修正）

> 日历改动方案认可，但需新增以颜色深浅表示花销大小的功能：除提醒与标志需表示紧急程度外，
> 其余颜色一律沿用强调色（当前主强调色为蓝色），通过不同深浅的蓝色帮助用户快速定位
> 花费最多与最少的月份，仅需四种状态色，即最多-最深、稍多-略深、平均数上下-普通、最少-最浅。

**这是这一轮唯一新增的「数据可视化」**，所以每条判据都要能解释：

| 档 | 含义 | 判据（m ＝ 本档均值） | 底色（叠在卡片底上） |
|---|---|---|---|
| **4** | **最多** · 最深 | ≥ 1.5 m | `rgba(59,130,246,.42)` |
| **3** | **稍多** · 略深 | 1.15 m ~ 1.5 m | `rgba(59,130,246,.24)` |
| **2** | **平均数上下** · 普通 | 0.85 m ~ 1.15 m | `rgba(59,130,246,.12)` |
| **1** | **最少** · 最浅 | < 0.85 m | `rgba(59,130,246,.05)` |
| **0** | **一笔都没有**（不是第五种颜色） | 合计 ＝ 0 | 透明 + 一圈描边 |

**「四档」说的是色阶只有四种，0 不占色阶** ——
它没有填充、只有描边，读起来是「空」而不是「浅」。
把它当成第五档写进图例也可以，但必须和「最少」在视觉上分开（见下）。

**为什么以「均值」为轴，而不是在最大 / 最小之间等分**：
用户的原话是「**平均数上下＝普通**」—— 这句话要求「普通」这一档**跨在均值两侧**。
若按最大最小等分，「平均的那个月」会被归进「稍多」或「最少」，与这句话对不上。
四档的语义于是落成：**均值附近是普通，一倍半往上是最多，不到均值一半是最少。**

**为什么「0」要单独一档**：**没花钱和花得少不是一件事。**
把 0 涂成「最浅」，读起来是「那个月花得很少」；实际是「那个月一分没花」。
颜色越淡承担的信息越弱，而 0 是一个很强的信息（断供、换卡、没记账），
所以它用**描边（＝空）**，而不是最浅的填充（＝少）。

**值用 rgba 叠在卡片底上**，深浅两个主题自动成立（浅色主题叠出淡蓝，深色主题叠出深蓝）；
最深一档（.42）配深字仍有约 9.8:1，够 AA。

**颜色纪律（这条最重要）**：页面上现在有**两套颜色语义**，不许串 ——

| | 用什么说 | 说什么 | 出现在哪 |
|---|---|---|---|
| **提醒** | **色相**（黄 / 红） | 需不需要你动手 | **只有箭头和文字** |
| **日历** | **明度**（蓝的深浅） | 花了多少 | **只有格子底** |

把日历的深蓝挪去别处用（比如给「本月支出」的大数字铺底），
就会把「花得多」误读成「要注意」—— 那正是第六次修正刚拆开的东西。
**「其余颜色一律沿用强调色」这条约束的真正作用，是把第二个色相挡在门外。**

**选中态与深浅不冲突**：选中用**描边**（`aria-pressed`）、深浅用**底色** ——
两者占的是不同的视觉通道，互不覆盖。
（这也是第六次那条纪律「颜色不铺成背景」与本次不冲突的原因：那条管的是**紧急度**，
日历的底色是**量**，不是「要动手」。）

##### 图例删掉（第十次修正）

> 越深＝花得越多（月均 ¥8,033） 最少 普通 稍多 最多 空月 这种说明不要。

删的是**整行图例**（含那五格色点），保留的是**汇总行里的月均**：

```

```

那条图例的**载荷只有一个月均数**，而这个数就在它正上方。
**同一个数在一个页面里出现两次，不是强调，是让人怀疑「这两处是不是同一个数」。**
至于「最深＝最多」，四格并排时是**看图就懂**的 —— 需要解释的只有轴在哪，
而轴就是那行汇总。完整论证见 §〇.9 第 1 条。

**「数据」只给管理员。** 导出含全家庭的数据、导入 / 清空会改全家的数据。
客户端隐藏按钮**不算权限控制**，所以服务端每一条数据类路由都挂了
`requireAdmin` —— 前端这里只是不把一个注定 403 的入口摆出来。
它用 `v-if` 而不是 `v-show`：其余 tab 用 `v-show` 是为了留住编辑态，
而这一页要的恰好相反（每次进来重读概览，条数才是当下的）；
用 `v-show` 的话它在页面加载时就会发一次请求，非管理员即使看不到这个 tab
也会先吃一个 403。

**两个按钮的文案与设计稿不一样**，是刻意的：

| 设计稿 | 落地 | 为什么改 |
|---|---|---|
| 清空全部数据 | **清空账目数据** | 它清的是支出 / 计划 / 待办，**不动**分类、支付方式、账号 —— 那是配置，删了记账当场没有分类可选。「全部数据」四个字是错的 |
| 重置演示数据 | 重置演示数据 | 保留，但**加了前置条件**（见下） |

#### 二、「重置演示数据」为什么必须有前置条件

一个叫「重置」的按钮，**最容易被理解成「把我的数据整理一下」**。
若库里已经有真实账目而它照跑，用户会丢掉全部真实数据、换来一堆假账单 ——
而且他以为自己在「重置」。

所以判据落在**上一次种子留下的 id 清单**上（存在 `settings.demo_seed`）：

- 活着的账目里**只要有一条不在清单里**，就拒绝（409），
  并把那句话直接写出来：`库里已经有不是演示数据的东西（支出 1 条），拒绝重置。`
- 清单**不存在**时：库里一条账目都没有 → 放行（这是「灌一份演示数据」的路径）；
  有账目 → 全部算「不在清单里」 → 拒绝。**同一个条件覆盖了两种情形，不需要特判。**

顺带两个实现约束，都是「不做就会在第二次点击时炸」的那一类：

1. **凭据必须与种子在同一次事务里写下** —— 种子成功而凭据没写，下一次重置会因为
   「清单是空的」而被自己拒绝；
2. **清空账目时必须清掉凭据** —— 留着会让下一次重置拿一份**过期清单**当准入依据，
   而那时库里已经一条不剩，本该判定为「可以直接灌」。

#### 三、演示数据的日期是**相对今天**算的

原来的 `server/scripts/seed-demo.mjs` 写死 2026-08 / 2026-09。
那是**只在开发机上跑一次**的脚本，写死没问题；而「重置演示数据」是界面上
**一个能按的按钮** —— 写死的话，第二年按下去会长出「去年的数据」，
用户看到的是「演示数据坏了」。

所以移植进服务端时只保留**相对关系**（上一月 / 本月 / 往前两个月 …），
日期现算，`today` 由客户端传（服务端从不自己推算业务日期 —— 见 `config.ts`）。
今天跑与一年后跑，得到的结构完全一样：本月那一期房贷**必然逾期未确认**，
所以首页「该处理了」一进来就有东西 —— 这是这个种子存在的意义。

#### 四、还没做的那一行

设计稿在「数据」tab 表格的第一行列了**顶部数据元信息**
（最后备份时间 · 数据库大小 · 首笔日期）。它是 **§九 第 7 步（`A16`）** 的内容，
**不属于 `#11`**，所以这一轮没做。概念上要分清：
它不是成就数字（「记录天数/总笔数」在概况的累计块），而是**「数据」这摊事的元信息**。

### 6.5 计划与还款提醒放哪里

这一节回答一个 §6.1 没写清的问题：**概况改成一屏总览之后，「该处理了」去哪。**
（也解释了为什么参考项目不用想这个问题。）

#### 一、我们其实有两条线，BeeCount 只有一条

| 线 | 数据来源 | 语义 | 能否提前知道金额 |
|---|---|---|---|
| **计划待办** | `plan_todos`（`remind_date` + `repayment_date` + `amount_cents`） | **金额确定、期数确定**的欠款（房贷 / 分期） | 能 |
| **信用卡账单** | `payment_methods.repayment_date` | 每月循环、**金额不确定**的账单 | 不能 |

参考项目只有第二条，而且**不把它当实体** —— 它是账户的两个字段
（`accounts.field.billingDay` 账单日 / `accounts.field.paymentDueDay` 还款日），
在资产页的账户详情里显示成「还款日 · 每月 25 号 · **还有 3 天**」。
账户一直在那儿，所以它不需要「提醒放哪里」。

**我们多出来的第一条，恰好是「能提前知道金额」的那种** ——
所以我们的提醒应该直接带金额（`3期 ¥2,800`），
而参考项目只能说「还有 3 天」。**这是我们比它多出来的能力，别浪费。**

#### 二、现状（核过代码）

| 信息 | 现在在哪 | 形态 |
|---|---|---|
| 该处理了 | 概况（`DashboardView.vue:278`） | `plansStore.dueTodos` → `PlanTodoCard` 网格 |
| 本月待还 | 概况（`:317`） | `creditDue`，来自**支付方式**，不是计划 |
| 计划完整管理 | **设置页**（`SettingsView.vue:428`） | `<PlansPanel hide-todos />` |

`dueTodos` 的口径是 `remind_date <= today` 且 `status='pending'`
（`stores/plans.ts:41`，参数 `remindBefore: today`）。

注意：由此发现：**`remind_date` 只当了筛选条件，它的日期值从没在界面上出现过。**
字段一路传到 `web/src/api/types.ts:195`，库上还专门建了索引
`ON plan_todos (status, remind_date) WHERE deleted_at IS NULL`，但 UI 只显示「该处理了」，
不显示「几号开始提醒的 / 还有几天」。

#### 三、三层归属（结论）

| 层 | 装什么 | 放哪 | 形态 |
|---|---|---|---|
| **行动层** | 已到提醒日 / 已逾期的待办 | **跟着落地页走**（§六 平台规则）：桌面 → 概况 hero 卡底部一条；移动端 → **流水页顶卡的右半格**（§6.6 三） | 桌面 `3 期待处理 · ¥8,200` ＋**展开箭头**，**点击**展开；移动端 `3 期待处理` 点击下展。两处都**不染色**，紧急度只落在**箭头**上 |
| **信息层** | 本月要还多少（信用类） | 概况网格里的 ② 卡 | 不参与三档 tab |
| **管理层** | 新建 / 结束 / 看期次 / 撤销入账 | **设置页 → 计划 tab**（现状不变） | `<PlansPanel hide-todos />` |

**行动层为什么有两个落点、而这不叫「重复」**：它只有一个落点，
只是那个落点由**平台**决定 —— 桌面的落地页是概况，移动端的落地页是流水页。
**判断标准是「同一个平台内出现几次」**，不是「全站一共出现几次」。
反过来说，如果移动端的概况 hero 上**也**留一条，那才是重复 ——
所以移动端概况页的 hero 底部**不放提醒条**（§6.6 四）。

**行动层的展开形态**（学 §2.7 第 11、12 条的三层结构）：

```
（叠在 hero 上的 popover —— 桌面：**点击**展开，悬停用于预览）

「明天到期」琥珀 /「逾期29天」红 /「10月2日到期」灰。

```

> **仍然是两行**（金额掉第二行、日期折成「28 / 日」）—— 因为网格规则被覆盖掉了。

#### 三·补、展开之后必须能动手（第五次修正，用户提出）

**没有动作的提醒只是通知。** 通知的责任是「让人知道」，提醒的责任是「让人做完」。
「3 期待处理」展开之后如果只有明细、没有按钮，用户看完还得自己跑去计划页找那一期 ——
那就等于把提醒降级成了一条横幅。所以**展开区里每一条下面必须有一行动作**：

| 这一期**现在**会不会自动入账 | 按钮 | 点了之后 |
|---|---|---|
| **会**<br>计划开了 `auto_post`，且本期没被撤销过 | `确认`<br>**一个** | 这一条从列表消失、顶卡计数 −1，**不再提醒**；到还款日照旧**自动入账**。<br>用户只是表示「我知道了」，**没有改任何业务状态** |

**判据不是「计划有没有开自动入账」，而是「这一期现在还会不会自动入账」**：

```
会   ＝  plans.auto_post = 1  AND  plan_todos.hold_auto_post = 0
不会 ＝  plans.auto_post = 0  OR   plan_todos.hold_auto_post = 1
```

上面例子里的**5期 · 房贷**就是这个差别的落点：房贷计划**是**开了自动入账的，

用户点了以为没事，**那笔账却永远不入，并且不报错**。

**为什么「会」那一类不能复用「忽略」**：`skipTodo` 会把这一期置成 `skipped`，
而 `settleAutoPost` 只挑 `status = 'pending'` 的期次 ——

用户以为只是「别提醒我」，结果账单不再入账。所以这一类只能给一个**纯知悉**的动作，

#### 二、三个入口放在哪 —— 怎么放才不叫「把底栏搬上来」

三个入口现在与**期间选择器同一行**（第五次修正），坐在那一行的**右端**；
搜索框独占下一行。位置上它们是「屏幕最上那一块」的一部分，
**跟着内容一起滚走**。

这是这一节最容易做错的一步。**把三个入口做成等宽 + 图标 + 选中态的一行，
就是把底栏原样搬到了顶上** —— 低频入口照样占着高频位置的租金。

判据是**视觉语言必须与底栏不同**：

| | 底栏（现状，要删掉） | 入口行（新） |
|---|---|---|
| 形态 | 等宽四格 | **一行次要链接**，**右对齐**、不定宽 |
| 视觉 | 图标在上、文字在下；有选中态（`text-primary-text`） | 纯文字（或小图标 + 文字）；**没有选中态** |
| 语义 | 「你在哪一页」 | 「这里还有几个地方可以去」 |
| 位置 | 屏幕最下（拇指区、常驻） | **控制行的右端**（随内容滚动、**不常驻**） |
| 随滚动 | 固定 | **滚走就滚走** |

最后一条是关键的：**入口行跟着内容滚走，底栏不滚**。
这一个小差别就把「常驻导航」和「一次性入口」分开了 ——
而且滚走之后列表能占满整屏，这正是「只保留一页」想要的效果。

**为什么不塞进一个「更多 ▾」菜单**：那要多点一次，而且三个入口会「消失」，
用户会以为设置没了。一行放得下三个词，就不值得藏。

#### 二·补、行数账：首屏之上从 3 行压到 2 行（第四、五次修正）

|---|---|---|
| 第 1 行 | 期间行：`‹ 9月 ▾` …… `38 笔` | **控制行**：`‹ 9月 ▾` **靠左** ＋ `还有 概况 · 报表 · 设置` **靠右** |
| 第 2 行 | 搜索行：搜索框 + 筛选 | **搜索行**：搜索框**独占并撑满** ＋ `筛选` |
| 第 3 行 | 入口行：还有 概况 · 报表 · 设置 | （并入第 1 行） |

**为什么入口并进期间行、而搜索单独一行**：判据不只是语义，还有**宽度需求**。
这一条里唯一**需要撑开**的控件是搜索框 —— 输入框窄了就没法用；
期间选择器、筛选按钮、三个入口，都是一行放得下的固定宽度小控件。
所以四个控件按「要不要宽度」自然分成两类：**要宽度的独占一行，不要宽度的并成一行。**

**这一版推翻了上一版的结论，值得记下为什么。** 上一版把入口单独留一行，
理由是「一行里两种语义会糊」—— 这条理由**到现在仍然成立**，
但它只算了语义、**没算视觉重量**：三个 12px 的链接占掉一整行时，
行高由它们决定、横向却空着大半，看起来像一行被遗弃的东西。
语义改用**位置**解决 —— **控制一律靠左、跳转一律靠右**，中间那段留白本身就是分隔符。

> 一般化的说法：**一行里出现两种语义时，先想「用位置分开」，不要先想「用行分开」**。
> 后者的代价是白占一整行 —— 而在首屏之上，一整行是很贵的东西。

顺带删掉了期间行末尾的 `38 笔`（**顶卡已经写了**）——
同一屏出现两次正是这一轮要消灭的东西。

**收益是可量的**：首屏之上少一行，约 **44px**；390×844 上列表的第一行因此提前小半行。

#### 二·补二、三个入口到底「在不在顶部」—— 只在，且只在一个地方（第六次修正）

用户在裁决 M4 时追加了一问：*「这个功能需要明确入口是只在顶部，
还是这几个入口会跟随页面固定在顶部。」* 这条要写死，否则实现时必走歪：

| 问题 | 答案 | 理由 |
|---|---|---|
| 入口放在哪 | **只在流水页顶部**，在控制行右端 | 它是「这一页还有几个地方可以去」，不属于页面本身 |
| 会不会跟随滚动 | **不吸顶、随内容滚走** | ① 与「删掉底栏＝不常驻导航」是同一条原则 —— 吸顶就等于把底栏搬回顶部；② 它要占掉一整行，而首屏之上每一行都贵；③ 与 §6.6 六「二级页标题行也不吸顶」一致 |
| 二级页里还有没有 | **没有**，一个字都不重复 | 二级页有自己的标题行 + 行尾 `×`，再加一条入口行就是「页面之上又压一条工具条」 |
| 那怎么回流水页 | **行尾 `×`**（§6.6 六） | 这是唯一的出口，也是唯一的返回语义 |

> **「只在顶部」有两层意思**，实现时要都满足：
> **①空间上只在顶部**（不吸顶）、**②层级上只在流水页**（二级页里不重复）。
> 只满足第一层是最容易犯的错 —— 那样用户从「报表」里还能看到「还有 概况 · 报表 · 设置」，
> 其中「报表」还是当前页，等于给了一个指向自己的链接。

**为什么这条值得单独写**：入口行的「不常驻」是**这一节所有设计的价值来源**
（删掉底栏换来的那一整行高度）。它一旦吸顶，删底栏就白删了 ——
**等于用新的一行常驻控件，换掉了旧的一行常驻控件**，成本一分没省。

#### 三、顶卡的三种状态 + 提醒可折叠 + 展开后有动作（第四、五次修正）

顶卡把 **本月支出** 与 **处理提醒** 并排放在同一行。两个数回答的是同一句话的两半：
**「这个月花了多少」** 和 **「这个月还有什么要动手」**。
上一版把提醒压成通栏一条 chip，换来了「不占格」，代价是移动端这一页
**没有本月支出** —— 它留在概况那页，而概况在移动端是二级页。

| 状态 | 本月支出 | 处理提醒（收起态） | 是否吸顶 |
|---|---|---|---|
| 有待处理（未逾期） | 半格 | `3 期待处理` / `¥8,200 · 点开看明细`（**中性底 + 黄标记**） | 不吸顶，滚走让路 |
| **有逾期** | 半格 | `1 期已逾期` / `29 天 · ¥2,800`（**中性底 + 红标记**） | **整张顶卡吸顶** |
| 无待处理 | **独占整列** | **整格消失**（不留半格，也不放「没有待处理」占位） | 不吸顶（没东西可吸） |

> 注意：**第六次修正：这一格不再染色。** 原来是「琥珀底 / 红底」，
> 用户改成**卡片无色 + 一个颜色标记**（自动入账＝无 / 需手动确认＝黄 / 逾期＝红），
> 紧急度走**文字**。所以上表里「中性底 + 标记」才是终态 ——
> **吸顶与颜色是两件事**：吸顶由「有没有逾期」决定，颜色由「要不要动手」决定。

**折叠规则**（§五 第 11 条）：

- **默认收起** —— 「3 期待处理」是**结论**，每天都看；「哪 3 期、各多少、几号还」是**细节**，
  一周看一次。默认展开就是拿高频的成本去赔低频的内容。
- **展开是向下的，把列表顶下去**，不是浮层。浮层会盖住「展开之后我想看的那些行在哪」。
- **默认收起要写在 HTML 属性上，不要在 JS 里初始化** —— 否则脚本没跑（或跑得慢）时
  会先闪一下展开态再收起。
- **两种形态要同一个组件 + 一个布尔**，不要写成两个分支 —— 那会长出两套间距。

**「无待处理时整格消失」推翻了 §6.5 三 的一条旧规则**：
旧规则说「0 条时显示 `没有待处理`，空态本身是信息」。
那条在**桌面 hero 的提醒条**上仍然成立 —— 那里是一行 12px 的灰字，成本≈0，桌面也有横向空间。
但在移动端它是一个**半格**：格子消失能直接换来本月支出从半格变整格。
**同一个信息在两地的成本不同，处理就该不同。**

**为什么只有逾期才吸顶**：不吸顶的代价是「滚一下就不见了」，
而逾期恰恰是**不该被滚走**的那种状态。用一条规则同时表达
「它重要」和「它占地方」。
**注意它与颜色已经解耦**（第六次修正后不再有「红 = 吸顶」这条解释）：
吸顶说的是**位置**，颜色标记说的是**要不要动手**，两者都由「有没有逾期」推出，
但互不解释。这样顶卡**不会被染成一片红**，却仍然会在该吸顶的时候吸顶。

**展开区里每一条要有动作**（第五、六次修正）—— 完整规则见 §6.5 三·补。
这里只补一条与顶卡有关的：**动作的反馈必须回到顶卡上**。
点「确认」/「忽略」/「入账」→ 那一条消失、顶卡**计数 −1**；
**计数归零 → 顶卡自动变回单列**（本月支出独占整列）。
也就是说，「两列 / 一列」这个形态**是数据的结果，不是用户的选择** ——
这正是第 11 条说「两种形态要同一个组件 + 一个布尔」的原因：
那个布尔就是「待处理数是否为零」，它跟着数据走，不需要额外开关。
（紧急度的表达见 §6.5 六：**容器不染色，颜色只出现在明细前的标记上**。）

#### 五、下拉唤出记账

**先确认一块空地：** 核过 `web/src`，**全站零触摸手势**
（`grep touchstart|touchmove|pointerdown` 无结果），**也没有下拉刷新**。
所以「下拉」是一块**没被占用的地皮** —— 可以直接给记账用，
不必和任何人抢。将来若要下拉刷新，改用期间行里的刷新按钮，**不要来抢这个手势**。

**手势与动画**：

```
静置                 拖拽中（跟手）            松手
┌──────────┐        ┌──────────┐            ┌──────────┐
│ 提醒框 │        │  ↓ 记一笔 │ ← 跟手露出   │ 记账面板  │
│ 搜索      │        ├──────────┤            │ （现状抽屉 │
│ 分组列表  │  下拉   │ 提醒框 │            │  从底部升起）│
│          │  ────►  │ 搜索      │            │          │
└──────────┘        └──────────┘            └──────────┘
```

- **手势是触发器，面板仍从底部升起** —— 复用现有 `ExpenseSheet.vue`
  （手机上是 `inset-x-0 bottom-0 top-[6vh]` 的底部抽屉），**组件零改动**，
  只是在 `App.vue` 加一个手势监听去调 `ui.openCreate()`。
  面板不放顶部，是因为记账是最高频动作，**底部才是拇指够得到的地方**。
- **只在列表处于顶部时生效**（`scrollTop === 0`），阈值 60px。
  这是主流程：「打开 App → 列表在顶部 → 下拉 → 记账 → 保存 → 新增那条出现在列表顶」。
- **保存后把新记录滚到顶并高亮 1.5 秒** —— 让这个手势有闭环，
  否则用户下拉一下就"消失"在一个面板里，不知道刚才发生了什么。

**两个必须一起做的前提（否则手势会变成「隐形按钮」）**：

1. **首次引导**：第一次进流水页时提示一次「下拉可记账」，之后永不再现。
   手势是**不可见**的，没有引导就等于没有入口。
2. **跟手反馈**：拖拽时面板边缘要跟着手指露出，松手才完全展开。
   没有跟手，用户会以为下拉没反应。

> 注意：**兜底出口已删（第六次修正，用户裁决）**：用户明确说**不需要额外入口**，
> 所以我原方案里的两条兜底 ——「列表滚到底出现一行『＋ 记一笔』」和「空态给一个按钮」
> ——**都不做**。
>
> 这把手势从「主入口」提成**唯一入口**，风险随之上升：
> 原来兜底是安全网（手势不灵还能在列表尾部找到入口），现在**手势失灵就没有任何记账入口**。
> 所以 `A19` 的实测判据要相应升级（§八 / §九）：
> **不是「手势好不好用」，而是「在手势失败率为 0 之前不能算完」** ——
> 真机上要覆盖 iOS Safari 的橡皮筋滚动、Android 的 overscroll 接管、
> 以及「列表不在顶部」这个前提本身会不会被用户误解成「下拉没反应」。
>
> 用户选择不带兜底也有它的道理：**多一个入口，就多一处「要维持的界面」**，
> 而且那两处入口会把用户的注意力从手势上分走 ——
> **在只有一个入口的系统里，那一个入口会被学得更牢。**

#### 六、二级页的页头与关闭（第五次修正改写）

概况 / 报表 / 设置从控制行进去之后，**没有底栏可以回来**，所以必须有出口。
**上一版是「页头左上角一个 `‹ 流水`」，它自己占了一行** ——
等于在页面之上又压了一条工具条。这一版**并进标题行**：

```
采用：关闭在行尾                对照：关闭在标题前（不采用）
┌────────────────────────┐       ┌────────────────────────┐
│ 设置                 × │       │ ×  设置                │
│ 我的账本 · 5 个 tab     │       │    我的账本 · 5 个 tab  │
├────────────────────────┤       ├────────────────────────┤
│ 导出 / 导入 / 备份与恢复 │       │ （标题被推右，与内容    │
│                        │       │   左边界错开）          │
└────────────────────────┘       └────────────────────────┘
```

**为什么选行尾**（用户倾向行尾，我同意）：

1. 与「**关闭在右上**」的通用预期一致（`‹` 在左上＝返回，`×` 在右上＝关闭）；
2. 标题与页面内容**同为左对齐**，不引入第二套基线；
3. `×` 与标题之间隔着整行宽度，**误触率最低**。

**`‹` 与 `×` 不是一回事**：`‹` 是「返回上一页」，`×` 是「关闭这个页面」。
我们的场景是后者（从流水页进来，关掉就回到流水页），所以用 `×`。

三件要写清的事：

| # | 事项 | 说明 |
|---|---|---|
| 1 | **只窄屏渲染** | 桌面顶栏常驻、四页可直切，不需要关闭键 |
| 2 | **触达 40×40** | 字号 19px、默认 `--fg-muted`。它是页面里唯一的出口，不能做得比正文还轻 |
| 3 | **标题只在页头出现一次** | 页面内容里不再重复一遍「设置」二字（现在是页头写一遍、`card` 标题再写一遍） |

**不吸顶** —— 吸顶就等于一个 mini 顶栏，与「不常驻」相冲。
但报表页内容长时，滚到中段关闭键会滚出屏幕，要在 390×844 上实测一次
「滚到中段想出去」别不别扭（列进 §十一）。

顺带要改一处：**概况 hero 里那个「设置」链接（`DashboardView.vue:202-207`，`lg:hidden`）要删掉**
—— 设置现在有唯一的入口（流水页的控制行），概况 hero 上再挂一个就是两处入口。

### 6.7 版式：卡片不为对齐而撑高（§五 第 12 条）

这一节是被用户抓出来的（§〇.3 第 3 条）。**它不属于某一页，属于全站。**

#### 一、症状 → 根因

症状是「有些卡片看起来空了一大块」，例如设置页的**危险区**。
根因不在那一页，在 CSS 的**一个默认值**：

```css
/* grid 的默认值 —— 没人写它，但它是生效的 */
.grid { align-items: stretch; }
```

它把同一行的卡片**一律拉到行高**。矮的那张多出来的空间**全落在卡片底部** ——
于是卡片自己凹进去一块。**项目里没有任何人「决定」要这么做**，
所以修法也不该是逐页调样式，而是在 `.grid` 这个基类上把它关掉一次。

#### 二、判据（能量出来，不用看）

> **一张卡片里，最后一行内容离卡片底边的距离 > 40px，就是错。**

量法（`getBoundingClientRect`）：

```js
// 卡内底部空白 = 卡片底边 − padding-bottom − 最深后代元素的底边
const slack = rect.bottom - parseFloat(getComputedStyle(card).paddingBottom)
            - Math.max(...[...card.querySelectorAll('*')].map(e => e.getBoundingClientRect().bottom));
```

这条和「概况的 DOM 里不出现分类名」是同一种东西：
**把一条原则翻译成一句能量出来的断言，原则才会被真正遵守。**
体检脚本：四页 × 三个档位全量，见预览页 ⑨。

#### 三、实测（1440 宽，改之前）

| 位置 | 卡内底部空白 | 为什么会这样 |
|---|---|---|
| **设置 · 危险区** | **89px** | 和「备份与恢复」并排在 `grid--2` 里，内容只有「标题 + 一行 + 两个按钮」，被拉到 222px |
| 报表 · 按记录人 | 73px（年档 53px） | 和「本期洞察」并排，洞察有 3 条规则句 |
| 报表 · 涨跌榜 | 52px | 和「还款节奏」并排，还款节奏多一个「下月要还」的块 |

#### 四、两条修法，按顺序用

| 顺序 | 修法 | 性质 |
|---|---|---|
| **①** | **卡片网格一律 `align-items: start`** —— 卡片按内容高 | **结构性的**：一次关掉全站的默认撑高 |
| **②** | **高度差太大的两张，本来就不该并排** —— 危险区改成**通栏一条**放最底 | **配对性的**：撑高只是掩盖，配对才是根因 |

改后：**三处空白全部归零**（脚本复测：`.card / .dangerband / .strip` 全页扫描，三档均 < 40px）。

##### 落地时的修正：它不能写成 `.grid { align-items: start }`（第十一次）

上面第 ① 条原本写的是「`.grid` 一律 `align-items: start`」—— **写成全局覆盖是错的**。
落代码时才看清：这个项目的网格是 Tailwind 工具类，而且**有些网格靠 `stretch` 撑满格子**：

| 网格 | 为什么不能改成 `start` |
|---|---|
| 数字键盘（`grid-rows-4`） | `⌫` / `＋` 是 `text-lg`、数字键是 `text-xl` —— 键高**靠拉伸对齐**；「保存」更是**跨两行**，不拉就只剩一行高 |
| 期间选择器的三格 | 同上一类：一个分段控件里按钮不等高就是坏的 |
| 设置页窄屏 tab 条 | 五个标签长度不同（「分类」对「家庭与账号」），折行之后靠拉伸保持等高 |

所以落地形态是一个**新的类**而不是一条全局覆盖：

```css
.card-grid { display: grid; align-items: start; gap: 12px; }
```

> **可复用的一条**：「网格不该撑高」这条规则，**主语是卡片，不是网格**。
> 把它写成对 `grid` 的全局覆盖，等于顺手改掉了一批**本来就该撑满**的网格 ——
> 而它们坏掉的样子（键盘散架、分段控件不等高）与「卡片多了一截空白」
> 看起来毫不相干，不会有人想到是同一行 CSS 干的。

#### 五、顺带说明两件事

- **危险区为什么是通栏而不是「塞满」**：它天然排在所有操作的最后，
  通栏 + 说明在左、按钮右对齐，反而更像一道「闸门」。**塞内容是掩盖，换形态是解决。**
- **为什么不去做「让所有卡片等高」**：等高本身不是目标，「看起来整齐」才是。
  两张卡内容量差一倍时，等高只能靠撑高实现 —— **整齐没换来，空白倒是实打实的**。
  （同一类问题的另一种形态是「为了凑满一行把最后一张卡拉宽」，
  报表页的 `.grid--auto` 已经用 `auto-fit` 解掉了。）

> **`align-items: start` 之后剩下的是「行高差」**：矮卡片的下方会空出页面底色。
> 那是**行与行之间的留白**，不是**卡片里的凹陷** —— 前者不刺眼，
> 因为读者知道那是段落间距。**这两者必须分清，否则会误以为问题还在。**

**为什么把移动端放在最后一步**：单页化会**动 `App.vue` 的外壳**
（删底栏、`--bottom-bar-h` 归零），而前面的步骤都要改页面内容。
先改外壳会让后面每一步都要在「四页 + 底栏」和「一页 + 控制行」之间来回确认。
**内容先定，外壳最后换** —— 换的是壳，不是内容，所以放最后风险最小。

**为什么 `A22` 反而排在最前**：它和「外壳」相反 ——
`A22` 改的是**所有页共用的那一层**（卡片基类），越早落越省事；
而外壳改的是**所有页共用的那一层之外**（导航），越晚落越省事。
**判断依据是「这一改之后，后面的工作是在它上面做，还是在它两侧做」。**

## 十 附：收口 `#11` 时修掉的一个测试错

`tests/http/data.test.ts` 的恢复用例失败：

```
assert.ok(readdirSync(backupDir).some((name) => name.startsWith('pre-restore-')))
```

**是测试写错了，不是代码错了。**
`writePreRestoreSnapshot()` 落在 `join(config.backupDir, 'pre-restore')` ——
即 `backupDir` 下的一个**子目录**里，而断言直接读 `backupDir`，
读到的只有那个子目录本身，名字是 `pre-restore` 而不是 `pre-restore-…`。
改成读 `join(backupDir, 'pre-restore')` 后 **15/15 全过**。

**教训**：同一行里前两句断言（`snapshot.startsWith(backupDir)`、`existsSync`）
都是**跟着被测代码的返回值走**的，所以过了；第三句是**凭印象写目录层级**的，所以错了。
→ **凡是断言里出现「我以为文件在哪」，都要改成从被测代码的返回值推。**
