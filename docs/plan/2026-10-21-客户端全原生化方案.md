## 一、为什么这次不接受「混合 / 折中」

WebView 套壳的代价，在这个项目里已经能看到具体形态，不是理论问题：

1. **WebView 被逼着承担系统级职责**。现在鸿蒙的「静态资源」不是打进去的资源，而是
   `Index.ets` 里手写的一整套虚拟域名 + 拦截器：
   `LOCAL_ORIGIN = 'http://localhost'`（`hw/entry/src/main/ets/pages/Index.ets:17`）、
   `onInterceptRequest` 逐条 `decodeURIComponent` 后从 rawfile 读文件、自己维护 14 种 MIME 表、
   自己实现 SPA 回退（`:284-390`）。**这是一份浏览器内核的活儿**，任何一处漏了就白屏。
2. **两个 owner**。返回键由原生 `onBackPress()` 无条件转发给 `window.__suenmoneyOnNativeBack`（`:257-282`），
   而「有没有未保存草稿」只有 Web 知道（`ExpenseSheet.vue:684-708`）——
   原生要拦要放，必须问 Web；Web 要退出，必须求原生。这类双向依赖每加一个能力就多一条。
3. **两套渲染管线各写一遍**：安全区（`Index.ets:163-190` 注入 `--safe-top/--safe-bottom`）、
   软键盘避让、下拉手势、动效、无障碍 —— 全都得在「WebView 内」与「原生壳」之间对齐。
4. **离线是 Web 的 IndexedDB**（`web/src/utils/idb.ts`，v2，7 个 object store + Outbox），
   它的可用性依赖 `databaseAccess(true)` 这种 WebView 开关（`Index.ets:332`）——
   一个平台级开关决定记账数据能不能离线写。

**结论：要么全原生，要么别做这次迭代。**（这句直接沿用参考实现的判据，不再重新论证。）

## 二、目标架构与四条硬约束

```
                    ┌──────────────────────────────────────┐
                    │  服务端（单一真相源，几乎不改）        │
                    │  Fastify + node:sqlite + /api/*        │
                    │  + 托管 web/dist（计划一）             │
                    └────┬──────────────┬──────────────────┘
             JSON / HTTP │              │ JSON / HTTP
        ┌────────────────▼───┐   ┌──────▼─────────────────┐   ┌────────────────────┐
        │ iOS（SwiftUI）      │   │ 鸿蒙（ArkUI）           │   │ Web（Vue SPA）      │
        │ URLSession + SQLite │   │ http.request + RDB      │   │ 仍为完整客户端       │
        │ Keychain            │   │ preferences             │   │ （PC 唯一入口）      │
        └─────────────────────┘   └─────────────────────────┘   └────────────────────┘
                    ↑ 本地库 + 出站队列；UI 只下发意图
```

1. **服务端是唯一真相源**；客户端不做权威数据、不做时间推算（业务日期仍由客户端按本地时区给出 `YYYY-MM-DD`）。
2. **本地状态机只能有一个 owner（原生）**；界面只下发意图、只展示状态。
3. **客户端 UI 里没有 WebView**。
4. **离线靠「本地库 + 出站队列」**，语义与今天 `idb.ts` + `stores/sync.ts` **逐条对齐**（不是重新设计一套）。

## 三、服务端要改的地方：很少，但不是零

盘点下来记账域的全部端点**都已存在**，两端只要照 `docs/api.md` 实现客户端即可。真正要动的只有：

| # | 改动 | 现状证据 | 为什么 |
|---|---|---|---|
| S-1 | `/api/update/check` 增加平台 `harmony` | `server/src/services/ugreen-update.ts:7` `UpdatePlatform = 'android' \| 'ios'`；`web/src/stores/update.ts:77` 对鸿蒙**静默返回** | 原生化后鸿蒙也要走自己的更新通道，否则「断了 WebView 也断了更新」 |
| S-2 | `/api/health` 返回 `version` | 现在只 `{ok, service}`（`server/src/http/server.ts:79`） | 原生端探活要顺带校验版本与「是不是本产品」，参考实现 `probe` 就校验返回体（防门户劫持） |
| S-3 | **CORS 在 S6 整体移除** | `server/src/http/server.ts:32-49`，`origin` 默认 `cb(null, true)`**全放开** | 原生端（`URLSession` / `http.request`）根本不发 `Origin`，CORS 从来不是给它们的。三端全是原生 + 同源 Web 之后，这层不但无用，还是一个「默认全放开」的敞口 |
| S-4 | 会话令牌语义确认 | `server/src/http/auth.ts`（库内会话 + 令牌哈希 + `sessionDays=180`） | 客户端只需安全存 token（iOS Keychain / 鸿蒙 `preferences`），**不需要** refresh 轮换那套（本项目没有短期 access/refresh 分离） |

> 反过来说：**不要**为了原生化去改任何 endpoint 形状 —— 那会让 Web 端与两套原生端分叉成三份。

## 六、双端技术选型

| 关注点 | iOS | 鸿蒙 |
|---|---|---|
| UI | SwiftUI（`TabView` + `sheet` 半屏） | ArkUI（`Tabs` + `bindSheet`） |
| 网络 | `URLSession` + `async/await` + `Codable` | `@kit.NetworkKit` `http.request` |
| 本地库 | SQLite（`GRDB` 或原生 `sqlite3`，**必须能存 outbox**） | `@kit.ArkData` `relationalStore`（RDB） |
| 小配置 / token | Keychain（token）+ `UserDefaults`（其余） | `preferences`（token 加密存储优先） |
| 图表 | Swift Charts（折线/柱）+ `Canvas`/`Shape` 自绘环图 | `Canvas` 自绘环图；柱/线用 `Polyline`/`Rect` |
| 数字键盘 | 自绘 `Grid` | 自绘 `Grid`（**不要用系统输入法**：金额要固定 5 列布局） |
| 返回/手势 | `NavigationStack` 默认 + 自定义「草稿未保存」确认 | `onBackPress()` + `router` 栈，草稿判定在原生 |
| 平台默认值 | **iOS 26 起步**，不考虑低版本分支 | **`compatibleSdkVersion 26.0.0`**，同上 |

**多服务端选路**：算法照 `web/src/api/client.ts:81-430` 的语义重写（同源优先 → 内网优先 →
4s 首试快速失败 → 单飞重试 → 10s 离线冷却），参考实现两端已有同构实现可直接对照
（iOS `ServerRouter`、鸿蒙 `APIClient.probe/failoverIfNeeded`）。

## 七、离线契约（本计划最大的工作量，必须单独定死）

现状在 Web 里已经是一套完整机制，两端**照抄语义**而不是重新发明：

| 机制 | Web 现状 | 两端要求 |
|---|---|---|
| 本地表 | `idb.ts` v2：`meta / categories / payment_methods / expenses / plans / plan_todos / outbox`（`web/src/utils/idb.ts:80-113`） | 原生库建同名表（列名保持 `snake_case`，与同步快照一致） |
| 出站队列 | `outbox` 8 种动作：`create/update/delete_expense`、`confirm/skip/ack/revert/restore_todo`（`:17-33`） | 同 8 种，字段同构 |
| 重试 | `OUTBOX_MAX_RETRY=3`、退避 5s/10s/30s（`stores/sync.ts:40,114`） | 一致 |
| 死信 | `getOutboxDeadLetters`（`idb.ts:564`），界面暴露 `deadLetters`（`sync.ts:98`） | 一致（不许静默丢弃） |
| 拉取 | `GET /api/sync/pull?since&limit` + 本地游标 | 一致 |
| 推送 | `POST /api/sync/push`（`server/src/http/sync.ts:54`） | 一致 |
| 冲突 | **只能改自己创建的记录**（这是权限，也是离线冲突的消解机制） | 一致 |
| 触发时机 | 本地变更 300ms 防抖、前台恢复、网络恢复（`stores/sync.ts:148-193`） | 一致 |

**分两档落地，避免一次吃成胖子**：

- **A 档（必须，S1/S3 门禁内）**：**离线可读** —— 列表/概况/报表在断网时用本地库现算（对应 `offline-stats.ts`）。
- **B 档（S2/S4 内）**：**离线可写** —— Outbox 全动作 + 补偿同步 + 死信界面。

> 判据：**A 档不过，B 档不开工。** 因为没有 A 的离线写只会让「用户以为记上了，其实队列坏了」更难发现。

| # | 风险 | 对策 |
