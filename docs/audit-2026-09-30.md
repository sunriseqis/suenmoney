## 一、业务逻辑与账务领域深度审查

### 1.1 记账与账务核心领域逻辑

#### 🚨 缺陷 1：`parseYuanToCents` 解析负数与角分失真
- **定位**：`web/src/utils/money.ts:62-71`
- **代码分析**：
  ```typescript
  export function parseYuanToCents(input: string): number {
    if (input === '' || input === '.') return 0;
    const [intPart = '0', decPart = ''] = input.split('.');
    const yuan = Number(intPart === '' ? '0' : intPart);
    const fen = Number((decPart + '00').slice(0, 2));
    if (!Number.isFinite(yuan) || !Number.isFinite(fen)) return 0;
    return yuan * 100 + fen;
  }
  ```
- **风险危害**：
  1. 输入负数金额（如账单导入/退款冲销 `"-15.50"`）：`yuan = -15`，`fen = 50`，`-15 * 100 + 50 = -1450` 分（实际应为 `-1550`），直接少记 1 元钱；
  2. 输入小于 1 元的负数（如 `"-0.50"`）：`Number("-0") === 0`，`0 + 50 = 50` 分，**负数直接翻转为正数**。
- **改进方案**：
  ```typescript
  export function parseYuanToCents(input: string): number {
    const trimmed = input.trim();
    if (trimmed === '' || trimmed === '.' || trimmed === '-.') return 0;
    const isNegative = trimmed.startsWith('-');
    const clean = isNegative ? trimmed.slice(1) : trimmed;
    const [intPart = '0', decPart = ''] = clean.split('.');
    const yuan = Number(intPart === '' ? '0' : intPart);
    const fen = Number((decPart + '00').slice(0, 2));
    if (!Number.isFinite(yuan) || !Number.isFinite(fen)) return 0;
    const total = yuan * 100 + fen;
    return isNegative ? -total : total;
  }
  ```

#### 🚨 缺陷 2：LPR 调息重算误删跳过历史，致使期序与时间轴倒流
- **定位**：`server/src/db/repo/plans.ts:753-759` 对比 `plans.ts:481-487`
- **代码追踪**：
  `updatePlan` 中先调用 `deletePendingTodos`（执行 `DELETE ... WHERE status IN ('pending', 'skipped')`），接着调用 `lastExecutedSeq`（查询 `MAX(period_seq) WHERE status IN ('confirmed', 'skipped')`）。
- **风险危害**：
  因为 `skipped` 期次已被提前硬删除，`lastExecutedSeq` 只能查到最后的 `confirmed` 期次。若用户第 1 期已还、第 2 期因银行宽限期显式选择“跳过”，调息后第 2 期被删除，系统把调息后的期序从第 2 期重新开始生成，**用户主动跳过的记录被彻底抹除，时间线发生严重倒流回缩**。
- **改进方案**：
  重构 `deletePendingTodos`，使其**仅删除 `status = 'pending'`**，严格保留 `skipped` 历史记录；或在删除待办前先计算 `lastExecutedSeq`。

#### ⚠️ 缺陷 3：报表「单笔最高支出」将纯退款月份错当最大支出
- **定位**：`server/src/db/repo/reports.ts:313-339`
- **代码追踪**：
  SQL 查询：`SELECT ... FROM expenses ... ORDER BY e.amount_cents DESC, e.id LIMIT 1` 缺少 `AND e.amount_cents > 0`。
- **风险危害**：若当月没有正向消费，仅有退款（如 -50 元与 -200 元），SQLite 将返回 `-50`，并在月报大卡片展示「本月最大一笔支出 -¥50.00」，违背统计常理。
- **改进方案**：在 `largestExpense` 的 WHERE 条件中强制追加 `AND e.amount_cents > 0`。

#### ⚠️ 缺陷 4：分类退款导致负净额时 SVG Donut 环图崩溃
- **定位**：`server/src/db/repo/reports.ts:234` 与 `web/src/utils/donut.ts:48-52`
- **风险危害**：某分类当月退款大于支出时净额为负，服务端计算出负比例 `ratio`。前端 `buildDonutArcs` 算出 `percent < 0`，导致 SVG `stroke-dasharray` 接收负数参数，破坏 SVG 语法引起图形错位。
- **改进方案**：在报表聚合计算分类占比时，对净额 ≤ 0 的分类进行过滤或统一归入冲销抵扣项，环图仅渲染正向净支出构成。

#### ⚠️ 缺陷 5：逆向账单推导 `resolvePostingDate` 小月边界倒退一个月
- **定位**：`server/src/domain/billing-cycle.ts:191-201`
- **代码追踪**：
  若信用卡设为同月还款（如 `billingDay = 28, repaymentDay = 29`）。平年 2 月还款日被钳制为 `2023-02-28`。当通过还款日反向推导入账日时，`repay.day > billingDay`（28 > 28）为 false，导致函数误调用 `shiftMonth(2023, 2, -1)`，将账单日倒退到 1 月 28 日。
- **改进方案**：`resolvePostingDate` 应引入 `cycle.repaymentDay` 作为比较判据，而不是用被月末天数 clamp 后的实际日期进行大小比较。

### 1.2 离线优先与增量同步引擎

#### 🚨 缺陷 1：离线批量推送“毒丸（Poison Pill）”永久锁死 Outbox 队列
- **定位**：`server/src/db/repo/sync.ts:154-158` 与 `web/src/stores/sync.ts:461-465`
- **代码追踪**：
  在 `pushChanges` 事务中，修改、删除与待办确认均有单个 `try/catch` 容错，唯独 `batchCreateExpenses` 是裸调用。若离线新增的一笔支出因分类或支付方式在云端已被失效而抛出 400，会导致整个请求失败。前端捕获异常后无法执行 `removeOutboxItems`，且缺少死信重试计数剔除，导致该无效项永久阻塞 Outbox，后续所有离线操作再也无法同步上云。
- **改进方案**：
  1. 服务端对批量新增支出改为逐条校验入库，并回传成功与失败的 ID 映射；
  2. 前端 Outbox 针对单项递增 `retryCount`，超过 3 次自动移入死信隔离队列并向用户提示。

#### ⚠️ 缺陷 2：待办操作离线闭环不对称
- **定位**：`web/src/stores/plans.ts:121-216`
- **代码追踪**：`confirmTodo`、`skipTodo`、`ackTodo` 均有完善的离线降级支持，但 `revertTodo`（撤销确认）与 `restoreTodo`（恢复跳过）完全没有离线分支，断网点击直接抛红字网络错误。
- **改进方案**：在 `revertTodo` 与 `restoreTodo` 中补齐离线分支，写入 Outbox（`action: 'revert_todo'` / `'restore_todo'`）并同步乐观更新本地 IndexedDB 待办状态。

### 1.3 功能完整度与日常高频痛点

#### ⚠️ 缺陷 1：流水搜索虚假承诺与月份锁定
- **定位**：`web/src/views/LedgerView.vue:811-877` 与 `server/src/db/repo/expenses.ts:289-294`
- **现象**：
  1. 前端输入框提示“搜索分类或备注…”，但后端 SQL 仅执行了 `e.note LIKE ?`，根本不搜分类名称；
  2. 前端搜索栏写死 `v-if="scope === 'month'"`，在年档和全部流水下搜索栏直接消失，家庭查往年历史账目（如“去年买手机花了多少”）的日常高频需求被完全阻断。
- **改进方案**：后端模糊搜索补齐 `OR c.name LIKE ?`；前端解除仅限单月的限制，支持全局搜索。

#### ⚠️ 缺陷 2：分类删除缺乏对进行中计划（Plans）的级联拦截
- **定位**：`server/src/db/repo/categories.ts:451`
- **现象**：删除分类仅检查了 `expenses` 和子分类，漏掉了 `plans` 表。删除关联了计划的分类后，该计划后续到期自动入账时会触发 `requireUsableCategory` 报错，导致计划待办永久卡死。
- **改进方案**：增加 `(SELECT COUNT(*) FROM plans WHERE category_id = ? AND deleted_at IS NULL)` 检查。

## 二、代码质量、性能与架构解耦审查

### 2.1 服务端并发、索引与资源管理

#### 🚨 缺陷 1：`expenses` 表核心字段 `spend_date` 索引缺失，流水列表默认全表扫描
- **定位**：`server/src/db/migrations/001_init.sql:267-277` 与 `server/src/db/repo/expenses.ts:259-261`
- **分析**：流水核心查询 `listExpenses` 的默认排序是 `ORDER BY e.spend_date DESC, e.id DESC`。数据库仅建了 `repayment_date` 索引，未对 `spend_date` 建立任何索引。随着记账量累积，每一次进入流水页都会触发 SQLite 全表扫描 + 内存/磁盘临时文件排序（Filesort）。
- **改进方案**：建立复合索引：
  ```sql
  CREATE INDEX IF NOT EXISTS ix_expenses_spend_date ON expenses (spend_date DESC, id DESC) WHERE deleted_at IS NULL;
  ```

#### 🚨 缺陷 2：优雅停机未关闭数据库连接与 WAL 归并
- **定位**：`server/src/index.ts:43-50` 与 `server/src/db/index.ts:44-51`
- **分析**：`index.ts` 捕获 `SIGTERM` 信号后，仅调用了调度器停止与 `app.close()`，在 `db/index.ts` 中定义的 `closeDatabase()` 从未被调用，也未执行 `PRAGMA wal_checkpoint(TRUNCATE)`。容器停止完全依赖 `process.exit(0)`，导致退出时 WAL 日志未能平滑归并回主库文件，每次容器重启必须依赖 SQLite 崩溃恢复。
- **改进方案**：停机钩子中显式调用 `db.exec('PRAGMA wal_checkpoint(TRUNCATE)')` 与 `closeDatabase()`，并为停机流程设置 10 秒超时强制退出保护。

#### ⚠️ 缺陷 3：WebDAV 备份全量加载到 Buffer 存在 OOM 风险
- **定位**：`server/src/db/repo/webdav.ts:213`
- **分析**：`readFileSync` 将整个 SQLite 数据库读入单个 Buffer 内存块，在 256MB~512MB RAM 的低配 VPS 或 NAS 容器中极易引发 OOM 崩溃；且所有 WebDAV 请求均缺少 `AbortSignal` 超时机制，网络僵死会导致连接永久挂起。
- **改进方案**：引入 `AbortSignal.timeout(30000)` 控制单次超时；改用流式上传或分块传输。

### 2.2 前端性能与响应式

#### ⚠️ 缺陷 1：`LedgerView.vue` 桌面表格与移动端列表双份 DOM 并行渲染
- **定位**：`web/src/views/LedgerView.vue:995-1063` 与 `1065-1150`
- **分析**：桌面 `table` 与移动端 `ul` 均常驻 DOM，仅靠 CSS `hidden lg:table` 与 `lg:hidden` 控制显隐。单页 200 条数据时，DOM 树同时存在 400 个行元素，并重复实例化 800 个 `CategoryIcon` 与 `PaymentIcon` 子组件，拖慢渲染速度与滚动流畅度。
- **改进方案**：使用 `v-if` 结合响应式断点控制单一树渲染，消除无意义的组件重复实例。

#### ⚠️ 缺陷 2：`platform/env.ts` 存在 `@capacitor/app` 静态动态导入残留
- **定位**：`web/src/platform/env.ts:25`
- **分析**：`const mod = await import('@capacitor/app')` 仍会被 Vite/Rollup 构建时静态分析。
- **改进方案**：改用全局运行时对象读取：`window.Capacitor?.Plugins?.['App']`，实现 Web 构建期彻底零原生依赖。

### 2.3 工程化与 CI/CD 优化

#### ⚠️ 缺陷 1：Web Dockerfile 交叉构建缺失 `--platform=$BUILDPLATFORM`
- **定位**：`web/Dockerfile:8`
- **分析**：`FROM node:22-alpine AS builder` 在交叉构建 `linux/arm64` 镜像时，通过 QEMU 慢速模拟运行 `npm ci` 与 `vite build`，构建耗时从 30 秒暴增至 8~10 分钟。静态资源编译本身架构无关，完全应在构建机原生架构运行。
- **改进方案**：Stage 1 改为 `FROM --platform=$BUILDPLATFORM node:22-alpine AS builder`。

#### ⚠️ 缺陷 2：移动端 CI 触发条件过宽（昂贵的 macOS 10x 计费浪费）
- **定位**：`.github/workflows/build-ios.yml:8-12`
- **分析**：`paths` 包含了 `'web/**'`，日常 Web 前端代码推送会自动触发昂贵的 `macos-15` runner（扣除 10 倍 GitHub Actions 分钟额度）。
- **改进方案**：移动端构建限制为 Tag 触发（`refs/tags/v*`）或手动派发（`workflow_dispatch`），或仅在 `ios/**` / `android/**` / `VERSION` 变更时触发。

## 三、UI/UX、交互体验与移动端适配审查

### 3.1 移动端核心操作冲突

#### 🚨 缺陷 1：记账抽屉“双重键盘踩踏”与遮挡
- **定位**：`web/src/components/ExpenseSheet.vue` 与 `NumericKeypad.vue`
- **现象**：用户点击“备注说明”输入框时，系统弹起原生输入法键盘，但底部的 5 列自建数字键盘依然顽固占着 220px 空间，导致整个视口被严重挤压变形，输入框和金额被顶出屏幕，用户只能在看不清内容的情况下盲打。
- **改进方案**：监听备注框的 `focus` 与 `blur`，当原生键盘唤起时自动平滑隐藏数字键盘，将“保存”按钮临时挂在原生键盘上方的快捷 Accessory Bar 中；收起原生键盘后恢复数字键盘。

#### 🚨 缺陷 2：数字键盘底部缺失安全区（全面屏手势冲突）
- **定位**：`web/src/components/NumericKeypad.vue`
- **现象**：键盘底行的 `.`, `0`, `00` 以及两行高的“保存”按钮完全贴在屏幕物理底边缘（缺少 `--safe-bottom` 内边距）。在 iPhone（Home 条）及 Android 全面屏手势机型上，点击 `0` 或“保存”与系统“返回桌面/切换应用”手势区 100% 冲突，频繁引发误退桌面。
- **改进方案**：为 `NumericKeypad.vue` 外层容器补充底部安全边距：`pb-[calc(var(--safe-bottom)+6px)]`。

#### 🚨 缺陷 3：顶部下拉记账手势越界与阈值生硬
- **定位**：`web/src/App.vue:45-139`
- **现象**：手势挂在全局 `window` 上，在“报表”、“设置”等二级页面顶部下拉也会误唤出记账；且由于 `0.44` 的阻尼乘数，实际需要手指在屏幕物理滑动 `48 / 0.44 ≈ 109px` 才能触发，手感生硬沉重。
- **改进方案**：手势限制仅在 `route.name === 'ledger'` 触发；将阈值调整为手指实际位移 ~60px 触发。

### 3.2 触摸热区与视觉可访问性

#### ⚠️ 缺陷 1：全局弹层关闭键触摸热区违规（严重低于 44×44px）
- **定位**：`ExpenseSheet.vue:843`、`CategoryPickerSheet.vue:93` 等
- **现象**：关闭键尺寸仅 `h-7 w-7`（28×28px），在手机端单手盲操作极难点中，误触率高。
- **改进方案**：尺寸放大至 `h-10 w-10`（40px），并通过透明外延伪元素保证不低于 44×44px 的标准拇指操作区。

#### ⚠️ 缺陷 2：移动端离线状态完全处于“视觉盲区”
- **定位**：`web/src/App.vue:258`
- **现象**：同步状态指示器只放在了 `<header class="hidden lg:block">` 内部，在移动端（`<1024px`）整个头部被隐藏，导致移动端用户在离线记账或等待同步时没有任何状态感知。
- **改进方案**：在移动端顶栏或顶部通知区中，当离线或存在未发队列时，展示轻量状态圆点与胶囊提示。
