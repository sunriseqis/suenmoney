# 路线图与进度

## 推进顺序

先跑通前后端 + Web，验证无误后再做 Docker 部署优化，然后交叉编译到移动端，
最后做离线同步与 iOS。

**离线排在移动端阶段**，因为它是移动端特有的需求（Web 端总在线，且承担管理后台职责）。
但**离线的数据模型约束必须在阶段一就写进 schema**（ULID 主键、软删除、
`rev` / `device_id`、`changes` 表）—— 这些如果等移动端再补，等于给所有表做一次
破坏性迁移。所以阶段一零额外成本，移动端阶段只是补实现。

**浏览器端到端**（Playwright + Firefox，走 Vite 代理 = 真实路径）：

- 切换到信用卡 → 提示由「还款日 9月27日」变为醒目的
  「**这笔会记在 2026 年 10 月（还款日 10月28日）**」
- 保存后：10 月报表显示 `¥32 / 共 1 笔`，分类构成把二级「外卖」正确归并到一级「餐饮」，
  按支付方式那行带出「10月28日 还款」；10 月流水「已加载 1 笔 · 合计 ¥32.00」

  并能通过界面新建信用卡（选「信用卡」后才出现账单日与还款日输入框）

### 本轮验证中修掉的问题

1. **默认支付方式被排成了信用卡**（SQLite 的 BINARY 排序把「招」排在「现」前），
   导致随手记的一笔跨月，看起来像没记上 → 改排序 + 加 `rowid` 兜底
2. **抽屉不说明这笔落在哪个月** → 新增 `/api/expenses/preview` 与醒目提示
3. **全新安装没有任何支付方式**，记账流程走不通 → `db:init` 播种「现金」
4. **空状态文案指向错误的「右下角」** → 改为「下方」
5. 记账抽屉没有实现「默认沿用上次选择」 → 用 `localStorage` 补上

## 浏览器验证怎么做

需要 Playwright 自己的浏览器构建（**原版 Firefox 不支持它依赖的 juggler 协议**，
所以系统装了 Firefox 也仍然要下载）。

```bash
# 国内网络用镜像（PLAYWRIGHT_DOWNLOAD_HOST）
PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright \
  playwright-cli install-browser firefox

# 在仓库外的目录运行，避免 .playwright-cli/ 污染仓库
cd /tmp && playwright-cli open --browser=firefox http://127.0.0.1:5310/
```

浏览器缓存在 `~/Library/Caches/ms-playwright/`（工具缓存，不是记忆目录）。

## 界面返工 ✅（插在阶段二之后）

起因：第一版界面做完后实际看着"太难看了"。查下来主因不是设计方向，是几个实现缺失。

| 问题 | 性质 | 处理 |
|---|---|---|
| 全站按钮/输入框的工具类全失效 | **真 bug**：`base.css` 未分层，压过了 Tailwind 的 `utilities` 层 | 重置进 `@layer base`，可复用类进 `@layer components`。详见 `docs/design/flat-design.md` 第十节 |
| 中文一直是系统苹方 | **真 bug**：字体栈写了 `MiSans VF`，但 `main.ts` 里从没引入过 | 接入 `misans` npm 包 |
| `@fontsource/outfit` 未在 `package.json` 声明 | **真 bug**：干净环境 `npm ci` 会构建失败 | 统一改用 `@fontsource-variable/outfit` |
| 五张满宽琥珀卡片 | 设计：饱和色面积不随待办数量伸缩 | 改为中性卡 + 4px 色条 + 状态文字着色 |
| 全站零图标 | 设计：没有任何视觉锚点 | `@lucide/vue` + 分类图标登记表 + 图标选择器 |
| 桌面就是手机界面居中 | 设计：没为「Web 偏管理后台」补桌面布局 | ≥1024px 顶部导航 + 1120px 内容 + 各页双栏 |

**验证**：`npm test` 193 项（163 + 30）+ schema 22 项全过，`typecheck` 干净，`build` 通过；
手机（390×844）与桌面（1440×900）两侧逐页截图核对，控制台 0 错误。

**新增的开发工具**：`npm --prefix server run seed:demo` —— 往一个**独立**的库写入
49 笔支出 + 3 个计划 + 36 期待办，用来在真实数据密度下评审界面。
空库或者只有一两笔数据时，流水、报表、进度条全是空壳，判断不出排版是否成立。
