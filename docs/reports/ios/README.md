**8 屏 / 603 条差异 / 124 个 blocker。**

差 1px、差一档字号、颜色令牌不同、少一个状态分支，全部记录。

## 问题性质分四类（不是按屏，按根因）

### A. 颜色/令牌解析错误 —— 一眼看出不是同一个 App

| 问题 | 说明 |
|---|---|
| `#0F00FF88` 被当 `#RRGGBBAA` | ArkUI 的 8 位色是 **#AARRGGBB**。鸿蒙意图是 `rgba(0,255,136,0.06)`（极淡绿雾），iOS 解析成 `rgb(15,0,255)@53%`（蓝紫罩）。cyber 顶卡整张走样 |
| 分类色哈希基数不同 | 鸿蒙 `% 1000003`，iOS `% 100000`。30 个常见分类名里 **10 个落到不同色槽**（餐饮 12→15、购物 10→13、药品 16→3…）。同一账本两端颜色大面积不一致 |
| 全仓没有 `.tint()` | 弹层保存/取消/删除、Menu 项、分段 Picker 全部用 iOS 系统蓝 `#007AFF` / 系统红 `#FF3B30`，与 candy 紫 `#8B5CF6` / cyber 绿 `#00ff88` 完全脱节 |
| cyber 下多处描边用错令牌 | 用 `tokens.line2(#2a2a3a)` 代替鸿蒙的 `outlineStrongOf(#6f6f92)`，控件边界几乎消失 |

### B. 结构性差异 —— 不是像素差，是「不是同一个页面」

| 屏 | 鸿蒙 | iOS |
|---|---|---|
| 概况页 | 待办块有合计金额、逾期笔数、自动/需手动徽标、每期金额、确认/入账按钮、更多→忽略 | 只剩一行「N 笔待处理」+ 紧急度文字，**动作闭环完全缺失** |
| 报表页 | 构成区是「环图 / 条形榜 / 星期柱」**三形态切换** + 图例整宽虚线行 | 压成「固定环图 + 右侧 5 行小图例」左右两栏；缺「节奏」维度、dimBars、前 7+其他聚合 |
| 记账抽屉 | 金额**右对齐 34pt** + 三段式账期提示 + **5 列键盘**（左支付列 + 4 列数字，保存键跨两行） | 金额**左对齐 40pt Heavy** + 信用卡专属单行 + **4 列键盘**（C/B/保存塞进左列） |
| 设置页 | 分类/支付完整表单（图标、颜色、账单日、还款日、合并） | 只实现约 **40%**；「新建计划」是一句「请在 Web 端操作」的占位 toast |

### C. 数据正确性缺陷 —— 会真的出错

| 问题 | 后果 |
|---|---|
| `MonthPoint.count` 非可选 | 服务端 `peakMonth` 只有 `{month,totalCents}` → 整个 YearlyReport 解码失败 → **年报整屏空白**（已修） |
| 编辑分类/支付清空 icon 与 color | iOS 的 `submitForm` 传 `icon: ""`、`color: ""`，且 `isEnabled: true` → **用户一编辑就丢配置** |
| 「检查更新」不发请求 | 直接 `updateMsg = "已是最新版本"`，谎报 |
| 入账不看 `willAutoPost` | 一律走 `confirmTodo`；鸿蒙对自动入账型走 `ackTodo`（只摘提醒，到期仍入账） |
| 快捷分类取错层级 | 鸿蒙按 `expenseCount` 取**二级**前 5，iOS 取**一级**前 5 |
| `categories.contains` 只比一级 | 编辑旧账时二级分类被静默重置成一级 → 存成错账 |
| 无 NavigationStack、`goBack()` 全仓无调用点 | 进二级页后**没有任何返回途径** |
| 删除无二次确认 | 鸿蒙有确认弹窗 |

### D. 视觉参数系统性偏移

- 大金额字号：hw `38/30/24` vs ios `34/28/22`，且 iOS 把 `¥` 算进长度导致提前降档
- 年格月份：hw `15pt 标题体` vs ios `10.5pt 等宽灰字`（年档视觉重心完全变了）
- 三事实：hw 左对齐 vs ios 居中；hw 虚线 vs ios 实线（底层 fill 把虚线间隙填满）
- 胶囊圆角：hw `rPill(999)` vs ios `rSm(9)`
- orb 圆图标：hw `34×34 纯色底+深色图标+阴影` vs ios `26×26 淡色底+彩色图标`
- 进度条高度：hw `5` vs ios `3`
- 搜索框高度：hw `40` vs ios `34`
- 大量 0.5–2pt 偏差（字号、间距、字重）

## 修复顺序建议

1. **A 类**（颜色解析、哈希基数、tint）—— 改动小、收益最大，先做
2. **C 类**（数据破坏、解码、返回途径）—— 功能性硬伤
3. **B 类**（结构差异）—— 工作量大，需要逐屏重做
4. **D 类**（参数偏移）—— 可批量脚本化
