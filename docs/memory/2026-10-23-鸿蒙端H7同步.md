| 文件 | 作用 |

## 二、四个关键决定

1. **八种动作分八组提交**，而不是逐条 POST
   服务端 `/api/sync/push` 一次事务落库；逐条提交在网络抖动时会出现
   「这三笔进了、那两笔没进」，用户无法判断该怎么补。

2. **离线记账不做乐观行**
   本地算不出还款日（账单周期那段逻辑只在服务端，这是 decisions 里刻意避免
   两份实现的点）。硬造一行会让「这个月合计」先对后错。
   所以只入队 + 告诉用户「已存入待发送队列，联网后自动记入」。

3. **网络错误不消耗重试次数**
   网络不可达是环境问题，不是请求有问题；整批原样留着下次一起发。
   只有 4xx/5xx 才 `retry_count + 1`，到 3 次进死信。

4. **死信必须可见**
   `retry_count >= 3` 的条目在设置「数据」区列出来，显示动作与失败原因，
   并给「全部重试」。静默丢弃是最坏的结果：用户以为记上了。

## 三、游标与冲突

- 游标存 `meta.sync_cursor`，只认服务端单调递增的 `latestVersion`，**绝不用时间戳**
  （decisions：时间戳在多设备下会漏变更）
- 冲突消解沿用「只能改自己创建的记录」——这是权限规则，也是离线冲突的出口；
  拉取时服务端已按记录级 LWW 算好，客户端只负责覆盖本地副本
