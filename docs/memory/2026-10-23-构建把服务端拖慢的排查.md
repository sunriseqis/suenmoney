# 2026-10-23 「服务端被关掉了？」——不是关掉，是被构建拖慢

## 现象

用户问「服务端被关掉了？」，看起来像 5310 打不开。

## 排查

| 检查 | 结果 |
|---|---|
| `systemctl is-active suenmoney` | **active**（自 2026-10-22 13:09 起未重启） |
| `curl /api/health` | 200，2ms |
| `ss -lntp` | 0.0.0.0:5310 正常监听（pid 619876） |
| 局域网 IP 访问 | `http://192.168.89.10:5310/` 200、`/api/health` 200 |
| 防火墙 | 无 ufw、无拦截规则 |
| `web/dist/index.html` | 在位（1398 字节） |

**服务端一直是好的。**

## 真因：hvigor 守护进程把 2GB 内存吃满

```
free -h         → used 1.4Gi / 2.0Gi，available 605Mi
uptime          → load average: 2.31, 4.08, 4.01
pgrep -fa hvigor → 4 个 node 守护进程（--max-old-space-size=8192）
                 + 1 个 java 守护进程（hvigor-java-daemon.jar）
```

`devecocli build` 默认开守护进程，**构建结束后不退出**。本机只有 **2GB 内存**，
4 个 8GB 堆上限的 node 进程 + 一个 JVM 留在后台，机器进入持续换页状态，
同机的 Web 服务响应变慢甚至超时 —— 用户看到的就是「服务端没了」。

## 处置

1. 立即：`pkill -f "hvigor/src/base/daemon/process"`、`pkill -f hvigor-java-daemon.jar`
   → 内存从 used 1.4Gi 回到 **753Mi**，available 1.3Gi
2. 根治：`hw-native/hvigor/hvigor-config.json5` 里 `"daemon": false`（已提交）
3. 习惯：构建用 `nice -n 19`，构建后 `pgrep -fa hvigor` 复查；日常改代码优先
   `devecocli check arkts`（秒级），只在需要产物时跑全量构建

## 教训

**小内存机器上跑重型工具链，必须管住后台进程。** 这次不是服务端的问题，
但用户感知就是「服务挂了」—— 以后每次构建完都顺手复查一次守护进程，
并且把这条写进项目 README/记忆，避免下次再问一遍。
