# 单向同步：拉取游标跳跃导致另一端的记录永久不出现（2026-11-19，v2.1.1）

用户报障原话：**「iOS 端（用户账号）看不到鸿蒙端（管理员）记录的数据，但鸿蒙端能看到 iOS 的。」**

不是权限问题。服务端流水读取是**读全开放**的（`server/src/http/expenses.ts:33` 明写「读全开放，写仅限创建者」），
`/api/sync/pull` 也不按 actor / 角色过滤。表象是「只上不下」，根因在**客户端拉取的游标**。

## 一、根因：把 `latestVersion` 当成了下一页的 `since`

`GET /api/sync/pull` 的响应里有两个版本号，语义完全不同：

| 字段 | 含义 |
|---|---|
| `latestVersion` | 服务端**全局最新版本**（`sync_sequence` 当前值） |
| 本页最后一条 `changes[n-1].version` | **本页真正发给你到哪儿了** |

一页取不完（`limit=200` 但有 250 条积压）时，两者相差 50。iOS / 鸿蒙两端写的是：

```swift
try writeCursor(body.latestVersion)          // ← 错
return PullResult(..., hasMore: body.hasMore)
```

于是每轮同步只消费**第一页**，游标直接跳到最新：

```
第 1 页 v1..v200 → 游标写成 latestVersion(=250)
第 2 页 since=250 → 空 → hasMore=false → 收工
v201..v250 永久丢失
```

更糟的是两端 `refresh()` 里都写了一个「翻页到 hasMore=false」的循环 —— 它被自己上一行的
游标跳跃**废掉了**：第二轮 `since` 已经是 latest，返回 0 条直接 break。注释写着
「否则一次启动只同步 200 条」，实际行为就还是 200 条。`syncNow()` 连循环都没有，只拉一页。

**Web 端一直是正确的**：`web/src/stores/sync.ts:723-781` 用
`currentVer = Math.max(currentVer, change.version)` 递进并循环。三端里只有两个原生端写错。

## 二、为什么表现为「单向」

落后的一端丢，领先的一端不丢：

- iOS 记的账 → push 到服务端 → 鸿蒙 pull 到（**鸿蒙看得见 iOS**）；
- 鸿蒙/后台记的账 → 服务端有 → iOS pull 时被游标跳过（**iOS 看得见才怪**）。

哪一端落后取决于使用频率。iOS 侧触发点少（冷启动 / 流水页 appear / 前台切回），
只要这段时间积压 >200 条变更（分期批量入账、批量导入、长时间没打开），就整块丢。

另有一条**首装即残**的路径更贴近本次报障（新 iOS 包 2.1.0 首次真编译发布，用户刚装上）：

`pull()` 里「本地空 → 走快照」的分支要求 `outbox` 也为空。用户装完先记了一笔（离线优先，
本地立即入账、入队），此时 `pendingCount>0` → 跳过快照 → 退回 `since=0` 重放历史
→ 只消费前 200 条（**最老的那批**）→ 游标跳到 latest → 最近的记录全缺。

## 三、复现（真服务端 + 真 pull 算法，不是脑补）

脚本 `node --experimental-strip-types` 拉起真 `buildServer()`，临时库，按 iOS 的算法驱动：

```
[首装快照] 快照版本=24  服务端支出=20  本地=20          ← 快照本身是好的
[iOS refresh() 翻页循环]
  第1轮: 本页 200 条 (version 25..224)  latest=274  hasMore=true
  第2轮: 本页 0 条                     latest=274  hasMore=false
服务端 270 笔；iOS 本地 220 笔；永久丢失 50 笔           ← 静默、无报错
```

首装变体（outbox 有 1 笔未推、服务端 300 笔历史）：

```
第1轮: 200 条 (v1..200) latest=304 hasMore=true
第2轮: 0 条             latest=304 hasMore=false
服务端 300 笔；iPhone 只看到 196 笔；永久丢失 104 笔
```

修完再跑同一脚本：`第1轮 200 条 nextSince=200` → `第2轮 104 条 nextSince=304 hasMore=false`
→ **300/300，零丢失**。

## 四、修法

1. **服务端给出唯一口径**：`pullChanges()` 新增 `nextSince` = 本页最后一条变更的版本
   （本页为空时 = `latestVersion`）。客户端**不再自己推导**游标 —— 这个坑两端各踩一次，
   就因为口径散落在三份客户端代码里。
2. **iOS / 鸿蒙**：游标取 `nextSince`（老服务端不返回时退化为「本页最后一条的 version」）；
   抽出 `pullAll()`（翻页到 `hasMore=false` 或本页为空），`syncNow()` 和 `refresh()` 共用 ——
   以前只有 `refresh()` 有循环，两条路径行为不一致。
3. **一次性自愈**：光修游标救不回已经丢掉的记录。两端加 `sync_resnapshot_v2` 标记，
   升级后第一次同步**强制重走一次全量快照**补齐。两个前置条件是必须的：
   - `outbox` 为空才做（快照是「先清后灌」，否则会冲掉没推上去的本地账）；
   - 快照失败**只试一次**并立刻留标记（服务端还是老版本时不能把日常同步卡死）。
4. **顺带修的**：iOS 的 `ExpenseDao.cache()` 在快照落地时漏写
   `plan_id` / `plan_period_seq` —— 计划生成的记录重灌后会丢掉「哪一期」的关联，
   流水行的「京东分期 · 3期」集体消失。鸿蒙的 `SyncStore` 本来就写了这两列。
   （不修这个，第 3 条的强制重灌反而会**弄坏**现有用户的计划标记。）

## 五、验证

- 新增 3 条契约测试（`server/tests/http/sync.test.ts`「增量游标 nextSince」）：
  `nextSince == 本页最后一条`、`hasMore=true 时 nextSince < latestVersion`、
  **250 条变更按 nextSince 翻页零丢失（断言恰好 2 页）**。
- `npm test`：284 passed / 0 failed；`tsc --noEmit` 干净。
- Swift 侧 `swiftc -parse` 通过（Linux 上无法连 SwiftUI SDK 做完整类型检查，真编译走 `build-ios`）。
- ArkTS 侧本地没有 DevEco SDK（`@ohos/hvigor-cli` 拉不到），**必须由 `build-hw` 流水线编译验证**。

## 六、对外恢复动作

升级到 2.1.1 后第一次同步会自动做全量补偿，无需用户操作。
若用户暂时不升级 App，在 iOS 设置页「退出登录 → 重新登录」也能达到同一效果
（登出会清本地业务表并把 `sync_cursor` 归零，登录后命中「本地空 → 快照」）。
