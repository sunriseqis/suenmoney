# 死信可见性 & 毒丸推送（2026-11-04，上机实测发现 3 个 bug）

本轮起因：「离线数据优先」改造完成后，还剩两条路径没上机验过 —— 死信 UI、设置页订阅刷新。
为了制造死信，必须先制造一笔**服务端一定会拒绝**的新增（毒丸），过程中挖出三个真问题。

## 一、服务端对新增是「逐条容错」，客户端却按整批成败处理 → 静默丢账

`POST /api/sync/push` 的设计是：单条坏数据（引用了已停用/已删除的分类或支付方式）
**不返回 4xx**，而是在 200 的响应体里回传 `failedExpenseIndexes: [下标]`，
让其余条目照常入库（避免毒丸把整批回滚）。

- Web 端正确分流（`web/src/stores/sync.ts:680` 一带：成功项出队、被拒项留在 Outbox 累计重试）。
- 鸿蒙 / iOS 端**只看 HTTP 200**，`await Api.syncPush(req)` 之后直接 `Outbox.remove(全部)`。

后果：服务端没有这笔，本地却有，队列已清 —— 用户以为同步完了，其实账只存在于这台机器上。
这正是 Outbox 注释里写「静默丢弃是最坏的」那种情况，只不过丢在服务端侧。

修法（两端同构）：
- `SyncPushBody` 增加 `failedExpenseIndexes?: number[]`；
- `push()` 里维护 `createEntries`（与 `req.expenses` 同序）→ 按回传下标分流：
  被拒项 `markFailed('服务端拒绝该笔新增')` 并留在队列，`retryCount+1 >= 3` 计入死信；
  其余动作（修改/删除/待办）服务端逐条容错接收，与 Web 一致直接出队。

实测证据（emulator，停用「工资卡」后记一笔 ¥12）：
- 记账后立刻出现「有 1 条本地记录待同步」——说明被拒项没有出队；
- 拉本地库（**必须连 `-wal` 一起拷**，只拷 `.db` 看到的是旧快照）：
  `outbox: retry_count=3, last_error='服务端拒绝该笔新增'`；
- 服务端该月没有 ¥12 这笔（正确，被拒）；
- 恢复「工资卡」后点「重试」→ 服务端出现 ¥12（`01M6JRGZG00G4ETNWPQR8SAHQ3`），提示条消失。

## 二、死信提示的容器条件漏了 deadCount → 死信永远看不见（鸿蒙）

死信时 `pendingSync` 一定是 0（那条已不再参与推送），而组装 hero 提醒条的外层判断写的是

```
if (this.heroTodos.length > 0 || this.pendingSync > 0) { …内层才是 pendingSync>0 || deadCount>0 }
```

无待办、无待同步时整条容器不渲染 → 内层再正确也白搭。
修：外层条件补 `|| this.deadCount > 0`。
（iOS 同一处写的是 `!heroTodos.isEmpty || pendingSync > 0 || deadCount > 0`，本来就对。）

## 三、冷启动不刷死信件数（两端都有）

- 鸿蒙 `LedgerScreen.aboutToAppear` 只手数 `Outbox.pendingCount()`，从不查 `deadLetters()`；
  而 `deadCount` 唯一会被赋值的时机是 `@Watch(DATA_VERSION)` → `refreshPending()`，
  冷启动时若服务端没有新变更，pull 不广播 DATA_VERSION，`deadCount` 永远停在 0。
- iOS 更彻底：`deadCount` 全程**没有任何赋值**（`LedgerScreen.swift` 里只有声明和读取）。

修：两端都收口成一个 `refreshPending()`（pending + dead 一起算），
`aboutToAppear` / `.task` / 通知回调 / `manualSync` 里统一调用；
`manualSync` 里把它提到 `report.skipped` 早返回**之前**（被跳过时计数也要刷）。

## 上机验证（鸿蒙 emulator 1320×2848）

| 路径 | 结果 |
|---|---|
| 毒丸新增（停用支付方式） | 本地入账 + 「有 1 条本地记录待同步」 |
| 连点「同步」三次 | `retry_count` 1→2→3，进死信 |
| 死信提示 | 「1 条记录同步失败，点「重试」再试一次」+ 按钮变「重试」 ✅ |
| 冷启动（重装保数据 `hdc install -r`） | 死信提示**仍然显示** ✅（修三之前不显示） |
| 恢复故障原因后点「重试」 | 推送成功、服务端有这笔、提示消失 ✅ |
| 设置页订阅刷新 | 停在设置页 → Home → 回前台（触发 pull）→ 新建的分类自动出现，无需离开页面 ✅ |

## 测试手法备查（这段浪费了不少时间，记下来）

- `uitest dumpLayout` **只看主窗口**。`bindSheet`（记账抽屉、分类选择器）是独立窗口，
  dump 里根本没有 —— 必须用 `snapshot_display` 截图 + `vision_crop` 按**原图像素**读坐标。
- 打开记账抽屉（下拉记一笔）的可用注入命令：
  `hdc shell uitest uiInput drag 660 1200 660 1900 300`（起点必须在列表区域内；
  起点在 hero 上、或 `uinput -T -g` 都不触发 PanGesture）。
- 抽屉内分类行 ≈ `(660, 957)`，支付方式竖排 ≈ `x=126, y=2120/2262/2405/2548`，
  数字键盘 ≈ `(373|630|887, 2150/2345/2540)`，保存 ≈ `(1157, 2490)`。
- 拷应用数据库核对状态：`hdc shell cp /data/app/el2/100/database/com.suenmoney.app/entry/rdb/suenmoney.db{,-wal,-shm}`
  然后 `hdc file recv`。**WAL 不拷就是脏读**（本次差点据此误判成「队列被清空」）。
- `hdc install -r` 保留数据，比 `hwdeploy.sh` 的「卸载重装」适合验证升级/冷启动行为
  （重装会清库，等于每次都要重新造毒丸）。
