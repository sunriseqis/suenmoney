## 一、改了什么

### 服务端

| 文件 | 改动 |
|---|---|
| `server/package.json` | 新增 `@fastify/static ^8.3.0` |
| `server/src/config.ts` | 新增 `webRoot`（默认 `../web/dist`）、`trustProxy`（**默认 false**）、`version`（env → 根 `VERSION` 文件 → `unknown`） |
| `server/src/http/server.ts` | `resolveWebRoot()` 导出；静态托管 + `onSend` 缓存头 + 404 分流；`/api/health` 补 `version` |
| `server/src/index.ts` | 启动日志打印「静态资源：<路径>」或「未启用（纯 API 模式）」 |
| `server/tests/http/static.test.ts` | 新增 7 条断言（见下） |

**404 分流是这一轮唯一真正危险的地方**，所以它有三条断言盯着：

```ts
// /api/* 未命中 → JSON；其余 → index.html（SPA 回退）
app.setNotFoundHandler((request, reply) => {
  if (request.url.startsWith('/api/') || indexHtml === null) {
    reply.code(404).send({ error: '接口不存在' });
    return;
  }
  reply.code(200).type('text/html; charset=utf-8').header('Cache-Control', 'no-cache');
  reply.send(indexHtml);
});
```

**缓存头的落点是 `onSend` 而不是 `setHeaders`** —— 后者会被 send 覆盖，表现为「配了但没生效」。
`/assets/*` 拿 30 天 `immutable`，`index.html` 一律 `no-cache`；两者必须配套，
否则用户会拿旧 HTML 去引用已消失的 hash 文件（白屏）。

## 二、三处「差点写错」的记录

### 1. 同源优先不能写在 `api/client.ts` 里 import `@/platform`

原方案写的是「用 `getPlatform()` 判平台」。落地时发现 `api/client.ts` 被
`web/tests/*.test.ts` **直接用 Node 加载**，而 `@/` 别名只有 Vite 认识
（`web/src/utils/bill-parser.ts` 里那条 `@/api/types` 之所以没暴露问题，是因为它 `import type`，
编译后就被抹掉了）。

于是改成模块内 6 行判定：只看 `window.Capacitor.isNativePlatform()` 与 `window.SuenHarmony / __HARMONY_NEXT__`
在不在。**代价是平台判定有两处实现**，收益是整个前端测试套件能继续在 Node 里跑 —— 这个交换是值的。

### 2. `trustProxy` 默认 false 是一个**行为变更**，不是纯新增

`server/src/http/server.ts` 原来硬编码 `trustProxy: true`（注释写着「部署形态是 nginx / Docker 反代在前面」）。
合并后 nginx 没了，服务端就在最前面，**信任 `X-Forwarded-For` 等于允许任何客户端伪造来源 IP**，
而登录限流是按 IP 计数的 —— 于是它变成绕过限流的入口。

改成 `SUENMONEY_TRUST_PROXY`（默认 `false`）之后有一个反直觉的后果要提醒用户：
**前面有反代却忘了开**，所有人会被算成同一个 IP，表现为「一个人试错口令，全家被限流」。
`docs/deploy.md` 第四节和第五节各写了一遍，属于刻意重复。

### 3. 顺手查出的文档幻像：`SUENMONEY_ADMIN_*` 从来没实现过

`docs/deploy.md` 旧版第二节写着「编辑 compose 里的 `SUENMONEY_ADMIN_USER/PASSWORD/NAME` 设初始管理员」。
`grep -rn "SUENMONEY_ADMIN" server/src server/scripts` → **零命中**。也就是说这一段是纯想象，
照着做的用户会以为配好了，实际库是空的。已删除，并改写为「初始化管理员表单 / `user:add` 命令」两条真路径。

> 教训：文档里的每个环境变量都该能被 `grep` 打到，否则它只是许愿。

## 四、没验证到的（必须由真机/真 Docker 补）

1. **`docker build` 一次都没跑** —— 本机 `docker: command not found`。风险点两个：
   ① web 阶段 `npm ci --ignore-scripts` 后 `vite build` 能否跑通（本机同条件已证明能跑，
   esbuild 现由 optional 平台包提供，不依赖 postinstall）；
   ② `COPY VERSION /app/VERSION` 与服务端 `cwd=/app/server` 读 `../VERSION` 是否对得上。
2. **旧数据卷升级核对**（P2-5）：需要一份 v1.1.6 双容器的 `suenmoney-data` 卷做对照。
3. **回滚演练**（DoD-5）：`git checkout v1.1.6 -- docker-compose.yml` 起旧双容器。
4. **GHCR 单镜像**（P3-1）：`docker manifest inspect ghcr.io/<owner>/suenmoney:latest` 应看到 amd64+arm64。

## 五、踩到的一个小坑（复现了飞牛方案里写的第 20 条）

手测完清理进程时写了 `ps -eo pid,args | grep "[n]ode-run.mjs src/index.ts" | awk '{print $1}' | xargs -r kill`，
**把自己的 shell 也匹配进去杀了**（命令串里就含这个模式，`[n]` 只防住了 grep 自己不防住整行）。

`docs/plan/2026-10-21-飞牛fnOS应用套件工程方案.md` 里那条
「清理进程时先 `ps` 再按 pid 杀，别用 `pkill -f`」是同一个坑 —— 这次是自己踩进自己的注释里。
正确做法是先把候选 pid 打印出来、确认不含 `$$`/`$PPID` 再杀。
