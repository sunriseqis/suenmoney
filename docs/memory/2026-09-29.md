### 二、信用卡记账与还款的统计核心口径判定

#### 1. 核心疑问
用户提问：「当我记录一笔信用卡支付的时候，比如9日消费的100元，这笔款会被记录，然后29日还款的时候要还100元，这笔款还会入账一次。那么统计的时候到底是100还是200？如果是100，如何展示的，如果是200那就是错误的。因为一笔消费被记录了两次，所以怎么处理需要你帮我思考一下。」

#### 2. SuenMoney 核心财务逻辑定义与结论
- **统计金额是 100 元，绝对不是 200 元**。
- **根本原理**：
  1. **消费日（9月9日）**：用户在商户处消费 100 元，支付方式为「信用卡」。此时**真实发生了支出（购买了商品/服务）**，账目记入 `expenses` 表：金额 -100 元，报表月度支出统计为 100 元。
  2. **还款日（9月29日）**：用户从银行储蓄卡划扣 100 元还给信用卡。在双式记账与财务原则中，这是**家庭内部资金划转（账户平账 / 清偿债务）**，**并不是新的家庭支出**（资产减少 100，负债减少 100，净资产不变，没有买任何新东西）。
  3. **展示机制**：
     - **仪表盘/概况页的「待还信用卡」卡片与提醒**：是**应付账款日历**（按每笔信用卡消费推演出的还款日 `repayment_date` 进行聚合汇总展示），用来提醒用户「29 日需要保证银行卡里有 100 元用于还款」，它**绝不会也不应该自动再去生成一笔 100 元的支出记录**。
     - **计划待办（`plan_todos`）的分期确认**：仅针对「分期计划」到期确认入账，普通的日常信用卡刷卡在记录时已完整入账，还款仅需核对银行账单，不二次入账。
     - 若未来增加「账户转账/还款确认」功能，也仅作为内部转账标记（Transfer），不计入月度支出报表。

### 五、分类与支付方式软删除支持

#### 1. 业务动机
- 用户提出：「还有支付方式分类应该支持删除啊？」
- 过去系统仅提供「停用（isEnabled: false）」，缺少直接删除多余分类或错误新建支付方式的途径。

#### 2. 安全设计与实现
- **安全约束原则**：
  - 分类：若分类下存在未删除的子分类，禁止删除，提示「请先删除或移走子分类」；若分类下已有支出记录，拦截并提示「该分类下已有 X 笔支出记录。为保证历史账单完整，无法直接删除；若不再使用，可先转移记录或将其停用。」
  - 支付方式：若支付方式下存在活跃计划，禁止删除，提示「还有 X 个计划关联了此支付方式」；若已有支出记录，拦截并提示「该支付方式下已有 X 笔支出记录。为保证历史账单完整，无法直接删除；若不再使用，可点击『停用』将其归档。」
  - 干净项（0 记录、0 子项/计划）：执行软删除 `deleted_at = nowIso()`，并写入 `changes` 变动日志（`op: 'delete'`），保障多端同步幂等性。
- **后端接口与仓储**：
  - `server/src/db/repo/categories.ts`：导出 `deleteCategory(db, id, actorId, deviceId)`。
  - `server/src/http/categories.ts`：新增 `DELETE /api/categories/:id`。
  - `server/src/db/repo/payment-methods.ts`：导出 `deletePaymentMethod(db, id, actorId, deviceId)`。
  - `server/src/http/payment-methods.ts`：新增 `DELETE /api/payment-methods/:id`。
  - 测试套件 `server/tests/http/categories-payment-methods.test.ts`：新增分类与支付方式删除测试，服务端测试 217 项 100% 通过。
- **前端支持（`web/src/api/index.ts` & `SettingsView.vue`）**：
  - API 客户端扩充 `categories.remove(id)` 与 `paymentMethods.remove(id)`。

#### 1. 业务动机与核心挑战
- 用户对账与批量建账场景下，直接导入微信支付与支付宝导出的 CSV 账单可免去上百笔逐一录入的沉重负担。
- 难点在于：
  1. 微信与支付宝导出账单在表头元数据、注释行、金额符号、支付渠道命名各异；
  2. 中文 Windows 环境下导出的 CSV 常为 GBK 编码，需自动识别 UTF-8 / GBK 杜绝乱码；
  3. 二级分类必须智能命中，且子分类必须优先于宽泛的一级大类；
  4. 导入需在前端支持收支筛选（仅导支出）、批量快速归类与逐行微调；
  5. 导入提交需后端原子事务支持，批量处理数百笔时不产生 N+1 查询，发生异常整批回滚；
  6. 年度生活与财务总结需要独立于冰冷数据报表的叙事化回顾（年度之最、月度起伏画卷、全景生活勋章）。

### 九、阶段五：Docker 部署与运维物理快照备份落地

#### 1. 业务动机与架构目标
- 目标：提供开箱即用、一键拉起的自托管生产级部署方案（Docker Compose）；
- 核心要求：
  1. **服务双容器分工**：`server` 跑 Fastify + node:sqlite；`web` 由 Nginx 托管 Vue 3 静态资源（含 Gzip 压缩与静态资源 1 年强缓存），并将 `/api/` 透明反向代理至 `server:3310`；
  2. **运维级物理快照（SQLite VACUUM INTO）**：区别于用户侧的 JSON 导出包，运维侧需自动生成一份完整的、WAL 归并后的真实 `.sqlite` 副本，每日自动调度，保留最近 N 份（默认 14 份），Web 界面支持直接下载与手动创建；
  3. **数据持久化与灾备**：命名卷 `suenmoney-data` 挂载至 `/app/server/data`，并提供基于物理快照的冷恢复指引与卷备份方案；
  4. **完整的部署文档**：编写 `docs/deploy.md` 详述架构、端口映射、环境变量与容灾操作。

#### 2. 全链路设计与实现

##### （1）运维快照仓储与每日调度器（`server/src/db/repo/snapshots.ts`）
- `createSnapshot(db)`：调用 SQLite 原生 `VACUUM INTO ?` 生成只读无锁物理副本 `suenmoney-snapshot-YYYYMMDD-HHmmss.sqlite`，并自动触发超额清理；
- `listSnapshots()`：遍历扫描快照目录，安全提取文件大小、创建时间，按时间降序排列；
- `getSnapshotPath(filename)`：正则表达式硬校验 `^suenmoney-snapshot-[\w.-]+\.sqlite$`，防范任何路径穿越（Path Traversal）漏洞；
- `deleteSnapshot(filename)`：安全删除指定快照文件；
