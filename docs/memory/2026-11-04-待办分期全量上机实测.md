# 待办/分期全量上机实测：又挖出 3 个真 bug（2026-11-04）

用户裁决：C1 色卡尽量一致、C2 问缓存量级、C3/C4 不管、**D 全测**。
本文记录 D 组（计划待办五动作、分期记账、4xx/401、改密码、备份口径）的实测结果。

## 一、修的问题

### 1. 色卡第 4~8 槽与 Web 不一致（C1）

- 权威值：`web/styles/proto/theme.css` 的 `.app[data-theme="cyber"]` 块里有 `--chart-1..8`
  = `#00ff88 #ff00ff #00d4ff #ffb020 #8b5cff #00a3ff #ff3366 #7dffd0`。
  （早先误以为 cyber 没有覆写 chart，其实第 135~142 行就是。）
- iOS `CYBER.chart1..8`、鸿蒙 `CYBER.chart1..8` **本来就是对的**；
  错的是两端共用的 16 槽分类调色板（鸿蒙 `CATEGORY_COLORS` / iOS `categoryColors`），
  它第 4~8 槽是另一套：`#FBBF24 #5FD6A8 #66C4CC #E07060 #93A5F0`。
- 已把两端第 4~8 槽改成 Web 值，第 9~16 槽保留（Web 只定义 8 个，原生扩展需要 16 槽不重复）。

### 2. 分期记完，本地什么都没有（两端）

`ExpenseEditor` 的分期分支直接调 `Api.createPlan()`（本地队列表达不了 periods/purchaseDate），
然后 `onSaved('')` 就结束了 —— **既没写本地，也没触发 pull**。
后果：刚记的分期在流水/hero「本月要还」/待办提醒条里全部不存在，要等下次冷启动才出现。
实测证据：创建分期后本地游标 496、服务端 500，那 4 条变更（1 计划 + 3 期次）没被拉下来。
修：`await Api.createPlan(...)` 之后立刻 `await SyncEngine.refresh()`（iOS 同名）。

### 3. `ack_at` 空串让「N 笔待处理」永远不出现（两端）

增量同步把服务端的 `null` 写成 `''`（`str()` 的兜底），而提醒查询写的是 `t.ack_at IS NULL`
→ 每一期都「看起来已被忽略过」，提醒条永不渲染。**这个功能在两端其实一直是坏的。**
修：`(t.ack_at IS NULL OR t.ack_at = '')`，两种「未摘除」都认（老装机数据也能救回来）。
实测：修前提醒条不出现，修后立刻显示「2 笔待处理」。

### 4. `will_auto_post` 是服务端派生值，本地永远是 0（两端）

服务端 `willAutoPost = plan.auto_post === 1 && hold_auto_post === 0`（`repo/plans.ts:261`），
**这是读时算出来的，不写进 change payload**；客户端却按字段读，于是本地全 0。
后果：概况页把「自动入账」的期次全显示成「需手动」，动作从 `ack` 变成 `confirm`
（只摘提醒 → 变成立刻入账，账目时点就错了）。
修：两端查询里按同一公式现算
`CASE WHEN COALESCE(p.auto_post,0)=1 THEN 1 ELSE 0 END AS will_auto_post`。
实测：修前「确认测试」显示「需手动/入账」，修后显示「自动/确认」，点确认 → 服务端 `ackAt` 有值、
`status` 仍 pending、**没有生成支出**（正是「只摘提醒，到期自动入账」的语义）。

## 三、C2 本地报表缓存会到多大（回答，不改代码）

- 键只有三种：`report:monthly:YYYY-MM`、`report:yearly:YYYY`、`report:summary:all`，
  没有筛选参数变体（`ReportScreen`/`AnnualScreen`/`LedgerScreen` 全部走这三个模板）。
- 实测单条响应大小（81 笔的库）：月报 **5.7 KB**、年报 **5.4 KB**、汇总 **4.2 KB**。
  体量取决于**分类数 + Top-N 列表**，不随笔数线性增长，量级就在 5~15 KB/条。
- 估算上限（无淘汰策略下）：
  - 翻 24 个月 + 3 年 + 汇总 ≈ 24×8 + 3×6 + 4 ≈ **220 KB**
  - 极端翻完 10 年历史（120 个月）≈ 120×8 + 10×6 + 4 ≈ **1.0 MB**
- 结论：条目数被「有账的月份数」天然限住，**不会无限增长**，1 MB 量级对手机无感。
  所以不必须加淘汰；若要加，最省事的是定期删 `fetchedAt` 超过 30 天的键。

## 四、流水页顶卡待办动作：Web 在重构时丢了（已补回）

**裁定是有的**：`docs/reports/hw/2026-10-27-功能回归验收清单.md` C3 原文 ——
「点待办条 → 展开明细… **每条含「处理」「忽略」**（逾期只给「入账」）」，来源标注
「`LedgerView.vue:397-420` + 用户 2026-10-29 裁决」，且当时打了 ✅。

**老 Web 真有过**：`edc865e`（第四轮 UI）里 `plansStore.confirmTodo` / `skipTodo` 俱全，
模板里还有「忽略」按钮。

**是被换掉没的**：`c48831d refactor(web)!: 切换到重构版 —— web-v2 换名为 web`。
web-v2 把动作层只做到了概况页（`DashboardView.todoAction`），流水页顶卡退化成纯展示
（提货时那个文件里 `confirmTodo/skipTodo/ackTodo` 一个都不剩）。

**已按裁定补回**（`web/src/views/LedgerView.vue`）：
- 每行右侧加「处理」/「忽略」；`todoOverdue(t)` 为真时只留「入账」（= confirm），不给忽略。
- 语义与两端原生逐字一致：处理=confirm（立刻入账）；忽略=自动入账类走 ack（只摘提醒）、
  否则走 skip（本期不入账）；toast 文案也照抄。
- 动作后 `reload() + reloadReports()`：确认会立刻生成一笔支出，不重读会让顶卡停在旧数。
- 样式 `.todo-act` 单独给 `flex: 0 0 auto` + 小内距，标题靠 `min-width:0` 让位，360px 不换行。

教训：Web 是「现状优先」的基准，但它自己也会被重构悄悄削掉功能 ——
两边不一致时**先查验收清单和 git 历史，别默认原生端多做了**。

## 五、仍然存在、需要裁决的差异

- **流水页顶卡的待办行**：Web 移动端那里是**只读**（只显示「N 期·计划名 / 自动·需手动 / 金额」），
  动作在概况页；鸿蒙在流水页顶卡额外给了「入账/忽略/处理」。属于原生端多做的一层，
  不是 bug，但和「1:1」有出入 —— 要不要砍掉等你定。
- 概况页的动作集合（确认/入账/忽略本期）与 Web 一致，已验。

## 五、测试手法备查

- 待办动作必须等推送（300ms 防抖 + 一次网络往返）再看服务端，**提前查会误判成没生效**。
- `GET /api/plan-todos?today=YYYY-MM-DD` 会**先结算到期的自动入账期次**再返回；
  不带 `today` 不结算。手工造「到期自动入账」场景时注意这点。
- 测试计划用完要 `DELETE /api/plans/:id`（软删计划 + 相关期次，已生成支出保留），
  否则会一直出现在待办里。
- 模板字符串里写 SQL 注释**不能出现反引号**，否则字符串提前结束、ArkTS 报一堆看不懂的错。
