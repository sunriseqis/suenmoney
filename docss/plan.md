# 路线图与进度

## 推进顺序

先跑通前后端 + Web，验证无误后再做 Docker 部署优化，然后交叉编译到移动端，
最后做离线同步与 iOS。

**离线排在移动端阶段**，因为它是移动端特有的需求（Web 端总在线，且承担管理后台职责）。
**数据导入导出同理**：只在 Web 端提供，移动端不做（见第三轮分支 F）。
但**离线的数据模型约束必须在阶段一就写进 schema**（ULID 主键、软删除、
`rev` / `device_id`、`changes` 表）—— 这些如果等移动端再补，等于给所有表做一次
破坏性迁移。所以阶段一零额外成本，移动端阶段只是补实现。

## 浏览器验证怎么做

需要 Playwright 自己的浏览器构建（**原版 Firefox 不支持它依赖的 juggler 协议**，
所以系统装了 Firefox 也仍然要下载）。

```bash
# 国内网络用镜像（PLAYWRIGHT_DOWNLOAD_HOST）
PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright \
  playwright-cli install-browser firefox

# 在仓库外的目录运行，避免 .playwright-cli/ 污染仓库
cd /tmp && playwright-cli open --browser=firefox http://127.0.0.1:5310/
```

浏览器缓存在 `~/Library/Caches/ms-playwright/`（工具缓存，不是记忆目录）。

## 界面与交互返工（第三轮）

起因：第二轮修完后逐条提出 9 个界面与交互问题，同日追加一条数据进出的边界补充。
**方案文档：`docs/design/ui-rework-2.md`**（含核查到的代码事实、决策与理由、落地顺序）。

逐条核过代码后，9 条不是同一种东西：

| 性质 | 条数 | 是哪几条 |
|---|---|---|
| 真 bug | 2 | 数字键盘错位、月份无法快跳 |
| 功能缺失 | 3 | 导出导入、分类改不了、计划无撤销 |
| 布局 / 信息架构 | 4 | 桌面月份占一行、底栏记一笔、报表右侧空白、抽屉要下滑 |

归成六件事：

| 分支 | 覆盖的问题 | 一句话 |
|---|---|---|
| A | 1、2 | 抽 `PeriodPicker`，三处共用，标题可点开年月面板 |
| B | 6 | 报表**块纵向堆叠、块内两栏**；首页删掉与报表重复的那块、改补四项指标 |
| C | 4、5、7 | 底栏记一笔移到最右 + 软色底衬；键盘只修错位；抽屉常驻摘要行 |
| D | 9 | 分类可改名 / 换图标 / 换色，可在**同深度**移动；一级笔数改累计子分类 |
| E | 8 | 计划待办的**撤销**与**跳过恢复**（唯一动 schema 的一件，migration 002） |
| F | 3 + 补充 | 导出（可按范围）/ 导入 / 备份恢复，**仅 Web** |

**本轮最有价值的三处核查结论**（都是"看起来是设计问题、其实是实现缺失"）：

1. **报表右侧那 700px 空白不是分栏回来的**，是上一轮为修「图例被拉到 1000px 宽」
   而加的 `max-w-[22rem]` —— 修 A 造成的 B。解法是块内两栏，不是撤掉宽度上限。
2. **撤销入账对自动入账的计划是假的。** `settleAutoPost` 的选取条件是
   `status='pending' AND auto_post=1 AND 还款日 <= 今天`，只把状态改回 `pending`
   会被立刻重新入账，且不报错。必须加「本期不再自动入账」标记。
3. **导出与备份必须是两个功能。** 只做一个入口加一个范围参数，用户会把
   「按月导出」当月度备份拿去恢复，静默丢掉其他月份。

**落地顺序**（依赖少、改完立刻可见的在前）：
键盘错位 → `PeriodPicker` 与两页接入 → 底栏与抽屉 → 报表块内布局与首页补指标 →
分类改造 → 计划撤销链路（含 migration 002）→ 导出 / 导入 / 备份。

> **这一轮不先改代码，先让这份预览过一遍。**
>
> **预览页已经过八轮反馈**，第九版（一条明细必须真的是一行）加了：
> ① **报表按档位组织块**（月 8 / 年 7 / 汇总 5，换档 = 换掉一整组块）

> ③ **移动端顶卡**：本月支出与处理提醒**同行**（有提醒两列 / 无提醒独占整列），
> 提醒**默认收起、点击向下展开**
> ④ **卡片不为对齐而撑高**：`.grid` 一律 `align-items: start`，
> 危险区改**通栏一条**（原先卡内空 89px）
> ⑤ **控制行**：期间靠左 + 三个入口靠右（同一行），**搜索独占一行**；
> 入口**只存在于流水页顶部、不吸顶**，二级页里不重复
> ⑥ **提醒展开后要能动手，桌面与移动端都要**：会自动入账 → **「确认」**；
> 不会 → **「入账 / 忽略」**（三按钮等长）
> ⑦ **二级页关闭收进标题行行尾**（`设置 ×`，不单独占一行）
> ⑧ **流水三档三形态**：**月＝列表 / 年＝12 个月格日历 / 全部＝一格一年日历**；
> 日历**点一下只选中（下方卡切到这个期间）、再点或按「进入」才下钻**
> ⑨ **提醒改颜色标记、不染卡片**：颜色**挂在展开箭头上**（中性 / 黄 / 红），
> **展开后不再重复标记**，紧急度走**文字颜色**
> ⑩ **日历是流水页年 / 全部两档的形态**（第七次更正：原先误放在报表页）——
> 点年跳月、点月进流水；**不新增页面与路由**
> ⑪ **流水行改「一行一项」**：主名与副信息同行，装不下时副信息截断，**行高固定不换行**
> ⑫ **组头设计整套移除**（第八次）：`.daygroup` 连样式带脚本删掉，月档直接就是明细
> ⑬ **日历加「花销深浅」四档**（第八次）：只用强调色的四个透明度
> （最多 / 稍多 / 均值上下 / 最少），基准是均值；**除提醒与标记外，其余颜色一律沿用强调色**
> ⑭ **一条明细必须真的是一行**（第九次）：修掉两个让它「多行 / 显示不完全」的**结构**问题 ——
> 流水行的网格规则被同名类覆盖、提醒行缺 `min-width:0`；**再**挤掉文案水分
> （`第 3 期`→`3期`、`需手动入账`→`需手动`，`自动入账` 不删）
> ⑮ **删掉日历的四档图例**（第十次）：那条「越深＝花得越多（月均 ¥8,033）」的载荷
> 只有一个月均数，而这个数就在它正上方的汇总行里 —— **同一页出现两次不是强调**
> ⑯ **所有页面里的「说明式文字」全部拿掉**（第十次）：判据＝**这句话有没有改变你要做什么**

「日均」那一条最能说明问题：首页与报表**走同一个 `elapsedDays`，两个数字逐位相同**，
却被当成两个独立指标各占一格。**现在是「同一个数字换四种字体」，不是「四个不同的答案」。**

读 BeeCount 的源码与预览图后确认，它值得学的是**七件事**：

1. **一页里多个时间维度各司其职** —— 这是「有效信息」的唯一机制
2. **顶层三档时间维度（本月 / 今年 / 汇总）**，其中「汇总」我们完全没有
3. **用颜色深浅编码金额**（月度热力图）
4. **「坚持」类指标**（记录天数 / 记账习惯 笔每天）—— 字段有，从没展示过
5. **Top 5 排行，且取「今年」口径** —— 跳出当期看长期
6. **对比型指标带进度条**（不只给一个数，还给「到了哪」）
7. **口径要说出来**；**没有记录的月份显示 `—` 而不是 `0`**
8. **「提醒」做成 hero 底部的一条计数 chip + 悬停展开 + 归因**，
   而不是一个区块（`home.insights.*`：`注意：异常 2 个月` → `9月 · 比月均高 116% ·
   手机数码 10,999（本月独有）`）。**它不占格、空态不空洞、可增可减**

**后来又把它部署实例实测了一遍**（`/app` 下 v1.6.3，无头 Firefox 逐页截图 +
扒前端产物的 1,626 条 i18n 词条）。实测才发现的三件事，读源码是看不出来的：

1. **Web 端根本没有「计划 / 待办 / 提醒」** —— 词频：提醒 0 · 计划 0 · 待办 0 ·
   到期 0 · 逾期 0。它不是「把提醒放在某一页」，是**没有这个实体**：它的「还款」
   只是账户的两个字段（账单日 / 还款日），在资产页显示成「还有 3 天」。
   而**我们有真正的计划实体，且金额与期数都是确定的** —— 所以我们的提醒
   应该直接带金额（`第 3 期 ¥2,800`），这是比它多出来的能力
2. **它的交易页是扁平列表 + 分页**（20/页、共 162 页），**不做分组** ——
   与第四轮原先定的「流水页按天分组」相反。**后来这一条连我们的「按天分组」也被推翻了**：
   用户改成**分组层级随档位**（月无组头 / 年按月 / 汇总两级），理由是一个月会长出
   28~31 个组头，而月档的期间是已知的。详见方案文档 §6.2
3. **它没有报表页**，分析全在首页的「扩展分析」区 ——
   我们的报表页因此必须**自证存在理由**。
   **这条后来答了**：首页被定为「只看量、横跨月年总」之后，
   报表页的存在理由变成结构性的 —— **首页给不了「构成」，也给不了「精度」**

**明确不学**：多账本 / 资产账户 / 标签 / 币种 / 附件（会把项目推向通用记账，
代价是每一页都要重新设计一次）、20 套头部皮肤、AI 记账、社区运营那一套、
分类管理拆成四张页面。

**一个重要的边界判断**：核 `001_init.sql` 后确认我们**没有** `budgets` 表、
`expenses` **没有** `direction`（单向金额，做不出收入 / 结余）。
但 `expenses` 有 **`spend_date` / `posting_date` / `repayment_date` 三个日期**
+ 两级分类 + `created_at` —— 而目前只用了 `repayment_date` 一个（月份归属），
另外几个**一次都没在界面上出现过**。

> **所以这一轮的价值大头是把已有的三个日期、两级分类、`created_at` 用透，而不是加表。**

**最有价值的五条新东西**：

1. **「汇总」这一档**——它是唯一能回答「我一共花了多少 / 一共记了多久」的维度。
   没有它，整站永远只有「当期」，也就永远只有那几个数可以放
2. **月度支出热力图**——一眼扫出哪个月最多，且能触发回忆。
   三条细则：单色深浅（不叠色相）· 格内放金额（不只有颜色）· 没有记录显示 `—` 不是 `0`
3. **首页「预计月末」**——`已花 ÷ 已过天数 × 当月总天数`。
   陷阱：月初第 1 天会算成「一天的金额 × 30」，误差可达十倍，
   所以**每当前 3 天不显示这一格**（这个「不显示」是刻意的）
4. **报表「下月要还」+「涨跌榜」**——前者是能让人改变行为的数字；
   后者按**变化额**排序，回答「这个月是什么让我多花了 800 块」
   （分类构成是按金额排的，永远是那几个大类常驻，看不出变化）
5. **「首页 / 报表 = 量 / 结构」这条二分**——它比「删掉重复的数字」更能解决问题。
   上一版靠「一级 / 二级」给分类分家，结果**两页都成了半成品**（首页有分类但看不到二级、
   报表有二级但没有总量），用户也永远记不清该去哪页。按**问题**分之后，
   边界一句话说得清，还能用 grep 验收
