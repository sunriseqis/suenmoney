### 本轮最有价值的三处核查结论（都是"看起来是设计问题、其实是实现缺失"）

1. **报表右侧约 700px 空白不是分栏回来的**，是上一轮为修「图例被拉到 1000px 宽
   中间空 600px」而加的 `max-w-[22rem]` —— 修 A 造成的 B。解法是块内两栏，
   不是撤掉宽度上限（撤了就退回原来的病）。
2. **"撤销入账"对自动入账的计划是假的。** `settleAutoPost` 的选取条件是
   `t.status='pending' AND p.auto_post=1 AND t.repayment_date <= today`
   （`server/src/db/repo/plans.ts:972-974`）。只把状态改回 `pending`，
   用户下次打开首页它就被重新入账，且**不报错**。必须加「本期不再自动入账」
   标记（migration 002）。恢复跳过的期次同理。
3. **导出和备份必须是两个功能、两个入口。** 只做一个入口加一个范围参数，
   用户会把「按月导出」当月度备份拿去恢复 → 静默丢掉其他月份。

- 提骨架用「注释段落 + 方法定义 + 大写开头的 widget 构造」三类标记，
  比通读 1200 行快得多。

### 诊断结论（这一轮的核心）

**「有效信息太少」和「重复性太高」是同一个病**：同一份内容被摊成了好几份。

| 重复的东西 | 次数 | 位置 |
|---|---|---|
| **本月支出总额** | **4** | 首页 hero / 报表大数字 / 报表环图中心 / 流水页合计 |
| 笔数 | 3 | 首页 hero / 报表「共 N 笔」/ 流水页「已加载 N 笔」 |
| 环比、日均 | 各 2 | 首页 hero 与报表概览 |
| 还款日 + 紧急度 | 2 | 首页「本月待还」/ 报表「按支付方式」 |

最有力的一条证据：首页与报表的「日均」**走同一个 `elapsedDays`，数值逐位相同**，
却被当成两个独立指标各占一格。
一句话概括：**现在是「同一个数字换四种字体」，不是「四个不同的答案」。**

### 数据边界（重要，决定了哪些信息根本做不出来）

核 `001_init.sql`：

- ❌ **没有 `budgets` 表** → 预算要新建（`settings` 是通用 key-value 表，目前完全没用）
- ❌ **`expenses` 没有 `direction`**，金额单向（`CHECK (amount_cents <> 0)`）
  → **收入 / 结余做不出来**
- ❌ 无账本表 / 币种 / 标签 / 附件
- ✅ **`expenses` 有三个日期**：`spend_date` / `posting_date` / `repayment_date`
  —— 目前只用了 `repayment_date` 一个（月份归属），**另外两个一次都没在界面上出现过**
- ✅ `categories` 有 `depth` / `parent_id` / `icon` / `color` / `sort_order` / `is_enabled`

> **判断**：这一轮的价值大头是**把已有的三个日期和两级分类用透，而不是加表**。

### BeeCount 值得学的四件事（其余明确不学）

1. 首页以**流水为主体** —— 信息量来自会持续增长的流水，而不是造区块
2. 一页里用**视角把维度乘开**（分析页 = 视角 × 周期 × 形态 三层）
3. 给**前瞻性**数字（它预算页的「日均可用 / 剩余 N 天」），不要只给回顾性的「较上月」
4. 排行榜每行都带金额、且**可下钻**；**口径要说出来**

不学：多账本 / 多币种 / 资产账户 / 标签 / 附件（会把项目推向通用记账，
代价是每一页都要重新设计一次）、20 套头部皮肤、AI 记账、社区运营那一套。

### 四页新分工（同一数字只在一处出现）

| 页面 | 时间窗口 | 回答 |
|---|---|---|
| 首页 | 当月 | 这个月怎么样了 |
| 流水 | 任意期间 | 那笔在哪 |
| 报表 | 月 / 年 | 比出来、再拆下去 |
| 设置 | 全部 | 我的东西在哪 |

两条最值得落实的新东西：
- **首页「预计月末」**= `已花 ÷ 已过天数 × 当月总天数`。
  **陷阱**：月初第 1 天会算成「一天的金额 × 30」，误差可达十倍
  → **每当前 3 天不显示这一格**（这个「不显示」是刻意的，不是没做）
- **报表「下月要还」**（把 `repayment_date` 平移到下月）+ **「本期洞察」**
  （3 条规则引擎生成的句子，把数字翻译成人话，**不需要 AI**）

### 顺手修掉的一个测试错

`tests/http/data.test.ts` 的恢复用例：
`readdirSync(backupDir).some(n => n.startsWith('pre-restore-'))` 失败。
**是测试写错了，不是代码错了** —— `writePreRestoreSnapshot()` 落在
`join(config.backupDir, 'pre-restore')`，即 `backupDir` 下的**子目录**里。
改成读子目录后 **15/15 全过**。

**教训**：同一行里前两句断言（`snapshot.startsWith(backupDir)`、`existsSync`）
都**跟着被测代码的返回值走**，所以过了；第三句是**凭印象写目录层级**的，所以错了。
→ **凡是断言里出现「我以为文件在哪」，都要改成从被测代码的返回值推。**

### 两条修正推翻了什么

| 意见 | 推翻了什么 |
|---|---|
| 报表按档位显示块 | 「三档只值一个大数字」—— 档位其实是**页面的组织方式** |
| 移动端只留一页 | 「四页平权 + 底栏四格」 |

### 三条能复用的判断

1. **「无关的不显示」的判据不是「能不能算出数」**。
   每个块在三档上**都算得出数**（「较上期」永远能算），所以按「能不能算出来」判，
   结果是一块都不减。有效判据是「**这一档下它还在不在回答一个新问题**」——
   年档去掉「还款节奏」是因为它退化成「全年各方式占比」，而那是「分类构成」已经答过的；
   汇总档去掉「对照 + 涨跌榜」是因为它们都依赖「较谁」。
   → **边界是「答案有没有重复」，不是「屏数够不够」。**
   块数：月 8 / 年 7 / 汇总 5（含档位卡本身）。

2. **一个东西可以有「两个落点」，只要落点由平台决定**。
   提醒条跟着**落地页**走：桌面落地页是概况 → hero 底部；移动端落地页是流水页 → 页顶。
   重复的判据是「**同一个平台内出现几次**」，不是「全站一共出现几次」。
   反过来说，移动端概况的 hero 上必须**不再**留提醒条。

3. **「收纳低频入口」最容易走歪成「把底栏搬到上面」**。
   判据是视觉语言必须与底栏不同：底栏 = 等宽四格 + 图标在上 + **有选中态**（导航，答「你在哪一页」）；
   入口行 = 一行不定宽次要链接 + **无选中态** + **随内容滚走**（入口，答「还有几个地方可以去」）。
   最后一条最关键：**入口行滚走，底栏不滚**。

## 第四轮方案 · 第五次修正（控制行拆分 / 提醒可动手 / 二级页关闭入标题行）

### 关键判断

- **第 1 条：我上一版的判据只算了语义、没算视觉重量**。三个 12px 链接独占一行时，

> 它是这个界面里**唯一表达「能展开」的符号**，没有替代品。

### ⑥ 日历深浅：四档、以均值为轴

| 档 | 含义 | 判据（m ＝ 均值） | 底色 |
|---|---|---|---|
| 4 | 最多 · 最深 | ≥ 1.5 m | `rgba(59,130,246,.42)` |
| 3 | 稍多 · 略深 | 1.15~1.5 m | `.24` |
| 2 | 平均数上下 · 普通 | 0.85~1.15 m | `.12` |
| 1 | 最少 · 最浅 | < 0.85 m | `.05` |
| 0 | 一笔都没有 | ＝ 0 | 透明 + 描边 |

**为什么以均值为轴、不在最大最小之间等分**：用户说「**平均数上下＝普通**」——
这句话要求「普通」跨在均值两侧。按最大最小等分的话，

| | 用什么说 | 说什么 |

| 提醒 | **色相**（黄 / 红） | 需不需要你动手 |

## 第九次修正：一条明细必须真的是一行（同日）

**用户给了一张真机截图**（提醒条 3 条 + 流水行 2 条），标了两处：
**「显示不完全，文字精简」**（提醒行）、**「多行」**（流水行），并给判据：
> 如果文字确实必要无法精简，重新设计布局，起码保证视觉上应该是一行。

### 关键发现：两处症状的主因都不是文案长

**① 流水行 —— 那条网格规则从来没生效过。**

```css
.trow--dated { grid-template-columns: 30px 26px minmax(0,1fr) auto; }  /* 写在前面 */
.trow        { grid-template-columns: 26px minmax(0,1fr) auto; }      /* 写在后面 */
```

特异性相同（都是 0,1,0）→ **源码顺序在后的 `.trow` 整条覆盖了 `.trow--dated`**。
后果精确可推、和截图完全对得上：4 个格子塞进 3 列 →
**金额被挤到第 2 行第 1 列**（所以 `¥62` 出现在左边缘）；
**日期列从 30px 掉回 26px** → 装不下「28日」→ 在「8」和「日」之间断行 → 竖排。

修法：`.trow.trow--dated`（0,2,0）提特异性 + 日期列改 `max-content` + `nowrap`。

**② 提醒行 —— flex 项的 `min-width` 默认是 `auto`，即「不小于内容宽度」，也就是缩不动。**

五个格子里，**唯一该缩的那格（计划名）恰好没写 `min-width:0`**，
而**唯一写了 `min-width:0` 的（状态词）被截断**。
→ **该缩的缩不动、不该缩的被截断** → 整行撑破卡片 → 按钮压到状态词上。

修法：把宽度纪律写进 CSS ——
金额 / 紧急度 / 状态 / 按钮 `flex:0 0 auto`（永不截断），**只有计划名 `flex:0 1 auto; min-width:0`**。

### 三条可复用的判断

> ① **「写了规则」和「规则生效」是两件事，中间隔着一个源码顺序。**
> 同一元素的多个类规则分散在两处时，**顺序就是一个不出现在任何规则里的隐形优先级**。
> 覆盖要么靠特异性、要么就近书写；**绝不能靠「我记得它在后面」**。

> ② **`min-width:auto` 会偷偷禁止 flex 项收缩。**
> 「哪一格可以被牺牲」必须**写进 CSS**，不能只写在文档里 ——
> 文档说「状态词可截断」，代码里那格有 `min-width:0`，而**真正该缩的那格什么也没写**。
> **只写在文档里的纪律，等于没有纪律。**

> ③ **「一行的容量」有上限，减到某个点就不能再减。**
> 那个点就是「再减会删掉一条推不出来的信息」。
> **到了这个点，该改的是布局，不是文案** —— 这正是用户那句话的意思。

### 一、`A22` 版式基线：落地时**改了写法**（本轮最值得记的一条）

方案原定 `.grid { align-items: start }` —— 「一行 CSS 关掉全站的默认撑高」。
**落地时发现不能这么写**：数字键盘（`NumericKeypad.vue`）与期间选择器（`PeriodPicker.vue`）

→ 落成**新类 `.card-grid`**（`base.css` `@layer components`），只给卡片网格用。

**教训：** 「一行 CSS」听起来最省事，但**那一行改的是别人依赖的默认值**。
写方案时判「这条改动小」只看行数，没问「谁正依赖这个默认值」。
这是第九次「写了规则 ≠ 规则生效」的**镜像**：那次是改了没生效，这次是生效了但改错了对象。

### 五、用户反馈问题修复与细节调优（第十三次记录）

1. **报表页分类构成环图文字错位修复**（`web/src/views/ReportView.vue`）：
   - **根本原因**：桌面视口下父容器采用 `lg:grid lg:grid-cols-[200px_minmax(0,1fr)]`，环图所在的 `div` 作为 Grid 子项，默认水平拉伸撑满 200px 宽；而内部 SVG 尺寸为固定 140px 居左，覆盖层文字采用 `absolute inset-0` 撑满 200px 并在 100px 处水平居中，导致中心文字与圆心（70px 处）发生 30px 的横向视觉错位。
   - **修复方案**：给环图容器明确指定 `w-[140px] h-[140px] justify-self-center`，使容器、SVG、文字覆盖层均绝对对齐于 140px 几何中心，并调为 `text-sm leading-tight` 确保文字紧凑居中不溢出。
2. **概况热力图点击路由报错修复**（`web/src/views/DashboardView.vue`）：
   - **根本原因**：`onHeatCellClick` 点击热力图月份单元格跳转时，调用了 `router.push({ name: 'reports' })`，而路由定义中的命名为单数 `report`，导致控制台报错 `No match for {"name":"reports"}`。
   - **修复方案**：更正为 `router.push({ name: 'report', query: { month: targetMonth } })`。
3. **设置页「数据」Tab 导入导出卡片合并与平铺**（`web/src/components/DataPanel.vue`）：
   - **根本原因**：原先采用 `.card-grid lg:grid-cols-2` 左右两栏并排，左侧导出卡片因包含范围选择、年月下拉、两行导出动作，高度达 240px+；右侧导入卡片仅有一虚线框，高度仅 160px，由于卡片不拉伸原则导致底部明显高低不平、参差别扭。
   - **重构方案**：将导入卡片直接并入导出卡片，组成通栏的「导出与导入」卡片。顶部靠右放置导出范围选择，主体区采用 `grid grid-cols-1 md:grid-cols-3 gap-3` 平铺：
     - ① 数据包 · JSON 导出
     - ② 对账表 · CSV 导出
     - ③ 数据包导入（选择 JSON 文件上传）
     三栏等宽等高，底端操作按钮水平对齐，彻底消除桌面端视觉落差。
